# T98 规格：「有声读物」识别 + **按集序**排列（不乱）

> 状态：**规格先行**（实现前定稿）。
> 起草：2026-11-16。
> 前置任务：T97（「随机 20 首」组一个歌单）。
> 用户拍板（2026-11-16）：① **新开一个「有声读物」页**；② **宁可多标 + 一键改判**；
> ③ **只对有声专辑生效**（普通专辑不给排序开关）。

---

## 零、不变量（**先写死，后面所有设计都受它约束**）

1. **曲库 = 当前登录用户自己的 NAS 曲库**，规模与内容**因人而异**
   ⇒ 本功能**不假设曲库有多大**，一切规模相关的量**运行时算**。
2. **识别靠「结构信号」，不靠名字、也不靠目录名** —— 实测：专辑名关键词的误报极高
   （「小说」12 个、「广播剧」17 个、「有声」7 张专辑，**几乎全是音乐专辑 / 晚会 / 主题曲**）；
   目录名同样因人而异（用户的是「有声小说」，别的库可能叫别的）⇒ **一律不引用**。
3. **「不乱」= 稳定排序 + 同键保原序**：宁可把解析不出集号的排在**后面**，
   也**不丢、不重、不打乱**已有相对次序。
4. **服务端行为不写死成契约**：一切「服务端认不认某个参数 / 怎么排序」的结论
   都标注「实测（哪台机、哪个账号、何时）」。
5. **识别一定会错 ⇒ 必须可人工改判**（用户拍板「宁可多标 + 一键改判」）。
6. 客户端**不新增 npm 依赖**；既有测试**一条不许删、断言一条不许弱化**。

---

## 一、目标与不做

### 目标

- 顶栏**曲库导航**加一项「有声」⇒ 一个**独立的「有声读物」页**；
  页里列出被判定为「有声读物」的专辑，并**显示判定依据**（可解释，不是黑箱）；
- 点进这样的专辑 ⇒ **详情页自动按集序排列**（不乱），并显示集号；
- 用户可**一键改判**（「这是有声」/「这不是有声」）⇒ 本地记住，改判优先于自动判定。

### 明确不做

- ❌ 不做「有声内容推荐 / 发现」（那是另一件事）；
- ❌ **不给普通专辑加排序开关**（用户拍板：只对有声专辑生效 ⇒ 不误伤）；
- ❌ 不改服务端行为（服务端「同秒无二级排序键」是**服务端的事实**，客户端只能规避）；
- ❌ 不引新 npm 依赖。

## 二、探针实测基线（**服务端事实**，2026-11-16，本机 + 该账号）

> 探针脚本：`release/verify/t98-01..15-*.mjs`（gitignored）。
> 手法：隔离 userData（只复制 `session.bin` + `Local State`）+ **真实 NAS** +
> 渲染进程里直发 `fnm://srv/…`。
> ⚠️ 探针输出**只记形状与计数**，不落真实歌名 / 标识（少量示例只打控制台）。
> ⚠️ **方法论**（本轮踩坑）：搜索是 **top-N 截断**且**命中集不稳定** ⇒
> **「搜不到」不能证明「不存在」**（§2.8）⇒ 存在性结论一律靠**全量扫描**。

### 2.1 `/track/album-detail/list`（专辑曲目）

| 项 | 实测 |
|---|---|
| **默认顺序** | **== `createdAt,asc`**（3 个专辑逐一比对，全部一致） |
| `sort=title,asc` | **生效**（与默认顺序**不同** ⇒ 服务端确实按标题排了） |
| `sort=createdAt,asc` | 生效（== 默认） |
| 分页 | `albumGUID` + `page` + `size` 生效 |

⇒ **服务端能按标题排**；但客户端仍要自己排（理由见 §2.2 与 §四）。

### 2.2 ⚠️「乱」的真正来源：**服务端同秒没有二级排序键**

- `createdAt` 是 **Unix 秒**；
- 实测：多个专辑的返回顺序 `createdAt` **升序但非严格增**
  ⇒ **同一批导入的曲目 `createdAt` 完全相同**；
- ⇒ 服务端在同秒曲目之间**没有二级排序键** ⇒ 相对次序 = 数据库物理序
  ⇒ **用户看到的「乱序」不是客户端 bug，是服务端同秒无序**。

⇒ 客户端唯一能做的就是：**自己给一个确定的次级键**（集号 / `trackNo` / 原序）。

### 2.3 数据形状（`Song` 的三个字段都不可靠）

| 字段 | 实测 | 结论 |
|---|---|---|
| `trackNo` | 39 首只有 **14** 个不同号、28 首只有 **13** 个 ⇒ **同号多条**；但在晚会类专辑里它**就是真实节目编号**（`[9,16,20,27]`、`[13,2,8,12]`） | ⇒ **要先验质量再用**：有值率 ≥ 90% **且** 去重率 ≥ 90% 才可信 |
| `discNo` | 几乎**恒为 1** | ⇒ 没用 |
| 标题集号 | 「第X集」类**几乎为 0**；「日期.序号」类（`17.0315丨标题`）**37/37 命中** | ⇒ 集号**在标题里**，且**要按数值比**（字典序会把 `10.1` 排到 `9.1` 前面） |
| `duration` | 单位**毫秒**（代码 `msToSeconds` 正确）⇒ 单曲 3–5 分钟；课程/有声 6–15 分钟；合集 50+ 分钟 | ⇒ **时长是最稳的结构信号** |

### 2.4 ⚠️ 名字关键词**极不可靠**（实测逐个看过）

| 关键词 | 命中专辑数 | 实际是什么 |
|---|---|---|
| 有声 | 7 | 音乐专辑（「有声有影」「无声胜有声」…） |
| 小说 | 12 | 音乐专辑（「大小说家」「短篇小说-黄凯芹」…） |
| 听书 | 7 | DJ 版 / 音乐 |
| 广播剧 | 31 | **晚会与主题曲**（「2023年中央广播电视总台春节联欢晚会」…） |
| 书 | 109 | 绝大多数是音乐 |

⇒ **名字只能当弱信号**，绝不单独成立。

### 2.5 ⚠️「集数多」**也不是**信号

集数最大的前 5 个专辑（1527 / 1003 / 542 / 352 / 219 集）实测全是
**DJ 合辑 / 垃圾合辑**（标题如「QQ群号：…」「串烧大碟」）
⇒ **不能靠集数判「有声」**。

### 2.6 全库结构扫描（T98-13，**全量扫完**，2026-11-16，本机 + 该账号）

扫描口径：`/track/list` **869 页 / 173,671 首**（`size=200`，`sort=createdAt,desc`）
+ `/album/list` **171 页 / 34,074 张专辑** ⇒ **无抽样、无截断**。

| 指标 | 实测值 | 含义 |
|---|---|---|
| 一级目录 | `vol02` **173,670** / `vol1` **1** | 曲库几乎全在一个卷 |
| path 含「**有声小说**」目录 | **5,244 首**（3.0%） | ⭐ 真·有声内容规模 |
| path 含「有声」 | 5,300 首 | 比「有声小说」多 56 ⇒ 其余是音乐误报 |
| 时长 ≥ 480 s（8 分钟） | **9,029 首**（5.2%） | ⭐ 时长候选池 |
| 标题可解析集号（v1 规则） | 390 首 | v1 规则几乎不适用 ⇒ §4.2 已重写 |
| `trackNo` 有值 | 131,366 首（75.7%） | ⇒ `trackNo` 对**多数**曲目有值 ⇒ 区分力低 |
| 专辑名含「小说 / 广播剧 / 有声 / 听书」 | 12 / 17 / 7 / 7 张，**几乎全是音乐** | ⭐ 名字信号**确认不可用** |

⚠️ **误伤分析（关键）**：长音频 9,029 首里**只有 5,244 首**是真有声
⇒ 另有 **3,785 首**长音频是 DJ 合辑 / 直播 / 节目录音
⇒ **单靠时长会误伤 42%** ⇒ 必须靠**标题形态一致**（§3.1）联合判定。

⚠️ **DJ 合辑与有声的区分**（实测）：
- DJ 合辑：每集标题**各不相同**且无统一形态 ⇒ 形态一致性**低** ⇒ 不计分 ✓；
- 有声：整本专辑标题**形态高度一致**（`21-` / `0010` / `第01季` / `第一季`）⇒ 命中 ✓。

### 2.7 ⚠️ 服务端**没有「目录浏览」能力**（T98-09 实测，20 个候选端点）

| 探测 | 结果 |
|---|---|
| `/folder/list`、`/directory/list`、`/dir/list`、`/browse`、`/path/list`、`/volume/list`、`/storage/list`、`/root/list`、`/tree/list`、`/file/list`、`/files`、`/album/folder-detail/list`、`/track/folder-detail/list` …（共 20 个） | **全部返回 HTTP 200 + 响应体 `null`**（⇒ 端点不存在） |
| `/search/folder`、`/search/directory`、`/search/dir`、`/search/path` | 全部 `null` |
| `/album/list?path=…` / `?folder=` / `?dir=` / `?directory=` / `?parentId=` / `?rootPath=` | **参数被忽略**（`total` 恒为 34,074） |

⇒ **「小说按目录分」这件事，客户端拿不到目录树**；
⇒ 目录信息**只能从 `audioSpec.path` 里读**，而 **`path` 每首歌只有一条**
（客户端模型 `Song.audioSpec.path`，服务端对象里也只有单个 `audioSpec`，
**没有** `paths[]` / `audioSpecs[]` 这类多路径字段 —— 已 dump 原始 JSON 确认）。

### 2.8 服务端搜索的**真实语义**（T98-07 / T98-10 / T98-12 实测）

| 结论 | 证据 |
|---|---|
| 命中字段 = **title / album / artists[].name / audioSpec.path** | 「瑾瑜」只命中标题；「有声鹿鸣」命中 path；「呱呱有声」命中艺人名 |
| 匹配 = **子串**（可跨词边界） | `?声的` → 19 命中（path 18 / title 19）；`?的无` → 8 命中 |
| **同时**做**分词 OR** | `?小说目` → 20 命中，但**没有一条**的 title/album/path 含「小说目」 |
| **`total` 上限 500**（服务端截断） | `?第`、`?集`、`?DJ打碟` 的 total 均为 500 |
| ⚠ **纯 ASCII 短 token 不进索引** | `?vol1` 搜不到 path 为 `/vol1/…` 的条目，而同一条目 `?茨厂街` **能**搜到 |
| ⚠ 中文目录名**可**被搜到 | `?歌手分类` → 332 命中；`?DJ打碟` → 500 命中；`?1000-0-3d135437` → 40 命中（path 含 40/40） |
| ⚠⚠ **同一查询的命中集**会**变**（**top-N 截断 + 分片差异**） | `?有声` 连查两次：`total` 都是 **17**，但第一次的 17 条**全是**音乐（「无声仿有声」…、path 含「有声」**0** 条），第二次的 17 条**path 含「有声」15 条**且**全在「有声小说」目录** |

⇒ **搜索可以做「定向查询」，不能做「全量枚举」**（500 截断 + 短 token 缺失）；
⇒ ⚠⚠ **「搜不到」永远不能证明「不存在」** —— 只有「搜得到」才是可靠阳性。
⇒ ⇒ **任何「某目录/某内容不存在」的结论，必须靠全量扫描，不能靠搜索。**
（⛔ 本轮曾因把 top-N 的阴性结果当穷尽证明，得出「有声小说目录不在索引里」的**错误结论**，
  被用户当场纠正；**该结论已作废**，见 §2.9。）

⇒ ⚠️ **不需要 NAS 侧任何操作**（文件早已入库）⇒ 交付**不分两段**。

### 2.10 ⭐ 「按目录分」形态的**跨根一致性**（实测）

除 `/vol02/1000-0-3d135437/有声小说/…` 外，还存在**第二个音乐根**，形态完全一致：

```
/vol1/1000/music/music/茨厂街/茨厂街_粤语谐剧_黄庆全_完整版.mp3
```

- 专辑《茨厂街 磁带原版转录》**只有 1 集**、**2706 秒**（45 分钟）、无艺人名；
- 目录层级 = **每部作品一个目录**、文件名带副标题与演员；
- ⚠ 这个根在索引里**几乎为空**（最新 1,000 条里只有这 1 条）⇒
  **不能把「有声小说」当唯一目录名**，判定**不得引用目录名**。

⇒ **可用且不依赖目录名的结构信号**：
**同一专辑的曲目是否聚集在同一个「作品目录」**
（= `path` 去掉文件名后，再去掉最后 1–2 段（分段目录 `Disc 01` / `0001-0115`）
得到的目录集合唯一）。
⚠ 普通音乐专辑整张放在一个文件夹时**也会命中** ⇒ 只给 **+1 分**，**不能单独成立**（§3.1）。

## 三、识别方案

### 3.1 信号表（每个信号都可量化、可单测）

> ⛔ **v2 信号表**：v1 的三个信号（`trackNo` 质量、标题几乎相同、同秒导入）
> 是按**错误画像**（拿 DJ 合辑当有声）定的，**已被真实有声数据推翻**：
> - `trackNo` 质量合格是**普通音乐专辑的常态**（普通专辑 trackNo 可靠）⇒ **必须去掉**，否则误伤；
> - 「标题几乎相同」是 **DJ 合辑**的特征，**有声内容相反**（每集标题不同）⇒ **必须去掉**；
> - 「同秒导入」区分力极低（普通专辑也常整批导入）⇒ **去掉**。
>
> v2 依据的**真实画像**（§2.9 实测）：单集 **9–32 分钟**、专辑 **6–2762 集**、
> 标题形态**专辑内高度一致**、同一作品聚集在**同一目录**。

| 信号 | 判定 | 分值 | 真实有声命中 |
|---|---|---|---|
| 单集**均长** | ≥ 8 分钟（480 s） | **+2** | ✅ 全部 5 个样本 |
| 单集**均长** | ≥ 20 分钟（1200 s） | **+1** | ✅ 三体 / 茨厂街 |
| **最长单集** | ≥ 30 分钟（1800 s） | **+1** | ✅ 三体 / 茨厂街 |
| 标题**形态一致** | ≥ 60% 的标题能按**同一规则**解析出集号（§4.2） | **+2** | ✅ 三体 / 牧神记 / 赶尸客栈 / 让青春继续 |
| 专辑**集数** | ≥ 8 集 | **+1** | ✅ 4/5（《让青春继续第二季》6 集漏） |
| **作品目录聚集** | `path` 去掉文件名与分段目录后，目录集合**唯一** | **+1** | ✅ 全部 5 个样本 |

- **≥ 4 分** ⇒ 判为「有声读物」；
- 界面**显示判定依据**（命中了哪几条）+ **判定分值**；
- ⚠ **普通音乐专辑得分 ≤ 2**（时长 0 分 + 集数 1 + 目录 1）⇒ **不误伤**；
  （「标题形态一致」对 `01- 标题` 形态的普通专辑会 +2 ⇒ 总分 4 ⚠ **恰好压线** ⇒
  ⇒ 该信号**必须**与「时长」**联动**：标题形态一致但均长 < 8 分钟 ⇒ **不计这 2 分**。）
- ⚠ **不依赖目录名**：目录名因人而异（用户的是「有声小说」，另一个库可能叫别的）
  ⇒ **任何判定都不得引用目录名**；
- ⚠ 识别**一定会有错** ⇒ 一键改判是**主路径的一部分**（§3.2）。

### 3.2 「宁可多标」（用户拍板）

阈值取**偏松**（≥ 4 分）⇒ 宁可多列几本 ⇒ 用户在页面上**一键改判**：

- 「不是有声」⇒ 记入**本地排除表**（优先于自动判定）；
- 「这是有声」⇒ 记入**本地包含表**（优先于自动判定）。

### 3.3 扫描策略（v2：**单阶段 · 本地聚合**，2026-11-16 实测后定稿）

#### 3.3.1 ⭐ 为什么**不需要**逐专辑拉详情

v1 设想「扫 `/album/list` 拿 `trackCount` → 对候选逐个拉 `/track/album-detail/list` 算指标」。
实测后**作废**：既然指标全部来自**曲目的时长 / 标题 / path / trackNo / createdAt**，
那就**直接扫曲库**，在**客户端本地按 `album.guid` 聚合** ⇒
**集数 / 均长 / 最长 / 形态一致性 / 作品目录聚集** 全部都能算出来
⇒ **一个专辑详情请求都不用发**。

| 方案 | 请求数（实测规模） | 评价 |
|---|---|---|
| v1：扫 34,074 张专辑 + 逐张拉详情 | 34,074 + ~4,700 = **~38,700 次** | ❌ 太贵 |
| **v2：只扫曲库**（`size=2000` ⇒ 173,671 / 2,000 = **87 页**） | **87 次** | ✅ |

- ⚠ `/track/list` 的 `size` 上限 **2000**、`page` 上限 **2000**（实测）
  ⇒ 87 页远在上限内，**一页 2,000 首**；
- ⚠ `sort=createdAt,desc` ⇒ **增量扫描**天然可行（§3.3.2）。

#### 3.3.2 增量与缓存键（**要让「重新扫描」真的便宜**）

| 缓存 | 键 | 值 | 失效条件 |
|---|---|---|---|
| 扫描水位 | — | `{ lastCreatedAt, scannedAt, scannedCount }` | — |
| 判定结果 | `albumGuid` | `{ score, reasons[], sortedIds[] }` | 该专辑**有新曲目** ⇒ 重算 |
| 用户改判 | `albumGuid` | `'audiobook' \| 'not-audiobook'` | 用户手动改时覆写（**永不失效**） |

- **增量扫描**：`sort=createdAt,desc` 从第 1 页往后拉，**遇到 `createdAt ≤ 水位` 就停**
  ⇒ 第二次「重新扫描」通常**只拉 1–2 页**；
- ⚠ **局限**：曲目被**删除**时，本地聚合的集数会偏 ⇒ 页面提供「**全量重扫**」入口；
- ⚠ **代价**：`/track/list` 一页 2,000 首的 JSON 约 2 MB ⇒ 87 页 ≈ 174 MB
  ⇒ **解析要流式、逐页处理、逐页释放**（不许把 17 万首全留在内存里）；
- ⇒ 落盘只留「命中有声的专辑」+ 水位 + 改判三张小表（**不落全库统计**）。

#### 3.3.3 界面要求

- 「重新扫描」按钮 + **进度**（已扫页 / 已扫首数 / 候选专辑数 / 命中数）；
- 可**中断**（中断点 = 已扫页数），下次**续跑**。

### 3.4 人工改判存哪

- 「用户改判」= **用户偏好** ⇒ 落 `prefs.json`（非敏感）；
- ⚠ `prefs.json` 有**白名单**（主进程）⇒ 新增键要同时改白名单与
  `src/state/appPrefsStore.ts`；
- 改判只存**专辑 id**（32 位 hex）+ 判定（是 / 不是）⇒ 体量小。

## 四、排序方案（**按集序，不乱**）

### 4.1 四层稳定排序键（**自上而下，先命中先用**）

1. **标题解析出的集号**（`resolveAlbumEpisodes` 的结果）
   ⚠ **只有该专辑「形态一致」（≥ 60%）时才用**；否则整层**作废**（所有条目视为无集号）；
2. **`trackNo`** —— **仅当质量合格**（有值率 ≥ 90% 且去重率 ≥ 90%）
   ⚠ 实测有声的 `trackNo` 大多为 `null`（《三体》《牧神记》《赶尸客栈》全 null）⇒
   这一层**多半用不上**，只当兜底；
3. **`createdAt`**（导入顺序）；
4. **原下标**（最终兜底 ⇒ 稳定、不丢、不重）。

⇒ 排序**必须稳定**（同键保原序）⇒ JS `Array.prototype.sort`（V8 稳定）满足；
⇒ 实现里**显式**用「原下标」做最后 tie-break，不依赖引擎实现细节。

### 4.2 集号解析规则（v2，`parseEpisode` + `resolveAlbumEpisodes`）

> ⛔ **v1 规则作废**：`17.0315` / `第X集` / `001_` / `1.` / `12、` / `【01】`
> 在**真实有声标题**里**一个都不出现**（实测形态见 §2.9）⇒ 必须重写。
> v2 已用**真实样本离线验证通过**（`release/verify/t98-15-scratch-episode-parse-v2.mjs`）。

#### 4.2.1 单条标题解析（**返回命中的规则名** + 段式数值）

| 规则名 | 形态 | 真实例子 | 解析结果 |
|---|---|---|---|
| `season-episode` | 第N季 + 集号 | `025- 第01季25`、`让青春继续第一季 10` | `[1, 25]` / `[1, 10]`（季, 集） |
| `episode-cn` | 第X集/回/章 | `第410集_瑾瑜的质问`、`第三回 相逢` | `[410]` / `[3]` |
| `dash-prefix` | 数字 + 连字符 | `21- 序章`、`23- 防御` | `[21]` / `[23]` |
| `dotted-prefix` | 点分数字前缀 | `17.0315丨坚持这三步…` | `[17, 315]` |
| `digits-only` | **纯数字标题** | `0010`（牧神记） | `[10]` |
| `bracket` | 括号数字 | `【01】开篇` | `[1]` |
| `trailing` | 末尾集号（**宽松**） | `让青春继续第一季 10`（已被上一条覆盖） | `[10]` |

- **年份保护**：4 位数且落在 1900–2100 ⇒ **不当集号**（`2024年…` ⇒ null）；
- 解析结果用**段式数值** ⇒ 比较时**逐段比数字**
  ⇒ `2.1 < 9.1 < 10.1 < 17.0315 < 17.0329`（字典序会把 `10.1` 排最前 ⇒ **错**）。

#### 4.2.2 ⭐ 专辑级**形态一致性**（防误判的关键）

单条标题的解析**不可靠**（纯数字标题既可能是集号，也可能是歌名「2003」）。
⇒ **两级解析**：

1. `parseEpisode(title)` → `{ rule, value } | null`；
2. `resolveAlbumEpisodes(titles)`：
   - 统计每条规则的命中数；
   - **只有当某一个规则命中 ≥ 60%** 时，才用该规则解析**全部**标题
     （同一专辑内形态应当一致）；命中数相同时**按规则优先级**取更具体的
     （`season-episode` > `episode-cn` > `dash-prefix` > `dotted-prefix` >
     `bracket` > `digits-only` > `trailing`）；
   - **否则整张专辑不按标题排序**（保持原序）⇒ **宁可不动也不乱**。

实测：

| 专辑 | 命中规则 | 命中率 | 集号序列 |
|---|---|---|---|
| 《三体》 | `dash-prefix` | 100% | 1,2,3,4,5,6,7,8,18,21,22,23,26 |
| 《赶尸客栈》 | `season-episode` | 100% | 1.1,1.2,1.17,1.20,1.21,1.25 |
| 《牧神记》 | `digits-only` | 100% | 1,2,3,4,5,6,7,8,10,11 |
| 《让青春继续第一季》 | `season-episode` | 100% | 1.1,1.3,…,1.31 |
| 混装专辑（3/6 是 `01-` 形态） | — | 50% | **不排序**（< 60% ⇒ 保持原序） |

### 4.3 ⚠️ 分页一致性（**「不乱」的最大坑**）

客户端只能排**已加载的页** ⇒ 若第 2 页的集号比第 1 页小 ⇒ 加载后会**跳序**。

⇒ **有声专辑一次性拉全量再排**
⇒ 顺序**一次定死**，不随「继续加载」变化。

⚠ **实测规模**：有声专辑可达 **2762 集**（《牧神记》）⇒
一次性拉全量 = 2762 / 200（默认每页）= **14 页**（或 2 页 @ `size=2000`）
⇒ 「一次性拉全量」**必须分页拉完再排**，且 ⚠ 服务端 `page`/`size` 上限都是 **2000**
⇒ 2762 集在 `size=2000` 下需要 **2 页** ⇒ **不许假设「一页拉完」**。

### 4.4 服务端 `sort=title,asc` 的定位（**本轮实测：不可用**）

- ⚠ 实测有声的标题形态（`21-` / `0010` / `第01季` / `第一季`）**全是变长数字前缀**
  ⇒ 字典序会把 `10-` 排到 `9-` **前面**（**错**）⇒ **服务端 `sort=title` 不能用**；
- ⇒ **主路径只能是客户端解析 + 段式数值比较**（§4.2）；
- ⇒ 服务端 `sort=title,asc` 只作**对照 / 调试参照**，**不入生产排序路径**。

## 七、验收点

1. **纯函数**（可单测）：
   - 集号解析覆盖**真实形态**：`21- 序章`→21、`0010`→10、`025- 第01季25`→[1,25]、
     `让青春继续第一季 10`→[1,10]、`第410集_…`→410、`17.0315丨…`→[17,315]；
   - **不误判**：年份（`2024年…`）、普通歌名（`思凡` / `Runaway Mama` / `Untitled`）
     ⇒ 解析为 null；
   - **形态一致性**：混装专辑（50% 命中）⇒ **不排序**（保持原序）；
   - 段式数值排序（`10.1` 排在 `9.1` 之后）、排序键优先级、同键稳定、**不丢不重**；
2. **识别**：
   - 普通音乐专辑得分 **≤ 2**（不误伤）；
   - 名字里带「小说 / 有声 / 广播剧」的**音乐**专辑**不得**被误判（实测这类误报极多）；
   - 「标题形态一致」信号**必须**与「时长」联动（否则 `01- 标题` 形态的普通专辑会压线）；
   - 命中依据**可解释**（列出命中了哪几条 + 判定分）；
3. **分页**：有声专辑「一次性拉全量后」的顺序 == 「逐页加载后」的顺序（**不跳序**）；
4. **E2E**：mock 造一个 12 集有声专辑 ⇒ 详情页顺序 = 集号顺序 + 显示集号；
5. **真机验收**（真实 NAS，本机 + 该账号）：
   - 《三体》89 集 ⇒ 按 `01-`/`21-`/`26-` 的集号顺序排列；
   - 《牧神记》2762 集 ⇒ 按 `0001…` 顺序（⚠ 一次性拉全量 ⇒ **分页不许截断**）；
   - 《赶尸客栈》跨 3 个 Disc ⇒ 跨目录合并后仍按集号排；
   - 《让青春继续第一季》32 集 ⇒ 按 [季, 集] 排；
   - **误伤核对**：长音频非有声的条目（DJ 合辑等）**不得**出现在页面上
     （**以你那台机那批文件为准**）。
