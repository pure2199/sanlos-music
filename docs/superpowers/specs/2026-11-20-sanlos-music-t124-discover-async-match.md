# T124：发现页「先出榜单、命中异步补」＋「二次进入不重打 NAS」

> 承接：台账遗留「发现页『先出榜单、命中异步补』」「二次进入『发现』会重打 NAS（匹配结果不缓存）」

---

## 一、起因

台账 T96/T97/T98/T100 的遗留里，连着挂了同一条：

> ⚠ T96 / T97 / T98 / T100 的遗留照旧：发现页「**先出榜单、命中异步补**」、二次进入重打 NAS。

两个问题，**同一个根因**：匹配（= 逐个歌手定向查 NAS）**挡在榜单前面**。

| 现状 | 后果 |
|---|---|
| `loadCharts()` **先 await 匹配**才 `set({ boards })` | 榜单明明已经拿到了（榜源不慢），却要等 **30–40 秒**的曲库匹配才出现在屏幕上 |
| 匹配结果**不缓存** | 二次进入「发现」**再打一遍 NAS** ⇒ 又 30–40 秒 |

---

## 二、事实依据（**代码事实**）

| 事实 | 出处 |
|---|---|
| 匹配 = **逐个歌手定向查**：`/search/artist` → `/track/artist-detail/list`（**不拉全量**） | `src/api/discover.ts` 的 `matchChartsToLibrary()` |
| 并发上限 `DISCOVER_QUERY_CONCURRENCY`，用 `mapWithLimit` | 同上 |
| 榜单条目最终判定靠 `shared/chartMatch.ts` 的 `matchChartEntry()`（**纯计算**） | 同上 |
| `loadCharts()` 把「拉榜」与「匹配」**串成 await** ⇒ 榜单被匹配挡住 | `src/state/discoverStore.ts`（改前） |
| 中继链路上匹配要 **30–40 秒** | 台账 T96 实测记录 |

---

## 三、方案

| 落点 | 做法 |
|---|---|
| `shared/chartTypes.ts` | `MatchedChartEntry` ＋**可选** `pending?: boolean`（缺省 = 已匹配完 ⇒ **既有行为一字未变**） |
| `src/api/discover.ts` | ＋`pendingChartBoards(boards)`：造一份「**还没匹配**」的榜单（每条 `pending: true`） |
| `src/state/discoverStore.ts` | ① 榜单一到 ⇒ **立刻** `set({ charts, boards: pendingBoards, chartsLoading: false, matching: true })` ⇒ **榜单先出**；② 匹配在后台跑 ⇒ 完成后**补上**命中结果；③ **会话内缓存**（模块级 `Map`，key = 榜单 id ＋ 条目数 ＋ 首条标题）⇒ 二次进入**一个 NAS 请求都不发** |
| `src/pages/DiscoverPage.tsx` | pending 条目显示「**匹配中…**」（**不是**「不在曲库」）；状态行 / 命中率文案在匹配期间显示「正在匹配你的曲库…」 |

⚠ **为什么缓存是「会话内」而不是带 TTL 的长期缓存**：曲库内容会变（用户新加了歌）
⇒ 缓存久了会给出**过时**的命中状态；而「二次进入不重打」这个诉求**只需要覆盖同一次运行**
⇒ 进程退出即失效，**最安全**。

⚠ **为什么条目要能区分「pending」与「不在曲库」**：「不在曲库」是**结论**，
「还没查」**不是结论** ⇒ 没有 `pending` 就会在匹配期间**说假话**。

---

## 四、钉子（**5 条**）

| # | 钉子 | 钉住什么 |
|---|---|---|
| ① | 榜单一到 ⇒ `boards` 已有条目且标 `pending`；`matching === true` | 「榜单先出」 |
| ② | 匹配完成 ⇒ `pending` 清空、命中数 / 总数正确 | 「命中异步补」 |
| ③ | **同样榜单第二次进来** ⇒ `searchArtists` **一次都没被调用**（缓存命中） | 「二次进入不重打 NAS」 |
| ④ | 曲库查不动（`unavailable`）⇒ 榜单**仍在** ＋ `matchError` ⇒ 条目**全部 pending** | 「不假装有结论」 |
| ⑤ | 界面：pending 条目显示「匹配中…」，**一个「不在曲库」都不许出现**；状态行说「正在匹配」 | 文案不撒谎 |
