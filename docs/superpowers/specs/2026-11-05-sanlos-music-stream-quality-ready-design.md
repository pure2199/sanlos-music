# T55 设计规格：标准音质的就绪判定（让服务端转码真能用起来）

- 日期：2026-11-05
- 承接：T54（音质偏好：原始音质 / 标准音质）
- 状态：待实现

---

## 1. 起因

T54 交付后的真机结论是：**服务端转码不可用 → 标准音质必然回退原始音质**。

用户随后反馈：**「用官方 APP，中继都可以选音质」** —— 与该结论冲突。
于是开了 T55-0 探针组（**未改任何产品代码**）把结论全部重新实测。

**结论：T54 选对了协议族，选错了就绪判定。服务端转码一直是好的。**

## 2. 实测事实（2026-11-05，真实 NAS / 真实账号，凭证只在探针进程内存里）

### 2.1 四路对比（同一套流程：登录 → 取 FLAC → 转码 → 取产物）

| 链路 | prepare | status | 产物（Range） | 产物（全量 7 005 165 B） |
| --- | --- | --- | --- | --- |
| 中继 `<FN-ID>.fnos.net` | ✅ | ready / 100% | 206 ✅ | 200，**12 930 ms** |
| **用户反代 `user-proxy.invalid`** | ✅ | 0%→98%→ready | 206 ✅ | 200，**1 154 ms** ✅ |
| NAS 内网 `192.168.100.xxx:5666` | — | — | 本机不在该内网（超时） | — |
| NAS 公网 `<公网 IP>:5666` | — | — | 超时 | — |

⇒ **用户的自建反代就能用，且比中继快 11 倍** → **不需要改反代、不需要走中继**。

### 2.2 「官方 HiRes」根路径端点在本机**不存在**

官方网页版 bundle 里那套 `GET {origin}/api/stream/hires?fileId=&quality=`（根路径，
播放走 HLS）：

- 中继：**404 + SPA 兜底页**（`auto` / `high` / `standard` / `lossless` / `hires` / `medium` / `320k` 七种 quality 全 404）；
- 反代：**404 + SPA 兜底页**（同样）。

⇒ 本机 fnOS **1.0.10 / mediasrv 0.8.43 没有实现这个端点**（官方网页版带的那套 HiRes 代码在此机上是空转）。
⇒ **不需要根路径通道、不需要自研 fMP4 HLS 客户端（MSE）**。

### 2.3 抽样 14 首：14/14 成功

| 曲目 | 格式 | 就绪 |
| --- | --- | --- |
| 占位曲目一 | flac 96000/24 | 2 570 ms |
| 占位曲目七 | flac 44100/16 | 2 646 ms |
| 占位曲目六 / 占位曲目八 / 占位曲目九 / 占位曲目十 / 占位曲目十一 / 占位曲目十二 / 曲目 1·2·7·8·9·15 | mp3 44100/32 | 130 ~ 812 ms |

**汇总**：14 成功 / 0 失败 / 0 超时；**平均就绪 988 ms，最慢 2 646 ms**。
产物 = **MP3 320k**（7 005 165 B / 175 s）⇒ 对比原始 FLAC 62 228 801 B，**省 88.8 % 流量**。

### 2.4 两首**确定性**失败（客户端救不了，只能诚实回退）

| 曲目 | 现象 |
| --- | --- |
| 占位曲目二 (变体一) | 转码到 **93 %** 才 `failed`，`errno=68157441 / errmsg='transcoding error'`（6/6） |

## 3. 根因：T54 的「就绪判定」错了

三处独立证据：

1. **重跑 T54 当时的探针**（同一个脚本、同一条链路）：全部 **88 ~ 203 ms** 返回，**零挂起**；
2. 文件端点在**产物未就绪**时回的是 `{"code":100002,"msg":"invalid arguments"}`（203 ms 到达）
   —— 是「**还没好**」，不是「没响应头」；
3. **Range 形态矩阵**全部 206 正常：`bytes=0-1` / `0-0` / `0-1023` / `100-200` / `-1024`（尾部）；
   不带 Range → 200 全量 7 005 165 B / 1 271 ms。

⇒ T54 的判定链是：`percent >= 100` → **单次**预检 → 预检不过 → **立刻**判 `unavailable` → 回退原始音质。

⇒ **`percent >= 100` 与「产物真能读」之间存在窗口期**（老实测记录过「status 第一次就报 ready，
随后又变回 `transcoding / percent=N`」）。窗口期一旦命中，单次预检就误判成「服务端转码不可用」。

⇒ **T54 的「服务端转码不可用」结论作废**（`docs/calibration.md` 同步更正）。

## 4. 方案

### 4.1 判定流程（新）

```
prepare
  ↓
loop（截止到 deadline）：
  ├─ status → word==='failed'          → 抛 transcode-failed（带服务端 errno/errmsg）
  ├─ percent >= 100（**只信 percent** —— status 词**不**作为触发条件，沿用 T54 的既有纪律）
  │    ├─ 产物预检（Range bytes=0-1）
  │    ├─ 预检通过 → **返回可播产物地址**
  │    └─ 预检失败 → **不判死**：等 probeRetryInterval 再来一轮
  │        （percent 可能掉回去；产物通常在 percent=100 后数百毫秒内可读）
  ├─ 进度回调用 percent 推进
  └─ 超时 → 见过 percent>=100 ? 抛 unavailable : 抛 timeout（并删掉服务端任务）
```

要点：

- **percent ≥ 100 只代表「可以试预检」**，不再代表「完成」；
- **预检失败 ≠ 失败**：这是本轮唯一的逻辑修正；
- **轮询间隔默认 500 ms**（实测平均就绪 988 ms ⇒ 少等一轮就少等 0.5 s）；
- 产物地址仍然只在**预检通过之后**才交给播放器（**绝不**把没验证过的地址塞给 `<audio>`）。

### 4.2 失败分类（五类，**不混淆**，各自有独立文案）

| reason | 触发条件 | 界面文案（灰字） |
| --- | --- | --- |
| `prepare-rejected` | 服务端拒绝 prepare | 标准音质不可用：服务端拒绝了转码请求，已改用原始音质播放 |
| `transcode-failed` | 服务端报 `failed`（带 errno/errmsg） | 标准音质不可用：服务端转码失败（<errmsg>），已改用原始音质播放 |
| `unavailable` | 服务端说完成，但产物一直读不到 | 标准音质不可用：服务端转码产物无法读取，已改用原始音质播放 |
| `timeout` | 轮询超时（还没完成） | 标准音质不可用：服务端转码超时，已改用原始音质播放 |
| `network` | 网络不可达 | 标准音质不可用：无法连接音乐服务，已改用原始音质播放 |

⚠️ 五类**全部**是「回退原始音质 + 灰字」，**没有一类**是红色 `role="alert"` ——
标准音质失败 **≠** 播放失败（T54 的失败语义不变）。

### 4.3 明确不做的事（边界）

- **不换协议**、**不改代理**、**不新增根路径通道**、**不写 HLS 客户端**；
- **不改设置页结构**、**不改偏好键**（`streamQuality` 仍是 `original` / `standard` 两档）；
- **不重试服务端明确 `failed` 的任务**：实测那两首 6/6 确定性失败，重试只是白等；
- **不引新 npm 依赖**；
- 不动 `electron/proxy.ts` 的二进制白名单（T54 已把 `download/track/transcode/file` 加进去，实测 206 + Range 正常）。

## 6. 验收点

1. **新增回归用例先红后绿**：`percent=100` 但产物前两次预检返回 `{"code":100002}`、第三次返回 206
   → 客户端**不许**判失败，最终**成功返回可播地址**；
2. 服务端 `failed` → 仍抛 `transcode-failed` 且**带上服务端原因**（既有断言不削弱）；
3. 产物一直读不到 → `unavailable`（**不是** `timeout`）；轮询超时 → `timeout`（既有断言不削弱）；
4. `tsc --noEmit` exit 0；`vitest run` 全绿（**≥ 1852 passed**）；`playwright test` **24 passed**；
   `npm run build` exit 0；
5. **真机**（真实 NAS + 真实 userData，偏好临时改 `standard`）：
   - `<audio>.src` 应为 `fnm://srv/download/track/transcode/file?downloadId=…`
     （**不再是** `fnm://srv/track/stream?guid=…`）；
   - 播放条先显示「正在准备标准音质…」，随后正常播放；
   - 实际取到的字节明显小于原始 FLAC（省流量）；
   - 跑完把 `prefs.json` **逐字节还原**。

## 7. 已知限制（如实标注）

- ⚠️ **服务端引擎对部分曲目确定性失败**（《占位曲目二》《占位曲目三》6/6，`errno=68157441`）
  → 客户端只能回退原始音质 + 灰字说明，**NAS 侧的问题客户端改不了**；
- ⚠️ 那两首为什么在 **79 %~93 %** 处崩**尚未查清**（引擎 / 编码器 / 时长 / 文件特征，未逐项排除）；
- ⚠️ 「标准音质」= **MP3 320k**（官方旧下载协议口径），服务端**没有** 192k 那一档；
- ⚠️ 标准音质**首次起播要等 1~3 秒**（服务端转码时间），界面显示「正在准备标准音质…」；
- ⚠️ 转码任务会在 NAS 上留一个临时产物 → 客户端在切歌 / 超时 / 失败时删掉它；
- ⚠️ 本机 NAS 的**内网地址是 `192.168.100.xxx`**（此前记录的 `192.168.1.2` 有误），本机不在该内网。
