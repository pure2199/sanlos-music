## 1. 起因与用户拍板

### 1.1 起因

用户问：「知道洛雪音乐用的是什么歌词 API 吗？能接入到我们的软件吗？」

⇒ 调研洛雪（`lyswhut/lx-music-desktop`，Apache-2.0）的歌词实现后确认：
**洛雪没有「一个歌词 API」，而是逐平台直连官方 Web 接口**，
且在「真逐字 + 翻译 + 罗马音」三件事上**比我们做得好**。

### 1.2 用户拍板（2026-11-13，问卷三题全选）

| 决策点 | 结论 |
| --- | --- |
| 接法 | **补 QQ 逐字**（`musicu.fcg` + QRC 解密） |
| 范围 | **再补酷狗 / 酷我 / 咪咕**，对齐洛雪 5 源 |
| 罗马音 | **一起做成原文 / 翻译 / 罗马音三行**（不是只取回不展示） |

## 2. 洛雪的歌词实现（源码事实，2026-11-13 核对 `master`）

每个平台一个模块：`src/renderer/utils/musicSdk/<平台>/lyric.js`。

| 平台 | 搜索 | 歌词端点 | 加密 | 能拿到 |
| --- | --- | --- | --- | --- |
| **网易云** `wy` | `music.163.com/api/search/get/web` | `POST interface3.music.163.com/eapi/song/lyric/v1` | **EAPI** = AES 加密的 form（`wy/utils/crypto.js`，**2.4 KB**） | `lrc` / `tlyric` / `romalrc` / **`yrc`** / `ytlrc` / `yromalrc` |
| **QQ** `tx` | `c.y.qq.com/soso/fcgi-bin/client_search_cp` | `POST u.y.qq.com/cgi-bin/musicu.fcg`（`GetPlayLyricInfo`，`crypt:1, qrc:1, roma:1, trans:1`） | **QRC** = **3DES-EDE3（ECB）+ zlib inflate**，固定密钥 `!@#)(*$%123ZXC!@!@#)(NHL` | **逐字 qrc** + 翻译 + **罗马音** |
| **酷狗** `kg` | `songsearch.kugou.com/song_search_v2`（要 `FileHash` + `Duration`） | `lyrics.kugou.com/search` → `lyrics.kugou.com/download?fmt=krc` | **KRC** = XOR + zlib（`common/utils/lyricUtils/kg.js`，2.2 KB） | 原文逐字（**无翻译、无罗马音**） |
| **酷我** `kw` | 洛雪 `kw/musicSearch.js` | `http://mlyric.kuwo.cn/mobi.s?f=web&type=lyric&lrcx=1&rid=<songmid>&encode=utf8` | `decodeLyric`（XOR + base64，key `yeelion`） | 原文 + 翻译（`lrcx=1` 带逐字 `<起,时>` 标签） |
| **咪咕** `mg` | 洛雪 `mg/musicSearch.js` | `getMusicInfo(songmid)` → `mrcUrl` / `lrcUrl` / `trcUrl` → GET | mrc 需 `decrypt`（`mg/utils/mrc`） | 原文（mrc 逐字）+ 翻译（trc 明文） |

### 2.1 两个**容易误解**的点

1. **洛雪的「自定义源脚本」（`api-source.js`）是给在线音频链接用的，不提供歌词** ⇒ 不可用于本任务。
2. **洛雪的「开放 API」**（v2.7.0+，`http://127.0.0.1:23332/lyric?id=…`，据社区文档）只暴露
   「洛雪自己正在播放的那首歌」⇒ 依赖用户装洛雪、对我们的多源曲库无价值 ⇒ **不采用**。

### 2.2 洛雪自己把 yrc/qrc 解析成两份

标准 LRC + 它自有的 `lxlyric`（行内**相对**毫秒逐字）。
⇒ **我们不抄它的格式**：我们已有「增强 LRC」（`<mm:ss.xx>` 绝对毫秒逐字标签）管线
（`yrcToEnhancedLrc` / `parseWordSegments`）⇒ 各平台的逐字格式**统一转成增强 LRC**即可，
**渲染层解析器一字不改**。

## 3. 我们现状与差距

### 3.1 现状（`electron/lyricProvider.ts`，主进程）

- 源链：`ONLINE_SOURCE_ORDER = ['netease', 'lrclib', 'qq', 'custom']`；设置面板可单选。
- 三级链路：**内嵌（T83）→ NAS 自带 → 外部源**；优先级默认「线上优先」。
- 已有能力：
  - `netease`：`music.163.com/api/song/lyric?…&yv=-1` ⇒ **已有 yrc 真逐字** + 行级 `tlyric`；
  - `qq`：`fcg_query_lyric_new.fcg` ⇒ **明文行级 LRC + 翻译**（**无逐字**）；
  - `lrclib`：第三方开源（实测 366–1300 ms、**偶发 503**）；
  - `custom`：用户自配 URL 模板。
- 实测：网易云歌词 31–41 ms / 10-10 全绿；QQ 歌词 70 ms 但**搜索 814 ms**。

### 3.2 差距

| 能力 | 我们 | 洛雪 | 差距 |
| --- | --- | --- | --- |
| QQ 逐字 | ❌ | ✅ | **最大缺口**（用户点名要） |
| 网易云逐字**翻译** | ❌（只有行级 tlyric） | ✅ `ytlrc` | 次要 |
| 罗马音 | ❌ | ✅（网易云 / QQ） | 用户点名要做 |
| 平台覆盖 | 2 个（网易云 / QQ）+ lrclib + custom | 5 个 | 冷门歌覆盖 |

### 3.3 ⚠️ 罗马音**不是所有源都有**（必须如实呈现）

| 源 | 罗马音 |
| --- | --- |
| 网易云 | ✅ 行级（`rv=-1`）；逐字（`yromalrc`）**需 EAPI** |
| QQ | ✅ **逐字**（`roma:1`，qrc 加密） |
| 酷狗 / 酷我 / 咪咕 | ❌ **没有** |

⇒ UI 的第三行**按源有无**决定显示，不存在时**不显示空行**。

## 4. 设计

### 4.1 模型扩展：原文 / 翻译 / 罗马音三行

现状的「第一条作原文、其余作翻译」是**位置约定** ⇒ 加第三行会歧义 ⇒ **必须引入角色标记**。

| 位置 | 改动 | 性质 |
| --- | --- | --- |
| `shared/lyricProvider.ts` | `ExternalLyricResult` 的 `ok` 变体加 `romanization: string`；`LyricSource` 加 `'kg' \| 'kw' \| 'mg'` | 改 |
| `src/api/types.ts` | `LyricEntry` 加 `role?: 'original' \| 'translation' \| 'romanization'`（**可选 ⇒ 缺省按旧位置约定 ⇒ 既有数据行为不变**） | 改 |
| `src/player/lyricSource.ts` | `toExternalEntries` 产出**三条**（原文 / 翻译 / 罗马音），各自带 `role` | 改 |
| `src/ui/lyrics/parse.ts` | `parseLyricEntries` 的合并规则改为**按 `role`**（无 `role` 的按旧位置约定 ⇒ 旧数据不受影响）；`LyricLine` 加 `romanization: string` | 改 |
| `src/ui/lyrics/LyricView.tsx` | 渲染第三行（罗马音）：无值时**不渲染**，不占位 | 改 |

⚠️ **向后兼容纪律**：`role` 缺失 ⇒ 按「第 1 条原文、其余翻译」处理
⇒ **既有测试一条不改也必须绿**。

### 4.2 适配器分层（沿用 T74a 的思路）

| 单元 | 职责 | 依赖 |
| --- | --- | --- |
| `electron/lyricWordFormat.ts`（**已存在？否，T74a 回滚时删了**） | `msToLrcTag()` | 无 |
| `electron/lyricCodecs/qrc.ts`（新增） | QRC 解密：**纯 JS 3DES（非标准 S 盒）** + `node:zlib` inflate | `node:zlib` |
| `electron/lyricCodecs/krc.ts`（新增） | KRC 解密：base64 → 跳 `krc1` → XOR → `node:zlib` inflate | `node:zlib` |
| `electron/lyricCodecs/kuwo.ts`（新增） | 酷我 `decodeLyric`：XOR + base64 | 无 |
| `electron/lyricCodecs/migu.ts`（新增） | 咪咕 `decrypt` | 无 |
| `electron/lyricProvider.ts`（改） | 每平台一个 `fetchXxx()`（内部完成「平台搜索 → 拿 id/hash → 取歌词」） | `fetchImpl`（注入） |

⚠️ **QQ 的 3DES 不能用 `node:crypto`**：QRC 用的是**非标准 DES 变体**
（`S2[23]=15`、`S4[53]=10`，标准值是 14 / 1）⇒ OpenSSL 的标准 DES **解不出来**
⇒ **必须移植洛雪那份纯 JS 3DES**（`tx/qrcDecode.js`，约 250 行，Apache-2.0，**须注明出处**）。

⚠️ **各平台的「搜索 → 取歌词」全部在主进程内部完成**：
渲染层**只传 4 个字段**（歌名 / 歌手 / 专辑 / 时长）——这是既有的**安全边界**
（主进程不接受渲染层传来的任何 id / URL）⇒ **不许**为了省事把 songid 之类塞进 IPC 契约。

### 4.3 出网通道

沿用 `electron/http.ts` 的 Chromium 分区 session：
- 自定义 header（酷狗要 `KG-RC` / `KG-THash` / `User-Agent`；酷我要 `Referer`）⇒ `session.fetch` 支持 `init.headers` ✔；
- ⚠️ 酷狗 / 酷我用的是 **http 明文**接口 ⇒ Chromium 默认允许（主进程发请求，不受页面 CSP / 混合内容约束），
  但**必须实测**（见 T90-②）；
- 仍**绝不附带 NAS 凭证**（干净分区、不附 token / Cookie）✔。

### 4.4 逐字 → 增强 LRC 的统一口径

各平台逐字格式的差异（**转换器必须区别对待**）：

| | 网易云 yrc | QQ qrc | 酷狗 KRC | 酷我 lrcx | 咪咕 mrc |
| --- | --- | --- | --- | --- | --- |
| 词元组 | `(起,时,0)` | `(起,时)` | `<起,时,0>` | `<起,时>` | `(起,时)` |
| 词时间基准 | **绝对毫秒** | **绝对毫秒**（⚠️ 2026-11-14 实测更正，原写「相对行开始」） | **相对行开始** | 相对行开始 | **绝对毫秒**（⚠️ 2026-11-14 实测更正，原写「相对行开始」；详见 §15.5） |
| 行头 | `[起,时]` | `[起,时]` | `[起,时]` | `[mm:ss.xx]` | `[起,时]` |

⇒ 统一输出：`[行标签]<词1标签>词1<词2标签>词2…`（**绝对**毫秒的 `<mm:ss.xx>`）
⇒ 交给**现有** `parseWordSegments` ⇒ **渲染层解析器一字不改**。

⚠️ **QQ qrc 的词时间基准更正**（T90-④ 实测）：原表写「相对行开始」，**实测是绝对毫秒**
（样本第 40 行：行首 93766、首词 93766、末词 95181，**全部 ≥ 行首**）。
⇒ 实现里保留「相对」的**兜底判定**（**词时间 < 行首 ⇒ 相对**），
   但**实测样本一律按绝对处理**（见 §10.4）。


### 4.5 错误处理（沿用既有纪律：如实上报，不静默）

| 情况 | 结果 |
| --- | --- |
| 平台搜索无结果 / 无候选 | `not-found` |
| 端点非 200 / 响应形状不对 | `error`（带消息） |
| 解密失败 / 头不是 `krc1` | `error`（**如实报，不静默吞掉**） |
| 解密后过滤完没有有效歌词行 | `not-found` |
| 任一环节超时 | 源级预算 ⇒ `error`，源链继续试下一个源 |

## 6. 风险与未知

1. **接口会变**（非官方、无 SLA）：5 个源都是非官方公开接口 ⇒ 源链的**兜底设计**（多源依次试）比单个源更重要。
2. **http 明文**：酷狗 / 酷我目前是 http ⇒ 若哪天上 https，适配器要改；先实测再定。
3. **许可与出处**：移植洛雪的纯 JS 3DES / 解密实现 ⇒ **必须注明出处 + Apache-2.0 声明**；
   本仓库自身协议需与用户确认后再定发布形式。
4. **QQ 三跳**：搜索（带 Referer）→ `songmid` → `songID`（`getMusicInfo`）→ `musicu.fcg`
   ⇒ **搜索那跳现在实测 814 ms** ⇒ QQ 逐字的**总延迟**可能到 1 s 级
   ⇒ 源级超时预算要单独放宽，且**UI 要能接受 1 s 才出词**（先出 NAS 的、线上后到覆盖）。
5. **逐字 ≠ 好看**：T81 已经确立「没有真逐字就整行显示」⇒ 新源若给不出真逐字，
   **不要为了显示而伪造**。
6. **罗马音的可用性**：只有网易云 / QQ 有 ⇒ 第三行在别的源上恒为空（**如实不显示**）。

## 7. 明确不做

- 不做洛雪的「开放 API」接入（依赖用户装洛雪、只覆盖单曲）。
- 不做洛雪的「自定义源脚本」机制（那是音频 URL 的，与歌词无关）。
- 不做多源**并发**择优（保持「依次试」的既有源链）。
- 不改 `src/ui/lyrics/parse.ts` 的**时间标签 / 伪逐字**逻辑（只加 `role` 合并规则）。
- 不改 NAS 侧歌词（服务端不动）。
- 不动已发布的 v0.2.9 资产（本次不发版，改完再走正常发版流程）。

## 8. 探针实测后的修正（T90-②，2026-11-14）

T90-② 的接口探针（`tools/fn-lyric-source-probe*.mjs`，**只验活 / 看字段形状 / 记延迟，不解密内容**）
推翻了本规格里的两处假设，并发现了两个必须改计划的事实。

### 8.1 两处修正

| # | 立项时的判断 | 实测 | 处置 |
| --- | --- | --- | --- |
| 1 | 酷我 `mobi.s` 返回 base64 密文 | 响应是 **`TP=content\r\nlrcx=1\r\n\r\n` + 二进制密文**（4655 B）；洛雪的 `decodeLyric(raw, …)` 收的正是 **Buffer** | **形状一致** ⇒ T90-⑥ 可直接照抄洛雪的 `kw/util` |
| 2 | 咪咕 `resourceinfo` 传 `copyrightId` | **必须传 `songId`**：传 copyrightId ⇒ `resource: []`；传 songId ⇒ 1 条 / 6631 B | **洛雪这里有传参错位** ⇒ T90-⑦ 用 `songId` |

### 8.2 两个必须改计划的事实

1. ⚠️ **我们线上在用的 QQ 旧端点已彻底下线**
   （`c.y.qq.com/lyric/fcg_query_lyric_new.fcg`，2 个 songmid × 3 个 URL 变体 = **6/6 全 404**）
   ⇒ **QQ 源目前是坏的** ⇒ **T90-④ 从「锦上添花」升级为「修复已坏的功能」**，优先级提到最前。
2. **网易云仍活着但覆盖差**：12 首样本里 5 首有 `lrc`、**2 首有 `yrc`**、**2 首有 `romalrc`**
   ⇒ **T90-⑧ 的罗马音可行**（旧接口加 `rv=-1` 即可，**不必上 EAPI**）；
   ⚠️ **周杰伦原唱基本没词**（与 T74a 结论一致）⇒ 网易云源的定位是「有就很好、没有就换源」。

### 8.3 五源实测速查（2026-11-14）

| 源 | 状态 | 延迟 | 逐字 | 罗马音 | 翻译 | 备注 |
| --- | --- | --- | --- | --- | --- | --- |
| 网易云 | ✅ 200 | 30–52ms | ✅ `yrc`（**覆盖约 2/12**） | ✅ `romalrc`（**2/12**） | 行级 `tlyric` | 覆盖差；周杰伦原唱无词 |
| QQ（旧） | ❌ **404** | — | — | — | — | **生产在用，已坏** |
| QQ（逐字） | ✅ 200 | 61ms（搜索 1507ms） | ✅ `qrc`（hex 6048 字符） | ✅ `roma`（样本为 0） | ✅ `trans`（样本为 0） | 需 QRC 解密 |

## 9. T90-③ 的实现约定（2026-11-14）

T90-③ 只做「**三行模型 + 渲染**」，**不加新源枚举**（`LyricSource` 不动）——
新源（`kg` / `kw` / `mg`）各自在 T90-⑤ / ⑥ / ⑦ 里实现时再加，
否则设置面板会出现「**有选项但用不了**」的源。

### 9.1 一处规格修正：`romanization` 改为**可选字段**

§4.1 写的是 `ExternalLyricResult` 的 ok 变体加 `romanization: string`（**必填**）。
但既有代码与既有测试**手写**的是 `{ status: 'ok', source, original, translation }`
⇒ 改成**必填**会让既有调用点与既有测试**全部编译不过**
⇒ 违反本仓库「**既有测试一条不许改**」的硬约束。

⇒ **改为 `romanization?: string`**（可选）：

- 缺省 ⇒ **没有罗马音**（多数源本来就没有 —— 洛雪也只对部分源开罗马音）；
- 既有调用点 / 既有测试 **零改动**；
- 主进程将来给出罗马音时**自然带上**这个键即可。

同理，`LyricLine.romanization` 也是**可选**（既有代码与测试里**手写**的 `LyricLine`
不带这个键 ⇒ 必填会编译不过）。

### 9.2 `role` 归类规则（定死）

| 条目的 `role` | 归类 |
| --- | --- |
| `'original'` | 原文（**取第一条**） |
| `'translation'` | 翻译 |
| `'romanization'` | 罗马音 |
| **无 `role`** | **旧的位置约定**：第 1 条非空条目作原文，其余作翻译 |

- 原文候选优先级：`role:'original'` → 无 role → `role:'translation'`（都没有 ⇒ 返回空数组）。
- 「多余的」条目（多出来的 `role:'original'`；或原文已由显式 role 选出、剩下的无 role 条目）
  ⇒ **一律当翻译候选**（**内容不丢**）。
- **副本过滤沿用旧规则**：**内容（忽略空白）与原文相同、且 offset 相同** ⇒ 丢弃。
  罗马音同样适用 ⇒ **罗马音与原文实质相同就不显示**（不显示两遍一样的行）。

### 9.3 渲染规则

- 副行顺序：**原文 → 翻译 → 罗马音**。
- **无值不渲染**（不占位、不渲染空的第三行）。
- 全量模式（`mode="all"`）：罗马音与翻译**同规则** —— 只有**当前行**显示
  （没有活跃行时回落到第一行）⇒ 「**槽位等高**」的前提不破。
- 罗马音**不参与推进**（没有词级时间戳）—— 与翻译同理。

### 9.4 本任务的边界

- **不动** `LyricSource`、**不动**主进程取词逻辑
  （罗马音的真实来源是 T90-⑧ 的网易云 `rv=-1`）。
- **不动**既有测试的**任何一条断言**；新增测试全部放在**新文件**里。

## 10. T90-④ 的实现约定（2026-11-14）

### 10.1 ⚠️ 更正 T90-② 的结论：**QQ 行级源一直是好的**

§8.2 记的是「我们线上在用的 QQ 旧端点已彻底下线（2 个 songmid × 3 个 URL 变体 =
**6/6 全 404**）⇒ **QQ 源目前是坏的**」—— **这条结论不成立**。

**根因**：T90-② 的探针当时测的是**少了 `fcgi-bin/` 的 URL 变体**，
而生产在用的是**另一个变体**。

| 端点 | T90-② 探针 | T90-④ 复测（2026-11-14，本机真打） |
| --- | --- | --- |
| `c.y.qq.com/lyric/fcg_query_lyric_new.fcg`（少 `fcgi-bin/`） | **404** | **404**（一致） |
| `c.y.qq.com/lyric/fcgi-bin/fcg_query_lyric_new.fcg`（**生产在用**） | **没测过** | **200 / 65ms / `retcode=0` / 歌词 1743 字符** |

⇒ **QQ 行级源一直是好的** ⇒ T90-④ 的定位从「修复已坏的功能」更正为
   「**给可用的 QQ 源加逐字**」⇒ **只增不减**，**不推倒重来**。
⇒ T90-② 的台账段留的是**假陈述** ⇒ 由 T90-④ 段**显式更正**（不改历史段）。

### 10.2 取词链路（**行级先、逐字后**）

| 步 | 端点 | 实测（2026-11-14） | 作用 |
| --- | --- | --- | --- |
| ① 搜索 | `c.y.qq.com/soso/fcgi-bin/client_search_cp` | 200 / 1364ms | `songmid` **+ `songid`** |
| ② 行级歌词 | `c.y.qq.com/lyric/fcgi-bin/fcg_query_lyric_new.fcg` | 200 / 65ms | 原文 + 翻译（**既有生产路径，一行不改**） |
| ③ 逐字歌词 | `u.y.qq.com/cgi-bin/musicu.fcg`（`GetPlayLyricInfo`） | 200 / 62ms | qrc **密文** → 解密 → 增强 LRC |

- ⚠️ **为什么行级在前**：既有生产路径与既有测试都认「行级是第 2 个请求」
  ⇒ 保持顺序 ⇒ **既有行为与既有断言一条不改**。
- ⚠️ **`songid` 能省一跳**：`client_search_cp` 的每条候选**都带** `songid`（数值型，
  与 `musicu.fcg` 的 `track_info.id` 一致）⇒ **不必**再查一次「songmid → songID」
  （那一跳 213ms）。**搜索结果里没有 `songid` ⇒ 这一路直接放弃（不出网）**。
- ⚠️ **不采用**洛雪的 `musicu.fcg` 搜索（要 `signRequest` 签名，脆弱）。

### 10.3 合并与错误语义

| 情况 | 结果 |
| --- | --- |
| 逐字成功 | **原文用逐字**（增强 LRC）；翻译**优先用行级**（已是明文 LRC、时间轴一致）；罗马音只来自逐字 |
| 逐字失败 | **回落行级**（行为与本任务之前**一字不变**） |
| 行级 + 逐字**都**失败 | 报**行级**的错误（它是用户原本就在用的那一路） |
| 行级 `retcode ≠ 0` | `error`（带错误码，如 `-1310`）—— **不是**「确实没有」 |
| 行级 200 但正文**不是 LRC** | `not-found` |
| 行级 HTTP 失败 | `error`（message 含状态码，如 `404`） |

### 10.4 QRC 明文的形状（实测，样本：孤勇者）

- 行头 `[起ms,时长ms]`；词元组 `(起ms,时长ms)`；
- **词时间是绝对毫秒**（更正 §4.4；实测第 40 行：行首 93766、首词 93766、末词 95181）；
  实现保留「**相对**」的兜底判定（**词时间 < 行首 ⇒ 相对**）——
  两种基准下**第一词的结果一致** ⇒ 不会误判；
- 头部 **12 行无行头**（`[ti:]` 之类）⇒ 天然被行头规则挡掉；
- **69 行带行头的行里，12 行是制作信息**（实测角色词）：
  `词` `曲` `编曲` `吉他` `人声录音师` `混音/母带` `词版权管理方` `曲版权管理方`
  `录音作品及MV版权` `出品监制` `制作人` `联合出品方`；
- ⇒ 滤干净之后 **57 行歌词 + 12 行制作信息 = 69 行**（活体验证已核对）。
  ⚠️ **⚠️ 这组数字已被 §11.1 更正**：真机回归发现还有 **2 行制作信息 + 1 行标题行**漏网
  ⇒ 真正的歌词是 **54 行**（69 = 54 歌词 + 14 制作信息 + 1 标题行）。

**元信息行判定（三选一即算）**：先取**第一个冒号**之前当「角色部分」，再：

1. **精确命中**白名单；
2. **后缀命中**：角色部分 **≤ 6 字**且以某个**多字**角色词**结尾**
   （覆盖 `联合出品方` 这类带修饰前缀的复合角色词）；
3. **前缀命中**：以某个**多字**角色词**开头**，剩下 ≤ 12 字且**不含标点 / 空白**
   （覆盖 `录音作品及MV版权`）。

⚠️ **比 T74a 更严**：T74a 是「前缀白名单命中 ⇒ 无条件跳过」；
   本仓库实测发现「只按前缀」既会**误杀歌词行**（歌词里以「曲」「词」开头的句子很多）
   又会**漏掉复合角色词** ⇒ 必须三管齐下。
⚠️ **单字角色词（`词` `曲` `鼓`）只走「精确匹配」** ⇒ 「词不达意：…」不会被误杀。
⚠️ **误杀的代价高于漏杀**：漏杀只是多显示一行制作信息（难看），
   误杀是**歌词内容丢失**（不可接受）⇒ 单字角色词不进前缀表。

**标题行**（`歌名 - 歌手`）沿用 T74a 的**三条件**：前 5 条**带行头的候选行**内、
≤ 30 字、含 ` - `。
⚠️ 「前 5 行」按**候选行**计（不是源行）—— QQ 的 QRC 头部有 12 行无行头的元信息，
按源行计会让标题行规则**永不生效**（等于没有）。
⚠️ **⚠️ 这条规则已被 §11.2 补充**（真机回归发现 45 字的长标题行会漏网
⇒ 补了「以**歌名**开头」这条判据；**本条仍作为兜底保留**）。

### 10.5 3DES 的正确性锚点（**不是** `node:crypto`）

⚠️ **原计划作废**：洛雪的注释只说 QRC 的 S 盒与标准 DES 差**两处**
（`S2[23]=15`、`S4[53]=10`）⇒ 原打算「用 `node:crypto` 的标准密文交叉验证」。

**实测（2026-11-14）**：

1. `node:crypto` 的 `des-ede3` **可用**，但 `des-ecb` / `des-cbc` **不可用**
   （本机 OpenSSL 3 没开 legacy provider）；
2. 把那两处改回标准值后，本实现与 `node:crypto` **仍然对不上**；
3. 穷举「单点修正 8192 种」「S2×S4 双点 1024×1024 种」⇒ **都无解**
   ⇒ **QRC 的 3DES 与标准 DES 的差异不止那两处**（是改造过的 DES 变体）。

⇒ **唯一可靠的外部锚点 = 与洛雪上游逐字节差分**：
   同一份**真实** QQ 密文 ⇒ 本实现与上游解出的明文**逐字节相同**
   （实测 **8587 字符全等**）。
⇒ 仓库里固化的是「**占位歌词**密文 + 上游解出的期望明文」这组 fixture
   （**真实密文不入库**：QRC 密钥是公开的 ⇒ 密文入库 = 把歌词放进公开仓库）。
⇒ 同时保留**换表差分**断言（同一密文换 S 盒 ⇒ 结果不同）⇒ 证明那两处改动**真的在起作用**。

### 10.6 超时预算

QQ 一次取词要走**三跳**（实测 ≈1.5s）⇒ 通用 3s 预算**余量太薄**
⇒ QQ 源**单独放宽**到 **8s**（§6 风险 4 已写明「源级超时预算要单独放宽」）。
⚠️ 单测**显式注入**的 `perSourceTimeoutMs` **优先**（那是测试钩子，语义不变）。

### 10.7 出处与边界

- 3DES 核心**移植自洛雪**（Apache-2.0）⇒ 完整声明见 `THIRD_PARTY_NOTICES.md`；
- 改动清单：改写 TypeScript、拆出 S 盒补丁、抽出 `decrypt3des` / `encrypt3des`、
  补 QRC→增强 LRC 转换、补元信息行过滤；
- ⚠️ **模块拆分**：`electron/lyricCodecs/qrc.ts` = **只解密**（**无相对 import** ⇒
  探针脚本能直接用 raw Node 跑它）；`electron/lyricWordFormat.ts` = **纯格式转换**
  （`msToLrcTag` + yrc/qrc → 增强 LRC + 元信息判定）；
- ⚠️ **待校准**：QQ 的 `trans` / `roma` 实测样本为 **0 字节** ⇒ 代码路径已接上，
  但**「该源能拿到罗马音」这件事没有实测样本支撑** ⇒ 台账里如实标注。

### 11.6 对账口径（回归脚本用）

⚠️ **不能用「标签数」当期望词数**，也不能用「`line.words.length`」当
**DOM 元素数**——渲染层有三条会改变数量的规则：

1. `parseWordSegments`：**后面没有文本**的标签**不成词**；
2. `assemble`：**时间戳相同**的多行会**合并**（第一条作原文、其余作翻译 ⇒ 词被丢掉）；
3. `LyricView.buildSegments`：词的字符数与行文本**对不上** ⇒ 整行退化成纯文本
   ⇒ 该行**一个 `[data-word]` 都不渲染**；且**词内含空白**时**一个词会拆成多个元素**。

⇒ 期望值必须用**渲染层的真解析器**（`parseEnhancedLrc`）+ **同一套 `buildSegments` 规则**算。

## 12. T90-④-b：词内含空白 ⇒ 填色分段重置的修复（2026-11-14）

### 12.1 症状与根因

QQ（网易云同形）会把**整段英文**（含空格）塞进**一个**词元组
（实测《孤勇者》第 45 行有 1 个词：18 字符、3 个普通空格 `U+0020`、时长 0.646s）
⇒ 渲染层的 `LyricView.buildSegments` 按空白把它**拆成多个 DOM 元素**
（**共用同一个 `data-word`**）
⇒ 卡拉OK 填色时**这些元素同时是「当前词」**
⇒ 每个片段**各自从 0 起算** ⇒ 视觉上就是「**填色分段重置**」。

⚠️ **不能改渲染层**：`test/lyric-view.test.tsx` **显式钉住**了
「含空格的词被拆成多个片段、共享一个词号、一起染色」这个行为 ⇒ 改它等于**推翻既有断言**。

### 12.2 解法：转换层就**别产出「内部含空白的词」**

`electron/lyricWordFormat.ts` 新增两个助手（**qrc 与 yrc 共用**）：

- `splitWordByWhitespace(text)`：按**空白串**切开，空白**跟着它前面的片段**走
  ⇒ 拼回去**逐字等于原文**（不丢空格）；
  **纯空白**的片段（词首/词尾多出来的空格）**并进相邻的有字片段**
  ⇒ 否则渲染层 trim 之后那个片段会「消失」（凭空少一个词）；
- `splitWordsAtWhitespace(words, lineEnd)`：把一行里**内部含空白**的词
  **拆成多个独立词**，时间**按非空白字符数比例**分配。

### 12.3 ⚠️ 时间口径必须与渲染层**逐字一致**

渲染层 `assemble` 给每个词的**词尾** =「**下一个词的起点**」；
行内最后一个词 ⇒「**下一行的行时间**」（没有下一行 ⇒ 行时间 + 0.5s）。

⇒ **跨度**必须用这套口径，否则填色会漂。
⇒ 为此**两个转换器都改成两遍**：第一遍解析出全部行（qrc 还要先滤掉元信息行
——**被丢掉的行不参与「下一行行时间」的计算**），第二遍才知道「下一行行时间」。

⚠️ **QRC 的行时长不能用**：实测 69 行里只有 10 行满足「行时长 == 下一行行时间 − 行首」
（差值样例 −1 / 1 / 1139 / 1823 ms）⇒ 行时长是**源给的另一套口径**。
⚠️ **QRC 的词时长也不能用**：实测行 32 首词的 QRC 词时长 481ms，
而渲染层给的词尾跨度是 3752ms ⇒ 差一个数量级。

### 12.4 两条护栏

1. **跨度不够就不拆**：`跨度（ms） < 片段数` ⇒ 必然出现「零长度的词」
   （渲染层会算出 `end === start` ⇒ 比例除零）⇒ **保持原样**；
2. **片段起点必须严格递增**（毫秒）⇒ 同上；
   且**最后一个片段的起点必须小于词尾**（否则它会盖住下一个词）。

### 13.2 `fmt` 的选择：**有逐字就用逐字**，没有就回退行级

洛雪的口径（`musicSdk/kg/lyric.js`）：`(krctype == 1 && contenttype != 1) ? 'krc' : 'lrc'`
⇒ 实测《孤勇者》：`krctype = 1` / `contenttype = 0` ⇒ **真逐字**。

⇒ 本实现：
1. 先按 `krctype` / `contenttype` 决定 `fmt`；
2. **`fmt=krc` 优先**（真逐字）；下载失败 / 解密失败 ⇒ **回退 `fmt=lrc`**（行级）
   ⇒ 歌词**不会因为「没有逐字」而整首丢掉**（与 QQ 的「行级先 / 逐字后」同一套思路）。

### 13.3 KRC 解密（`electron/lyricCodecs/krc.ts`）

```
body   = base64Decode(content).subarray(4)       // 跳过 "krc1"
body[i] ^= KRC_XOR_KEY[i % 16]                   // 循环 XOR（16 字节固定密钥）
plain  = zlib.inflateSync(body).toString('utf8') // 标准 zlib
```

- `KRC_XOR_KEY = [64,71,97,119,94,50,116,71,81,54,49,45,206,210,110,105]`；
- ⚠️ 解密后**可能带 UTF-8 BOM**（实测《孤勇者》《Counting Stars》带，《一路向北》不带）⇒ 解析须容忍；
- ⚠️ zlib 用 **Node 内置**（`node:zlib`）⇒ **不引新 npm 依赖**（与 `electron/lyricCodecs/qrc.ts` 同款）；
- ⚠️ **头不是 `krc1` ⇒ 抛错**（如实报「源不可用」，不静默吞掉）；
- ⚠️ **不移植洛雪的代码**：算法本身是公开算法（4 个独立公开实现交叉验证一致），
   本仓库**按算法自行实现** ⇒ `THIRD_PARTY_NOTICES.md` **不需要新增条目**。

### 13.4 KRC → 增强 LRC（`electron/lyricWordFormat.ts` 的 `krcToEnhancedLrc`）

**与 QRC / yrc 的三处差异**（转换器必须区别对待）：

| | 网易云 yrc | QQ qrc | **酷狗 KRC** |
| --- | --- | --- | --- |
| 词元组形状 | `(起ms,时长ms,0)` | `(起ms,时长ms)` | **`<起ms,时长ms,0>`**（尖括号） |
| 词时间的基准 | 绝对 | 绝对（实测） | **相对行开始** ⇒ 绝对 = **行首 + 相对** |
| 额外内容 | 无 | 制作信息 + 标题行 | 制作信息 + 标题行（**形态同 QRC**） |

**规则（定死）**：

1. 行头只认 `[起ms,时长ms]`；**无行头**的行（`[id:]` / `[ti:]` / `[ar:]` 之类）**丢掉**
   （实测《孤勇者》81 行里 **11 行**是无行头的元信息）；
2. **元信息行**（制作信息 / 标题行）**丢掉**（见 §13.5）；
3. 行内按**顺序扫描**找词元组 `<(\d+),(\d+),(\d+)>`（只认数字形状）
   ⇒ 词文本里的尖括号**不会错位**；
4. 词文本 = 词元组之间的内容（**原样保留**，不 trim 词内空格）；
5. 词时间 = **行首 + 相对毫秒**（KRC 的词时间**一律按相对基准**处理）。

   ⚠️⚠️ **本条是对初稿的技术更正（2026-11-14 实现前发现）**：
   初稿写的是「用与 QRC 同一个 `resolveWordTime` 兜底
   （『相对值 ≥ 行首 ⇒ 判绝对』）」⇒ **那条兜底对 KRC 是错的**：
   `resolveWordTime` 是为 **QRC 的绝对基准** 设计的；而 KRC 的行内相对值
   **可以超过行首的毫秒数**（例：行首 1000ms、行长 3000ms 的长句 ⇒ 行内相对值 2000
   ⇒ `2000 ≥ 1000` ⇒ 被**误判成绝对** ⇒ 绝对时间少了 1000ms ⇒ **填色偏 1 秒**）。

   ⇒ **一律相对**（KRC 的格式规范如此，3 首实测也一致）⇒ 绝对 = **行首 + 相对**。
   ⚠️ 若将来遇到**绝对基准**的 KRC 样本，应在**整首歌**层面判定
   （相对基准 ⇒ 每行首词的相对值恒为 0），**不要**用「逐词比较大小」那种判据；
6. **零时长词**（实测《孤勇者》4 个）→ **并入前一个词**，不单独成词；
7. **空文本的词** → **不产出标签**；
8. **词内含空白** → **拆成多个独立词**（见下）；
9. 空串 / 非串 → 返回空串（**不抛异常**）。

#### ⚠️ 第 8 条是本任务的技术要点（**实测数据**）

酷狗**也**把整段英文塞进**一个**词元组 ⇒ 与 QQ / 网易云同形 ⇒ 必须走
T90-④-b 的 `splitWordsAtWhitespace` ⇒ 否则卡拉OK 填色**分段重置**。

实测（2026-11-14，三首）：

| 歌 | 歌词行 | 词元组 | **含空白的词元组** |
| --- | --- | --- | --- |
| 《孤勇者》/ 陈奕迅 | 69 | 591 | 24 |
| 《一路向北》/ 周杰伦 | 35 | 358 | 21 |
| 《Counting Stars》/ OneRepublic | 100 | 547 | **432** |

⚠️ **英文歌最严重**（《Counting Stars》**79%** 的词元组含空白）⇒ 不拆必然错。

#### 词尾口径（**与 T90-④-b 完全一致**）

- 词尾 = **下一个词的起点**；行内最后一个词 = **下一行的行时间**（无下一行 ⇒ 行时间 + 500ms）；
- ⚠️ **KRC 的行时长不能用**：实测《孤勇者》行 11 的行时长 7433ms，
  而「下一行行首 − 行首」= 7499ms ⇒ 行时长是**源给的另一套口径**；
- ⚠️ **KRC 的词时长也不采用**（同 QRC 的结论：源给的词时长与渲染层跨度对不上）
  ⇒ 一律按「下一个词起点 / 下一行行时间」推。

## 14. T90-⑥ 的实现约定：酷我源（2026-11-14）

⚠️ 本节所有结论都是**本机真实 Electron 主进程**实测（不是 Node 探针）——
T90-⑤ 已证明「Node 的 fetch 能通 ≠ 生产能通」（Chromium 分区栈全局拦 http 明文）。

### 14.1 ⚠️ 端点必须走 **https**（同因 §13.1，但**同端点换 https 就能通**）

| 用途 | 端点 | 实测 |
| --- | --- | --- |
| 搜索 | `https://search.kuwo.cn/r.s?client=kt&all=<关键词>&pn=0&rn=10&uid=794762570&ver=kwplayer_ar_9.2.2.1&vipver=1&show_copyright_off=1&newver=1&ft=music&cluster=0&strategy=2012&encoding=utf8&rformat=json&vermerge=1&mobi=1&issubtitle=1` | **200 / 204ms / 10 候选** |
| 歌词（逐字） | `https://mlyric.kuwo.cn/mobi.s?f=web&type=lyric&lrcx=1&rid=<rid>&encode=utf8` | **200 / 181ms** |

- ⚠️ **http 明文一律被拦**（实测 `http://search.kuwo.cn/r.s` 与 `http://mlyric.kuwo.cn/mobi.s`
  都是 `net::ERR_BLOCKED_BY_CLIENT`）
  ⇒ **只要把协议换成 https，同一个端点就能用**
  （与酷狗不同：酷狗的 `mobilecdn` 证书主机名不匹配 ⇒ 必须换域名；酷我**不用换域名**）；
- 搜索响应：`{ abslist: [{ MUSICRID, SONGNAME, ARTIST, ALBUM, DURATION }] }`
  ⇒ `rid` = `MUSICRID` **去掉 `MUSIC_` 前缀**；
  ⇒ ⚠️ `DURATION` 是**秒**（实测《孤勇者》= 256）⇒ 与 `pickCandidate` 的口径一致，
  **不用**除 1000；
- 歌词响应：**二进制**（不是 JSON）⇒ 走 `res.arrayBuffer()`；
- ⚠️ **已排除的端点**（本机实测）：
  - `https://www.kuwo.cn/api/www/lyric?rid=` → `{"success":false,...}`（要 csrf + cookie）；
  - `https://m.kuwo.cn/rest/search` / `https://m.kuwo.cn/rest/lyric` → **403**；
  ⇒ 一律**不用**。

### 14.2 酷我 **lrcx** 的形状（实测三首：孤勇者 / Counting Stars / 一路向北）

    [mm:ss.xxx]<a,b>词文本<a,b>词文本…

- **行头**是 `[mm:ss.xxx]`（**三位**毫秒）
  ⇒ 与 QRC / KRC 的 `[起ms,时长ms]` **完全不同**，解析器要另写一条分支；
- **词标签**是**尖括号** `<a,b>`（`a` / `b` **可负**）；
- ⚠️ 词时间**相对行首** ⇒ **绝对 = 行首 + 相对**；
- 头部标签行（`[kuwo:…]` / `[ver:…]` / `[ti:…]` / `[ar:…]` / `[al:…]` / `[by:…]` /
  `[offset:…]` / `[ml:…]`）**没有行头** ⇒ 一律丢掉
  （⚠️ `[ml:1.0]` 是 Counting Stars 独有的，不在洛雪的标签白名单里 ⇒ 也要能认出来「不是歌词行」）。

### 14.3 ⚠️ `[kuwo:八进制]` 偏移参数（本任务的**技术要点**）

`<a,b>` **不是**「开始毫秒 + 时长毫秒」，而是**经过缩放的**一对数：

    offset  = trunc(v / 10)      // v = parseInt("[kuwo:NNN]" 的 NNN, 8)
    offset2 = trunc(v % 10)
    词相对开始 = trunc(|a + b| / (offset  × 2))
    词相对时长 = trunc(|a - b| / (offset2 × 2))

- 三首实测的 `[kuwo:…]` **各不相同** ⇒ **不能写死**：

  | 歌 | `[kuwo:…]` | 八进制值 | `offset` | `offset2` |
  | --- | --- | --- | --- | --- |
  | 孤勇者 | `[kuwo:034]` | 28 | 2 | 8 |
  | Counting Stars | `[kuwo:140]` | 96 | 9 | 6 |
  | 一路向北 | `[kuwo:061]` | 49 | 4 | 9 |

- ⚠️ **必须用对参数**，否则整首的时间轴全错。验算（Counting Stars，`offset=9` / `offset2=6`）：
  `<168,-168>` → 相对开始 `|0|/18 = 0`、时长 `|336|/12 = 28`；
  `<420,84>` → 开始 `|504|/18 = 28`、时长 `|336|/12 = 28` ⇒ **首尾相接**、每词 28ms ✓；
- ⚠️ **缺省**：文件里**没有** `[kuwo:…]` ⇒ `offset = offset2 = 1`（洛雪的缺省口径）；
- ⚠️ `offset` 或 `offset2` 为 **0** ⇒ 该文件**不可用**（除零）⇒ 抛错（洛雪的 `isOK=false` 同款口径）；
- `[kuwo:…]` **可以出现在任何一行** ⇒ 必须**先全量扫一遍**再开始解析行。

### 14.4 ⚠️ 翻译行 = 「**同一时间戳的前一行**，且词标签**全为 `<0,0>`**」；⚠️ **它属于「上一句」原文**

实测（Counting Stars，同一首歌，**文件原序**）：

    [00:00.790]<0,0>Lately <0,0>I've …                                      ← 翻译（零时长）
    [00:05.499]<0,0>最近我总是辗转反侧 难以入眠                                ← 翻译（零时长）
    [00:05.499]<1008,-1008>On <2706,318>just <4257,2349>doing <6504,2964>what …  ← 原文（真实时长）

- ⚠️ **翻译行排在原文行之前**，且**两者时间戳完全相同**；
- ⚠️⚠️ **翻译行自己的时间戳 = 「下一句」原文的时间戳**，而它的**文本属于「上一句」原文**
  ⇒ ⚠️ **按自己的时间戳对齐 ⇒ 中文整体偏移一行**（挂到下一句英文上）；
- ⇒ **对齐规则（定死，对齐洛雪）**：翻译行的时间戳要**回退**到
  **「它前面最近一条原文行」的时间戳**（见 §14.8 第 12 条）。
- ⇒ **权威依据**：洛雪上游 `kw/lyric.js` 的 `sortLrcArr` 就是这么做的 ——
  同时间戳第二次出现时，**弹出前一条**（= 翻译行），
  再 `tItem.time = lrc[lrc.length - 1].time`（= **上一句**原文的时间戳）：

      for (const item of arr) {
        if (lrcSet.has(item.time)) {          // 同时间戳第二次出现
          if (lrc.length < 2) continue
          const tItem = lrc.pop()             // 弹出前一条（翻译行）
          tItem.time = lrc[lrc.length - 1].time // ← 回退到「上一句」原文的时间戳
          lrcT.push(tItem)
          lrc.push(item)
        } else { lrc.push(item); lrcSet.add(item.time) }
      }

  ⇒ 洛雪产出的 `lrc` / `lrcT` **两份 LRC 逐行同刻** ⇒ 翻译行与原文行一一对应。
- ⚠️ 翻译行的**词标签全是 `<0,0>`** ⇒ 翻译**只有行级**时间，**没有逐字**；
- 实测规模：Counting Stars **100 行翻译 / 101 行原文**（严格交替：`[原文, 翻译, 原文, 翻译, …]`）
  ⇒ 过滤掉 4 行元信息 + 1 行空行后 = **96 行原文 / 96 行翻译，时间戳逐行相等**；
  中文歌（孤勇者、一路向北）**没有**翻译行 ⇒ 翻译字段为空串；
- ⇒ **判据（定死）**：同一时间戳的一组行里，
  **词标签全为零时长的那行 = 翻译**，**有真实时长的那行 = 原文**；
  一组里只有一行 ⇒ 它就是原文；
  一组里两行都零时长 ⇒ 取**后一行**为原文（实测顺序：翻译在前）；
- ⇒ 翻译产出**行级 LRC**（`[mm:ss.xxx]文本`），与 QQ 的 `translation` **同一形状**；
- ⚠️ 翻译行也要过**制作信息过滤**（`isQrcCreditLine`），
  但**不套**标题行规则（标题提示是给原文用的）。

### 14.5 词内空白：**酷我已经按词拆开了** ⇒ 不需要拆词

- 实测三首的词文本里**内部空白词 = 0**：
  孤勇者 16 个、Counting Stars 185 个、一路向北 1 个，**全部是「尾随空格」**
  （如 `吗 ` / `I've ` / `- `）；
- 英文歌里的**空格是独立的词元组**（如 `<528,444> <753,345>Stars`）
  ⇒ 酷我**不会**把整段英文塞进一个词元组
  ⇒ **不存在** T90-④-b 那个「填色分段重置」的坑；
- ⇒ 仍**调用** `splitWordsAtWhitespace` 作**防御**（当前实测是 no-op：
  `splitWordByWhitespace('吗 ')` → `['吗 ']`，`splitWordByWhitespace(' ')` → `[' ']`）；
- ⚠️ **纯空格的词元组必须保留**（不能丢）：
  渲染层的 `parseWordSegments` 会把它 `.trim()` 成空串并丢掉，
  但**行文本**（`stripWordTags`）仍保留那个空格
  ⇒ 丢了它，英文歌词会显示成 `CountingStars`（**空格消失**）。

### 14.6 元信息行过滤：**复用 QRC 那套更严的规则**（同 §13.5）

实测《孤勇者》含 `词：唐恬` / `曲：钱雷` / `编曲：钱雷` 等**制作信息**，
以及标题行 `孤勇者 (《英雄联盟：双城之战》动画剧集中文主题曲) - 陈奕迅`
⇒ 与 QRC / KRC **同形** ⇒ 直接用 `isQrcMetaLine`（带**歌名提示**判标题行）。

### 14.7 解密（`electron/lyricCodecs/kuwo.ts`）

载荷形状（实测）：

    "TP=content\r\nlrcx=1\r\n\r\n" + <密文>

解密链：

    buf[:10].toLowerCase() === 'tp=content'   // 不对 ⇒ 抛错
    body = buf.subarray(buf.indexOf('\r\n\r\n') + 4)
    inflated = zlib.inflateSync(body)        // 标准 zlib
    inner = Buffer.from(inflated.toString('utf8'), 'base64')
    out[i] = inner[i] ^ 'yeelion'[i % 8]     // 8 字节固定密钥，循环 XOR
    plain = out.toString('utf8')

⚠️ **出处**：本仓库**按算法自行实现**，**不移植**洛雪的源码
（与 `electron/lyricCodecs/krc.ts` 同款处理）⇒ `THIRD_PARTY_NOTICES.md` **不需要新增条目**。
⚠️ **真实密文不入库**（XOR 密钥是**公开**的 ⇒ 真实密文入库 = 把歌词放进公开仓库）
⇒ 单测用**自己合成**的密文，且**独立手写**一份 XOR（生产密钥写错时用例**会红**）。

### 14.8 转换口径（`electron/lyricWordFormat.ts`）

- `kuwoToEnhancedLrc(plain, hint?)` → 增强 LRC（原文，逐字）；
- `kuwoToPlainLrc(plain)` → 行级 LRC（翻译用）；
- **规则（定死）**：
  1. 先全量扫 `[kuwo:…]` 取出 `offset` / `offset2`（缺省 1 / 1；为 0 ⇒ 抛错）；
  2. 行头只认 `[mm:ss.xxx]` / `[mm:ss.xx]`；**没有行头**的行（标签行）**丢掉**；
  3. 同一时间戳的行**分组**：全零时长的那行 = **翻译**，有真实时长的那行 = **原文**
     （见 §14.4）；⚠️ **翻译行的文本属于「上一句」原文**（不是同戳的那句）；
  4. **元信息行**（制作信息 / 标题行）**丢掉**（`isQrcMetaLine` + 歌名提示）；
  5. 词的**绝对时间** = **行首 + 相对毫秒**（§14.3 的公式算出来的相对值）；
  6. **零时长词** → **并入前一个词**（与 QRC / KRC 同款）；
  7. **空文本的词** → **不产出标签**；
  8. **纯空格的词元组** → **保留**（§14.5：丢了行文本里的空格就没了）；
  9. **词内含空白** → 走 `splitWordsAtWhitespace`（防御性，当前 no-op）；
  10. 一行里**没有有效词** → **跳过该行**；
  11. 空串 / 非串 → 返回空串（**不抛异常**）；
  12. ⚠️ **翻译行的时间戳必须「回退」**（洛雪 `sortLrcArr` 同款，§14.4）：
      翻译行产出时用 **「它前面最近一条原文行」的时间戳**，**不是它自己的**；
      - 「前面最近一条原文行」按**文件原序**取（含**元信息行**——元信息行本身会被
        原文侧滤掉，它对应的翻译也就随之无处可挂 ⇒ 一样是「不显示」）；
      - **前面一条原文行都没有** ⇒ 这条翻译**丢掉**（洛雪同款：`lrc.length < 2` ⇒ `continue`）；
      - ⇒ 产出的翻译 LRC 与原文 LRC **逐行同刻** ⇒ 渲染层按时间戳精确对齐
        ⇒ **每一句英文都挂上自己那一句的中文**（不偏移）。

## 15. T90-⑦ 的实现约定（咪咕源）

### 15.1 侦察结论（2026-11-14 实测，10 首歌 / 40 个候选）

| 环节 | 端点 | 结果 |
| --- | --- | --- |
| 搜索 | `GET https://jadeite.migu.cn/music_search/v3/search/searchAll` | ✅ 200 / **102–338 ms** / `code=000000` / 候选 **21–57** 个 |
| 歌词信息 | `POST https://c.musicapp.migu.cn/MIGUM2.0/v1.0/content/resourceinfo.do?resourceType=2` | ✅ 200 / 52–111 ms |
| 歌词载荷 | `GET https://d.musicapp.migu.cn/data/oss/resource/…` | ✅ 200 / 120–230 ms |

- ✅ **咪咕确实给逐字**：40 个候选里 **26 个有 `mrcUrl`**、4 个有 `trcUrl`、**40 个有 `lrcUrl`**；
- ⚠️ **载荷三种形态**：
  - `mrcUrl` ⇒ **hex 文本密文**（实测 33 680 字节十六进制）⇒ **需要解密**；
  - `lrcUrl` ⇒ **明文行级 LRC**（`[mm:ss.xx]`）；
  - `trcUrl` ⇒ **明文行级 LRC**（翻译）；
- ✅ **翻译与原文同刻**：trc 的时间戳与**同一首歌**的 lrc **完全一致**（实测 127/127、26/26、27/27）
  ⇒ 可以直接当**行级翻译 LRC** ⇒ 渲染层按时间戳**精确对齐**。
- ✅ **在真实 Electron 主进程里复验过**（`release/verify/t90-07-migu-electron-net-probe.mjs`，
  走生产同形的分区栈 `fn-nas-v0`）：搜索 **200 / 307 ms / 24 个候选**、
  `resourceinfo` **200 / 103 ms**、mrc **200 / 152 ms / 33 680 B（hex）**、
  lrc **200 / 109 ms / 68 行**
  ⇒ **三个端点在 Chromium 分区栈里都通**（全是 https ⇒ 不受「http 明文被拦」影响）。
- ⚠️ **搜索结果里 `mrcurl` 是空的**，**只有 `resourceinfo` 才给 `mrcUrl`**
  ⇒ ⇒ **必须走 `resourceinfo`**（这也正好落在 §8.1 第 2 条那条修正上）。

### 15.2 链路（**3 跳**）

1. **搜索**：`GET jadeite…/searchAll?isCorrect=0&isCopyright=1&searchSwitch=<json>&pageSize=20&text=<关键词>&pageNo=1&sort=0&sid=USS`
   ⇒ 响应 `songResultData.resultList[][]`，每项含 `songId` / `copyrightId` / `name` / `singerList[]`
   / `duration`（**秒**）/ `lrcUrl` / `mrcurl` / `trcUrl`；
2. **选候选**：复用既有 `pickCandidate`（歌名 → 歌手 → 时长 ±3s 的三级筛选，**不新写**）；
3. **歌词信息**：`POST resourceinfo`，body `resourceId=<songId>`
   ⇒ ⚠️ **必须传 `songId`**（传 `copyrightId` ⇒ `resource: []`，洛雪这里传参错位，见 §8.1 第 2 条）
   ⇒ `resource[0].{lrcUrl, mrcUrl, trcUrl}`；
4. **取载荷**：`mrcUrl` → `lrcUrl` → `trcUrl`（洛雪口径：**优先 mrc（逐字）**，没有才用 lrc（行级））。

### 15.3 搜索签名（**固定密钥 + 时间戳**）

- `sign = md5(`${keyword}${signatureMd5}${salt}${deviceId}${timestamp}`)`
  - `signatureMd5 = 6cdc72a439cef99a3418d2a78aa28c73`
  - `salt = yyapp2d16148780a1dcc7408e06336b98cfd50`
  - `deviceId = 963B7AA0D21511ED807EE5846EC87D20`（**固定**，洛雪同款）
  - `timestamp = Date.now()`（毫秒字符串）
- 请求头：`uiVersion: A_music_3.6.1` / `deviceId` / `timestamp` / `sign` / `channel: 0146921` + Android UA。

### 15.4 mrc 的解密（**TEA 变体，64 位字长**）

- ⚠️ **不是标准 TEA**（标准 TEA 是 32 位字长）⇒ **`node:crypto` 解不了** ⇒ 自己实现；
- 载荷是 **hex 字符串** ⇒ 每 **16 个 hex 字符** = 1 个 **64 位**字（`BigInt('0x…')`）；
- 密钥 = 9 个 64 位常量，⚠️ **实际只用前 4 个**（索引 `(3 & j6) ^ j5` ∈ 0…3）⇒ 其余 5 个是冗余；
- 解密后的字 ⇒ 每字 8 字节 **小端** ⇒ 按 **UTF-16LE** 拼接 ⇒ 字符串；
- ✅ **正确性锚点 = 与上游逐字节差分**：把洛雪 `mg/utils/mrc.js` 的快照留在 `release/verify/`，
  用**真实载荷**比对我们的实现与上游的输出 ⇒ **必须逐字节相等**（不是「看起来对」）；
- ⇒ 出于同样的理由（仓库既有 QRC 3DES 的先例），`THIRD_PARTY_NOTICES.md` **要补一条**说明算法出处。

### 15.5 mrc 明文格式（实测，68 行带行头的样本）

    [ti:孤勇者(《英雄联盟：双城之战》动画剧集中文主题曲) - 陈奕迅]   ← 无行头 ⇒ 丢掉
    [ar:陈奕迅]                                                      ← 无行头 ⇒ 丢掉
    [0,0]作(0,0)词(0,0)：…(0,0)…                                     ← 制作信息行（29 个零时长词）⇒ 丢掉
    [2045,649]都(2045,499)是(2544,50)勇(2594,50)敢(2644,50)          ← 歌词行

- ⚠️ **行头 `[起ms,时长ms]` = 绝对毫秒**；
- ⚠️ **词标签 `(起ms,时长ms)` = 绝对毫秒**（**不是相对行首** ⇒ **更正 §4.4 表格**的「相对行开始」）；
- ✅ **词时长 = 到下一个词的间隔**（实测 **553/553** 行全部满足「下一词起点 − 当前词起点 == 当前词时长」）
  ⇒ 词与词**首尾相接**、铺满整行；
- ✅ **词文本 = 标签「之前」的那一段**（即**标签在词之后**）：
  - 「文本片段数 − 标签数」**恒为 1**；
  - **行首片段恒非空**、**行尾片段恒为空**（68/68）
  ⇒ 若按「标签在词之前」解读，行首会多出一个**没有时间**的残片 ⇒ 与观测矛盾；
  ⇒ 与洛雪 `parseLyric` 的配对（`times[i] ↔ wordArr[i]`）**一致**；
- ⚠️ **元信息行**：制作信息在 mrc 里被**合并成一行**（行头 `[0,0]`、29 个 `(0,0)` 词元组）
  ⇒ 判据只能用**去掉词标签后的文本**（`isQrcMetaLine`），⚠️ **不能用酷我那套「零时长 ⇒ 翻译」判据**
  （咪咕的零时长行是**制作信息**，不是翻译）。

### 15.6 lrc / trc（**明文行级 LRC**）

- 两者都是 `[mm:ss.xx]` 的**行级** LRC（**没有**逐字标签）；
- `lrcUrl` 的内容含**标题行**（`歌名(…) - 歌手`）与**制作信息行**（作词/作曲/编曲/吉他/人声录音师/…）
  ⇒ 同一套 `isQrcMetaLine` 过滤；
- `trcUrl` 的内容含 `[ti:]` / `[ar:]`（**无行头**）与制作信息行 ⇒ 同样过滤；
- ⚠️ trc 的第一行是「歌曲名 X 歌手名 Y」（**不含 ` - `** ⇒ 认不出是标题行）
  ⇒ 但它的时间戳（`00:00.00`）在原文侧**没有对应行**（原文那一行是标题行，已被滤掉）
  ⇒ 挂不上 ⇒ **不会显示**（实测：127 行翻译里有 1 行这样 ⇒ 无害）。

### 15.7 转换口径（`electron/lyricWordFormat.ts`）

- `miguToEnhancedLrc(plain, hint?)` → 增强 LRC（原文，逐字）；
  **规则（定死）**：
  1. 行头只认 `[起ms,时长ms]`；**无行头**的行（`[ti:]` / `[ar:]` 之类）**丢掉**；
  2. 行内**顺序扫描**找词元组 ⇒ 词文本里的括号**不会错位**；
  3. **词文本 = 标签之前的那一段**（标签在词之后 ⇒ 片段 i ↔ 标签 i）；
  4. **词时间 = 标签里的绝对毫秒**（**不加行首**）；
  5. **元信息行**（制作信息 / 标题行）**丢掉**（`isQrcMetaLine`，判定用**去标签后的文本**）；
  6. **零时长词** → **并入前一个词**（与 QRC / KRC 同款）；
  7. **空文本的词** → **不产出标签**；
  8. **纯空格的词元组必须保留**（渲染层会 trim 掉它，行文本仍保留那个空格）；
  9. **词内含空白** → 走 `splitWordsAtWhitespace`（防御性）；
  10. 一行里**没有有效词** → **跳过该行**；
  11. 空串 / 非串 → 返回空串（**不抛异常**）。
- lrc / trc 分支：过滤元信息行 + 丢掉无行头的行 ⇒ **原样输出行级 LRC**（不做逐字转换）。

| 标签精度 | `romalrc` 是**厘秒**（`[mm:ss.xx]`）、`yrc` 行头是**毫秒** ⇒ 渲染层的「时间戳**精确匹配**」**必然失败** |
| 加 `rv=-1` 后 `lrc` / `tlyric` / `yrc` | 照常返回，形状与生产不带时一致（探针全程带 `rv=-1`） |
| 洛雪上游口径 | `parseTools.fixTimeTag`：**顺序配对 + 100 ms 容差**，把副行的时间标签**替换**成原文行的标签 |

⚠️ **洛雪的 100 ms 容差在我们这儿不够用**：实测轴差到 1899 ms
⇒ 直接照搬会丢掉 **44/48** 行 ⇒ **不可照搬**（必须换口径，见 §16.3）。

### 16.2 ⚠️ 本任务暴露的**既有**缺陷（**不是**新引入的）

`romalrc`（罗马音）与 `tlyric`（翻译）在网易云是**同一条 lrc 时间轴**；
而**逐字原文（yrc）是另一条轴**
⇒ 现有代码把副行**原样**交给渲染层时，渲染层的「精确匹配」**全部落空**
⇒ 退到「≤ 0.5 s 就近」⇒ **丢行**（并有挂错行的风险）：

| 样本 | 副行 | 直挂实挂 | 重建实挂（§16.3） |
| --- | --- | --- | --- |
| 残酷な天使のテーゼ | 罗马音 | 25 / 48 | **48 / 48** |
| orion | 罗马音 | 13 / 46 | **46 / 46** |
| 明年今日 | 罗马音 | 34 / 34 | **34 / 34** |
| 樱花树下 | 罗马音 | 39 / 43 | **40 / 40** |
| 残酷な天使のテーゼ | 翻译 | 25 / 48 | **48 / 48** |
| orion | 翻译 | 13 / 46 | **46 / 46** |
| LOSER | 翻译 | 38 / 38 | 38 / 38 |
| Counting Stars | 翻译 | 84 / 98 | **102 / 98**（98 行**精确同刻**；另 4 行是「原文有、翻译没有」的行 ⇒ 走渲染层**既有**的「≤ 0.5 s 就近」兜底） |

⚠️ 这条缺陷**早于**本任务（T67「yrc 优先」时就在了），但与罗马音**同根因**
⇒ **用户拍板（2026-11-15）**：翻译与罗马音**一起重建**，一次修好。

⚠️ **遗留（不在本任务修）**：原文里**没有**副行对应的那几行，渲染层仍会就近挂上**邻行**的副行
⇒ 可能显示一条**不属于该行**的翻译/罗马音。
这是渲染层 `attachAuxiliary` 的**既有**行为（精确匹配失败 ⇒ ≤ 0.5 s 就近），
本任务**不动渲染层** ⇒ 如实记录，留给后续单独评估。

### 16.3 口径：以原文行为锚的「副行重建」（**定死**）

```
原文行 --(纯文本相同 + 顺序单调)--> lrc 行 --(时间精确相等)--> 副行
输出 = [原文行的「原标签」] + 副行的纯文本
```

- **为什么不用洛雪的 `fixTimeTag`**：它按「时间就近 + 100 ms 容差」找对应行，
  而我们的轴差实测到 1899 ms ⇒ 会丢 44/48 行。
- **为什么输出「原文行的原标签」**：输出标签与原文行标签**逐字符一致**
  ⇒ 渲染层 `attachAuxiliary` 的「时间戳**精确匹配**」分支**必然命中**
  ⇒ **不走**「≤ 0.5 s 就近」⇒ 有副行的那些行**零错行**。
- **文本桥为什么可靠**：`romalrc` / `tlyric` 与 `lrc` **精确同刻**（§16.1）
  ⇒ `lrc` 是副行与原文之间**唯一**可靠的桥。
- **顺序单调**：同一句歌词在歌里出现两次（副歌）时按**出现顺序**配对
  ⇒ 实测 6 个「yrc + romalrc 共存」样本：**逆序 0**、重复句不一致 **0–1**。
- **无 yrc（行级原文）时**：文本桥恒成立（原文 == lrc）⇒ **同一套代码、不分支**
  ⇒ 实测 `romalrc` 与 lrc **100% 精确同刻**。
- **宁缺勿错**：配不上的副行**直接丢弃**（不猜、不就近）。
- **人工抽检**：残酷な天使のテーゼ / orion 各 4 行，罗马音与原文**逐句对得上**
  （`蒼い風がいま` → `a o i ka ze ga i ma`）。

### 16.4 `fetchNetease` 的改动

- 请求 URL 加 `rv=-1`；
- `NeteaseLyricPayload` 加 `romalrc?: { lyric?: unknown }`；
- 取 `romalrc.lyric` → 与 `lrc`、原文一起送进重建 → 得到**重新定时**后的副行；
- ⚠️ **仅当副行非空时**才在结果里带 `romanization` 字段
  ⇒ **没有罗马音时结果对象与今天一模一样** ⇒ 既有断言与既有行为**一字不变**；
- ⚠️ **翻译也走同一条重建**（§16.2，用户拍板）。
