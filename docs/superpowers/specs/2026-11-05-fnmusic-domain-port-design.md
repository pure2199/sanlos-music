# T43 设计规格：域名型 NAS 地址走标准端口（端口补全规则第五版）

- 日期：2026-11-05
- 状态：**已获用户批准**（用户拍板「域名一律走标准端口，IP 仍补 5666/5667」）
- 前置：T18-1（中继域名不补端口的第一条例外）

---

## 1. 背景与动机

用户反馈：**自建反向代理的域名型 NAS 地址登不上**，因为客户端把端口「写死」成 5666 / 5667。

### 1.1 真机实测（本轮用探针脚本量的，不是推断）

目标地址：`https://user-proxy.invalid`（用户自建反代，域名**不写端口**）。

| 端口 | 结果 |
| --- | --- |
| **443** | **通** —— TLS 握手成功；证书 CN=`cert-cn.invalid`，SAN 里**含** `user-proxy.invalid`（用户自己的泛域名证书）；`server: openresty` |
| **5666** | **ECONNREFUSED** |
| **5667** | **ECONNREFUSED** ← **这正是旧代码补出来的端口** |
| 80 | 通（openresty，301 跳 https） |

音乐接口本身**完全正常**（免凭证只读接口）：

```
GET https://user-proxy.invalid/music/api/v1/sys/config
→ 200 application/json
  {"code":0,"data":{"nasOAuth":{"clientId":"EDDLUH2WLY"},"serverName":"纯音乐",
   "serverVersion":"1.0.10","mediasrvVersion":"0.8.43", ...}}
```

⇒ **反代工作正常，服务器正常，唯一的问题是客户端把端口补错了。**

### 1.2 为什么旧规则不适用

旧规则只有一条域名例外：**`.fnos.net` 后缀**（`RELAY_DOMAIN_SUFFIX`）——那是 fnOS **官方中继**
`<fnId>.fnos.net` 的形状（官方中继也只听 443）。

而用户这个是**自建反向代理**（openresty + 自有泛域名证书）→ **后缀完全不在白名单里**
→ 旧规则把它当普通 NAS → 补 `:5667` → **必然 ECONNREFUSED**。

⚠️ **不能把用户的私有域名硬编码进白名单**：那是用户自己的域名，写死在代码里不可持续
（用户换域名、又换一套反代，就得再改一次代码）。**要做的是把判定维度换对。**

---

## 2. 关键设计决定

### 2.1 判定维度从「域名后缀」换成「**是不是 IP 字面量**」

| 主机形态 | 真实含义 | 该走哪个端口 |
| --- | --- | --- |
| **IP 字面量**（`192.168.1.2`） | **局域网直连 fnOS 音乐服务** | 5666 / 5667（**既有行为不变**） |
| **域名**（`user-proxy.invalid` / `x.fnos.net` / `nas.local`） | **反向代理 / 公网入口 / 官方中继** | **标准端口 80 / 443** |

理由：**域名几乎总是「入口」，不是「音乐服务本体的端口」**。fnOS 音乐服务用的是非标准端口
（5666 / 5667），**任何**在前面挂一层反代的部署都只暴露标准端口。

⇒ **只有 IP 字面量才补默认端口。**

### 2.2 五条规则（T43 之后）

`src/lib/address.ts` 的 `withDefaultPort()` 按顺序判：

1. 空串 → 原样返回；
2. 非 http/https 协议 → 原样返回（主进程给「地址无效」）；
3. **有显式端口** → **原样返回**（端口一个字符都不改，协议也不改）；
4. **`.fnos.net` 中继域名** → 不补端口 + **协议归一到 https**（官方中继只提供 HTTPS）；
5. **IP 字面量** → 按协议补 5666 / 5667；**其它域名 → 不补端口**（走标准端口）。

⚠️ 第 4 条**必须留在第 5 条前面**：官方中继域名也是域名，若不先归一协议，
用户写 `http://x.fnos.net` 会走 80 → 中继不监听 80 → 连不上。

### 2.3 「是不是 IP 字面量」怎么判

```ts
function isIpLiteral(host: string): boolean {
  if (host.length === 0) return false
  if (host.includes(':')) return true          // IPv6（方括号已去掉 → 必有冒号）
  return /^\d{1,3}(\.\d{1,3}){3}$/.test(host)   // IPv4：四段十进制
}
```

⚠️ **复用 `hostOfAuthority()`**：它已经处理掉 userinfo（`user:pw@host`）、端口（`host:5666`）
与 IPv6 方括号（`[::1]`）→ 判定与拆解用**同一套** host 语义，不会两处口径不一致。

### 2.4 已知代价：局域网**用域名**直连要显式写端口

`nas.local`（局域网 NAS 的主机名）→ 现在走 80 → 连不上 → 要写成 `nas.local:5666`。

⇒ **必须给用户可读的引导**，否则这个变化会变成「新的坑」：

- 登录页地址框下方的提示文案改成写明新规则；
- **连不上时补一句**：「若地址走反向代理或端口非标准，请在地址里显式写出端口（如 `https://host:443`）」。

### 2.5 「域名一律走标准端口」与用户实际拓扑对得上

| 用户怎么访问 | 填什么 | 新规则的结果 |
| --- | --- | --- |
| 局域网直连 | `192.168.1.2` | `http://192.168.1.2:5666` ✓ |
| 局域网直连（https） | `https://192.168.1.2` | `https://192.168.1.2:5667` ✓ |
| **公网反代（本例）** | `https://user-proxy.invalid` | `https://user-proxy.invalid`（443）✓ |
| 官方中继 | `https://<fnId>.fnos.net` | `https://<fnId>.fnos.net`（443）✓ |
| 非标准端口 | `host:1234` | 原样 ✓ |

⇒ **五个场景全对，且都不需要用户手写端口**（除非要非标准端口）。

## 5. 风险与待校准

- ⚠️ **局域网用域名直连**（`nas.local`）现在**要显式写端口**（`nas.local:5666`）→
  这是本次规则的**已知代价**，靠提示文案 + 连接失败提示引导；
- ⚠️ **`isRelayHost` 仍按 `.fnos.net` 后缀判定**（`src/lib/address.ts` 与 `electron/session.ts` 两处）
  → 用户的自建反代**不算**官方中继 → 登录请求**不带** `Cookie: mode=relay`。
  官方中继缺这个 Cookie 会返回 HTML 错误页（实测踩到）；
  ⚠️ **自建反代是否需要该 Cookie 取决于它后面接的是什么**（直连本机 5666 → 不需要；
  转发到官方中继 → 需要）→ **本轮不自动判定**，如实标注为待校准；
- ⚠️ **IPv4 判定只认四段十进制**：`0x7f000001` 这类十六进制写法会被当域名 → 不补端口
  （极端边缘，且 URL 规范化的写法本来就不是用户会填的）；
- ⚠️ **真机未验**：用域名地址**真登录**（需要用户凭证 → 用户侧操作）。
