# T60 设计规格：开源发布到 GitHub

## 1. 起因

T58 之后，仓库已经是「干净」的：工作树、已跟踪文件、忽略区、提交历史里都扫不到用户
的私有标识与明文口令。但仓库**从未被 push 过**（没有 remote），README 是开发期写的内部
口径（术语、量测数据、缺陷细节都混在一起），没有 LICENSE、没有 CI、没有界面截图。

用户要求：**把项目发布到 GitHub**，由我创建仓库、由我写并完善项目说明，账号 `pure2199`。

### 1.1 目标

- 仓库能被公开访问（**Public**），名字与产品一致；
- 首页 README 能让**第一次看到它的人**在 30 秒内搞懂「这是什么 / 怎么用 / 怎么构建 /
  凭什么安全」，并看到真实界面；
- 仓库自带 **LICENSE**（法务口径）与 **CI**（质量闸门）；
- **历史里不能有私有值** —— 公开仓库的历史是永久的，事后补救比事前抹除贵得多。

### 1.2 不做什么

- 不改任何**运行时行为**（本轮只动文档、徽章配置与仓库元信息）；
- 不 bump 版本号（本轮是「发布 0.1.0」，不是「发 0.2.0」）；
- 不打包、不发 Release、不做自动更新的发布流水线（另开任务）；
- 不把任何**真实凭证**写进仓库 —— 包括**测试账号**、FN ID、真实域名与内网地址。

## 2. 仓库与可见性决策

| 项 | 取值 | 理由 |
|---|---|---|
| 仓库名 | `sanlos-music` | 与产品名、应用内「关于」页、exe 产品名一致 |
| 归属 | `pure2199` | 用户给出的账号 |
| 可见性 | **Public** | 用户明确要求；本项目是通用客户端，公开才有生态 |
| 默认分支 | `feature/fnmusic-desktop`（**当前分支**） | 全部工作都在这条线上；`master` 只有 2 个 commit，是历史起点 |
| 认证 | **SSH 公钥** | 凭据只存在本机文件里，不进任何日志、不产生长期 token；GitHub 早已禁用密码推送 |
| 远端 | `git@github.com:pure2199/sanlos-music.git` | 不用 HTTPS + PAT（token 会落进 remote URL 或凭据存储） |

⚠️ **默认分支保持现状**，不把 `master` 强行提到前面：`master` 只有 2 个 commit，
推上去等于给公众一个「几乎空仓库」的首页，`feature/fnmusic-desktop` 才是真正的内容。
（若后续要改默认分支，是一次独立的、显式的决定。）

## 3. 发布前的历史重写（口径）

### 3.1 为什么必须重写

T58 的口径是「清当前版本，**不改写历史**」——理由是那时仓库从未 push，改写 152 个
commit 的 sha 会让台账的 sha 引用全断、且没有任何对外收益。**发布到公开仓库让这个
前提消失了**：历史一旦公开就是永久的。

具体到本项目：早期 commit 里散落着用户的自有反代域名、NAS 内网地址、公网 IP、
本机真实路径与会话标识。它们的危害是**可被利用的**：

- 拿着 FN ID 中继域名（或内网 IP + 端口）**直连 NAS**，绕过中继的带宽限制与访问关卡；
- 仓库里若能找到会话标识，等于给出一个**可复用的访问线索**。

⇒ 用户拍板：**先重写历史，再发布**。

⚠️ 这是**第二次**重写：第一轮按 T58 口径做掉「私有标识」；本轮补上 T59 的
「真实曲库内容 + NAS 对象标识」，两轮规则**叠加**在同一次改写里跑。

### 3.2 抹哪些 / 留哪些

**两道脱敏，叠加执行**：

- **T58**：私有标识（明文口令 / 自有域名 / 真实 IP / 本机路径 / 会话标识）；
- **T59**：**真实曲库内容**（歌名 / 歌手）与 **NAS 对象标识**（`serverGUID` / track guid）
  —— T58 的口径漏了整类，是补扫后由用户拍板「全抹」补上的。

**只做上下文敏感替换**（同名不同义要分开处理）：

- **抹**：用户自有反代域名与证书 CN、FN ID 中继域名、NAS 真实内网 / 公网 IP、
  本机真实路径与 Windows 用户名、会话标识；
- **留**：开发者署名（= 产品身份：关于页 / 安装包属性 / ICP 备案主体）、公司名 / 官网 /
  备案号、RFC1918 示例地址、签名常量、代码里本就存在的通用占位域名。

⚠️ 「开发者署名」与「FN ID」恰是同一串 —— 靠**上下文**区分：
`FN ID \`xxx\`` / `形如 \`xxx\`` 这类**描述值**要抹，署名（作者 / 版权 / 关于页）要留。

### 3.3 执行方式

1. `git bundle create` 做一份**可恢复备份**（重写是不可逆操作，必须留退路）；
2. 先在**临时仓库彩排**一遍 `filter-branch` 的参数组合与替换规则，确认无误再动真仓库；
3. `--index-filter`（改 blob）+ `--msg-filter`（改提交信息）+ `--commit-filter`
   （重写后记 old→new sha 映射）三者共存；
4. 删 `refs/original/*` → `git reflog expire --expire=now --all` → `git gc --prune=now`
   —— **不做这三步，旧对象仍留在 `.git` 里**，重写等于没做；
5. 移除会持有旧对象的遗留 worktree（否则 prune 不掉）。

### 3.4 台账 sha 引用的同步

台账在**仓库外**（不进版本库），里面引用了 97 处 commit sha。重写后这些 sha 全部失效
⇒ 用 old→new 映射把台账里的缩写 sha 同步成新 sha。

- 替换按**等长**做（7 位缩写 → 7 位缩写），字节数不变 ⇒ 不会顺带改动台账的其他内容；
- 替换前先确认**新前缀不冲突**（两个新 commit 撞同一 7 位前缀 ⇒ 缩写会指错对象）；
- 台账里**不是** git sha 的 7 位十六进制串（content-length、错误码）**不碰**。

## 4. README 的结构与内容约定

### 4.1 结构

首页 README 面向**公开读者**，与内部开发文档分工：

| 区块 | 内容 | 面向 |
|---|---|---|
| 徽章 | CI / MIT / Electron / React / TypeScript / Windows | 扫一眼就懂技术栈与质量状态 |
| 一句话 + 技术栈 | 直连 NAS、唯一出网通道是自家代理 | 首屏 5 秒 |
| 界面预览 | 3 张截图（曲库 / 歌词舞台 / 动态词岛） | 首屏 15 秒 |
| English summary | 英文版概要 | 英文检索 / 英文读者 |
| 功能清单 | 12 个能力域（沿用既有内容） | 决策要不要用 |
| 两种登录方式 / 快速开始 / 脚本一览 / 目录结构 | 上手 | 开发者 |
| 安全边界 | 凭证不出渲染层、唯一出网、证书放行范围 | 安全敏感读者 |
| 常见问题 | 用户真实卡点 | 使用中 |
| 文档索引 | 指向 `docs/` | 深入 |
| 开发与贡献 | 规格先行、双 commit、闸门、不引依赖、别提交凭证 | 贡献者 |
| 许可证与声明 | MIT + **第三方非官方客户端**免责声明 + 软件信息 | 法务 / 归属 |

⚠️ **免责声明必须写**：本项目使用 fnOS / 飞牛音乐等第三方名称，公开仓库必须明示
「非官方、无隶属、无背书」，且仓库**不含任何 NAS 服务端代码**。

### 4.2 界面截图的口径

- **用仓库自带的 mock NAS**（`mock-server/`）跑，**不用真实 NAS** → 截图里**不可能**
  出现真实歌名、真实封面、真实曲库规模；
- 占位数据（`示例曲目 N` / `示例专辑 N`）**照实保留**，并在图下注明「取自内置 mock
  NAS，不含任何真实数据」—— 不假装是真实曲库；
- 封面加载失败时应用**退化成占位块**（`CoverImage` 的既有行为），不会留下浏览器破图；
- 词岛窗口是**透明窗口**，用 Playwright 的 `page.screenshot()` 抓**页面内容**
  （不是桌面截图）—— 桌面截图会带出用户的其它窗口与隐私。

### 4.3 英文摘要

公开仓库会被英文检索命中 ⇒ 首屏给一段**英文概要**（能力清单 + 安全模型 + 非官方声明）。
**不做全文英译**（维护成本与漂移风险），只保证首屏可达。

## 5. LICENSE 与 CI

### 5.1 LICENSE

`package.json` 里早就写着 `"license": "MIT"`，但**仓库里没有 LICENSE 文件** —— 公开
仓库缺 LICENSE 会让「到底能不能用」无据可依。补标准 MIT 全文，版权主体写公司与署名。

### 5.2 CI 跑什么 / 不跑什么

| 步骤 | 跑 | 为什么 |
|---|---|---|
| `npm run typecheck` | ✅ | `strict` + 两条 unused 闸门，**最便宜的质量闸门** |
| `npm test` | ✅ | 1862 条单测，12 秒 |
| `npm run build` | ✅ | 主进程 esbuild + 渲染层 Vite，捕获构建期断裂 |
| `npm run e2e` | ❌ | 要起**真实 Electron + GUI**，CI 上不稳且慢；且 Playwright 用的是**仓库自带**的 Electron，不需 `playwright install` |

- runner 用 **windows-latest**：应用是 Windows 专属（托盘 / DPAPI / `safeStorage` /
  自定义协议）；
- **不用 Node 26**：`electron@32` 的 `install.js` 依赖的 `extract-zip@2` 在 Node 26 上
  解压会挂起（`scripts/ensure-electron.cjs` 的注释里记着这条）→ 用 Node 22；
- **绕开 `.npmrc` 的镜像**：仓库的 `.npmrc` 把 Electron 下载指向 npmmirror（面向国内
  网络），GitHub Runner 在境外 → CI 里显式指回官方 release 源；
- `permissions: contents: read`（最小权限）+ 同分支并发取消。

## 7. 验收点

1. `tsc --noEmit` exit 0；`vitest` **1862 passed / 85 files**（不增不减）；`playwright`
   **24 passed**；`npm run build` exit 0；
2. 新增/改写的文本文件：**无 BOM、纯 LF、无 U+FFFD、无 NUL 字节**；
3. README 引用的每个文档 / 图片路径**都真实存在**；
4. README、许可证、CI、提交信息、**全部 commit 的内容与提交信息**里，
   **私有值 0 命中**（T58 与 T59 两道口径一起验）；
5. 旧对象（重写前的 sha）→ `git cat-file` 报 `could not get object info`（**真的没了**）；
6. push 之后：`git ls-remote` 能读到两个分支，远端 HEAD 指向预期 sha；
7. 仓库可见性 = **Public**，README 正常渲染。

## 8. 风险与遗留

- **重写历史会改掉所有 sha** → 台账与任何外部引用（PR 链接、CI 徽章）都需同步；
  已用 old→new 映射同步台账，外部引用目前**没有**。
- **旧会话历史快照**（`.minimax/v2/sessions/**`）里仍含明文口令 —— **不在本仓库**，
  本轮不动；**有效收口是轮换 NAS 账号口令**（用户侧）。
- **没有代码签名证书** → 安装包仍是「未知发布者」，CI 徽章不能替代码签名；
- **CI 只跑 Windows** → 其它平台的构建问题（如有）不会被 CI 捕获；
- `scripts/pack.cjs` 的**跨卷发布缺陷**（`fs.renameSync` 跨盘 EXDEV，且报错文案
  掩盖真因）**本轮不修** → 另开任务；
- 默认分支保持 `feature/fnmusic-desktop`（见 §2），若要改成 `master` 需**显式决定**。
