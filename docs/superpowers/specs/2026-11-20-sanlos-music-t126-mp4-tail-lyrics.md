## 一、起因与定位结论

这条遗留在台账里挂了很久（**出处待定位**）。本轮先**定位**，再**实测**，最后才动手：

| 项 | 结论 |
|---|---|
| **受影响的层** | **只有「流式层」**（NAS 在线播放、没下载、没本地文件）——`electron/embeddedLyric.ts` ③ 分支**只读头 64 KB** |
| **本地文件层** | **不受影响** —— T42 已改成走**顶层原子表按偏移找 `moov`**（随机访问）⇒ 文件尾的 `moov` 也能找到 |
| **服务端支不支持尾读** | ✅ **支持**（实测见 §二） |
| ⚠ **原诊断要修正** | 「`moov` 在文件尾」只是**两种**缺口之一；另一种是「`moov` **超过 64 KB 窗口**」（实测那首的 `moov` 有 **212 KB**）⇒ `udta/ilst` 落在窗口外 |

⇒ 本轮要补的是「**头读窗口不够**」的**两种**情形：

- **G1**：`moov` 在**文件尾**（ffmpeg 默认产物）⇒ 头里**根本没有** `moov` ⇒ **尾读文件尾**；
- **G2**：`moov` 在头但**超出 64 KB 窗口** ⇒ **按 `moov` 的绝对偏移续读**它的内容。

## 二、真机实测（2026-11-20，本机 ＋ FN 中继 ＋ 真实 NAS，**只读 GET**）

- 曲库 `total = 173 671`；扫前 20 000 首的格式分布：
  `mp3 17 965 / flac 1 319 / wav 665 / ape 13 / dts 15 / **m4a 14** / wma 9`；
- 探针：`release/verify/t126-01…04-*.mjs`（gitignored ⇒ **不入库**）；证据 `t126-0*-probe.json`（同不入库）。

### ① 服务端支持尾读

| 请求 | 实测 |
|---|---|
| 无 Range | **200**，`content-length: 43379841`（整文件），`accept-ranges: bytes` |
| `Range: bytes=0-0` | **206**，`content-range: bytes 0-0/43379841` ⇒ 能拿到**总长度** |
| `Range: bytes=0-65535` | **206**，65536 字节（现状：读头） |
| **`Range: bytes=-65536`** | **206**，`content-range: bytes 43314305-43379840/43379841` ⇒ **确实是文件尾** |
| `Range: bytes=-1024` | **206**，`content-range: bytes 43378817-43379840/43379841` |
| `Range: bytes=100-199` | **206**，`content-range: bytes 100-199/43379841` |

⚠ **尾读很快**（215 ms / 116 ms），**从头读反而慢**（4–7 s）⇒ 尾读**不贵**。

### ② 这台 NAS 的 m4a 是 **faststart**，且**没有**内嵌歌词

对**全部 14 首** m4a 逐首量：

| 指标 | 实测 |
|---|---|
| `moov` 在**文件头** | **14 / 14**（偏移 32） |
| `moov` 在**文件尾** | **0 / 14** |
| `ilst` 在**头 64 KB 内** | **14 / 14**（偏移 10 304 – 19 360） |
| 带 `©lyr`（内嵌歌词） | **0 / 14** |
| `moov` 原子大小 | 样本《无眠》= **217 027 字节**（212 KB）⇒ **超过 64 KB 窗口** |

⚠⚠ **两条必须如实写进文档的结论**：

1. 这台 NAS 的 m4a **现有流式层已经能解析**（`ilst` 在头内）⇒ 本轮修复**对这台机当前文件没有可见变化**；
2. 这台机的 m4a **本身没有内嵌歌词** ⇒ 即便修复，也**读不出歌词**（没有词可读）。

⇒ 本轮修的是**机制缺口**（moov 在尾 / moov 超大），**这台机上没有实例**⇒ 用**合成样本**验机制（如实标注，不假装验过）。

## 三、代码事实（不是推测）

| 事实 | 出处 |
|---|---|
| 流式层只读**头 64 KB**（`EMBEDDED_LYRIC_STREAM_BYTES`） | `electron/embeddedLyric.ts` |
| 本地文件层走**顶层原子表按偏移找** `moov`（随机访问） | `electron/audioTags.ts` 的 `parseMp4Tags()` |
| `moov → udta → meta → ilst` 里取 `©lyr`（`data` 载荷前有 **8 字节**） | 同上 |
| `moov` 的解析逻辑**只有一份**（`parseMp4Tags` 内联） | 同上 ⇒ 本轮**抽出来**共用 |
| mock 的 `track/stream` **本来就支持** `bytes=-N`（后缀形式） | `mock-server/server.ts` 的 `parseByteRange()` |

## 四、方案

| 落点 | 做法 |
|---|---|
| `electron/audioTags.ts` | ① 抽出 **`parseMp4MoovContent(content)`**（moov 内容 → 标签）⇒ 本地文件层与流式层**共用一份**；② 导出 **`findMp4AtomInBuffer(buffer, type)`**（走顶层原子表定位 `moov` 的**绝对偏移＋大小**）；③ 新增 **`findMp4MoovInTail(tail)`**（尾段里按 `'moov'` 签名 ＋ **大小自洽校验**定位，返回**是否完整**）；④ 导出 **`isMp4Container(head)`** |
| `electron/embeddedLyric.ts` | ① 新增**可选**依赖 **`fetchStreamRange?(guid, start, length)`**（`start < 0` ＝ 尾读；返回 `{ bytes, totalSize }`）；② 流式层：头读 → 现有解析 → **是 MP4 且没拿到歌词** ⇒ 补读一次（**G2 续读** / **G1 尾读**）；③ 新增 `parseContentRangeTotal()`（从 `Content-Range` 取总长） |
| `electron/main.ts` | 实现 **`fetchStreamRange`**：`Range: bytes=start-end`（尾读用 `bytes=-N`）＋ 从 `Content-Range` 取总长 ＋ **读满即断** |
| `mock-server/server.ts` / `mock-server/fixtures.ts` | 加一首「**`moov` 在文件尾**的 MP4」（**按实例注入**，共享 fixtures 一条不改）；`track/stream` 对它返回该 MP4（`content-type: audio/mp4`） |
| `test/t126-mp4-tail-lyrics.test.ts`（新） | **6 条钉子** |
| `e2e/t126-mp4-tail-lyric.spec.ts`（新） | 真 Electron：**尾读** ⇒ 内嵌歌词出现 ＋ 来源如实显示 |

### ⚠ 关键取舍

- ⚠ **尾段里不能走顶层原子表**：尾段是从文件中间**截断**的，第一个字节多半在某个原子的**载荷中间** ⇒ 只能**按签名找** ＋ **大小自洽校验**（`size < 8` 不是原子头；`size == 0` ＝ 延伸到文件尾；否则必须**完整落在尾段里**）。
- ⚠ **从尾往头扫**：真正的 `moov`（在文件尾时）通常是**最后一个**顶层原子 ⇒ 音频数据里的同名字节更靠前 ⇒ 先命中的是**更可能真的**那个。
- ⚠ **尾窗口 64 KB 不够时**（`complete === false`）：用 `Content-Range` 的**总长度**换算 `moov` 的**绝对偏移**后**整读** ⇒ **不必加大窗口**。
- ⚠ **只对 MP4 补读**：别的容器头读就够 ⇒ 不白花请求（钉子 ⑥）。
- ⚠ **不扩大头窗口**：64 KB 是既有契约；「续读 `moov`」比「把头读到 1 MB」更省。
