# T96 规格：「发现」页 —— 音乐榜单 + 为你推荐

> 一句话：给客户端加一个**「发现」页**，两块内容——
> **音乐榜单**（QQ 音乐公开榜单，条目**匹配回你 NAS 里的曲库**，命中的才能播）与
> **为你推荐**（基于**你自己**的收藏 / 播放记录**自算**，**每条都在库、都能播**）。

---

## 零、不变量（先钉死，后文都按它写）

> **曲库 = 当前登录用户自己的 NAS 曲库。**
> 它有多大、装了什么、是谁的，**因人而异**。

- 客户端**不内置任何曲库数据**：榜单是**公共**的，曲库是**私人**的。
- 客户端**不对曲库规模做任何假设**：
  - 代码里**不写死**「17.3 万首」这类数字；
  - 也不用「我这台机的库有 17 万首」去推「那可以拉全量」。
    （开发机实测 17.3 万首，那只是**这台机、这个账号**的事实，**不是产品规格**。）
- **绝不拉全量曲库**：一律**定向查询**（按歌手 / 按专辑）。
  定向查询对**任何规模**的曲库都成立——小库也快、大库不炸，且**不依赖规模假设**。
- 「在不在曲库」「命中率」「为你推荐」**一律按当前用户的 NAS 实时算**：
  换一个人、换一个 NAS，结果就不同 —— 这是**特性**，不是 bug。
- 文档里出现的实测数字（曲库规模、命中率）**必须标注是哪台机 / 哪个账号**的实测值。

## 二、事实基线（**本轮实测**，不是推测）

### 2.1 外部榜单接口探测（`release/verify/t96-01-probe-chart-endpoints.mjs`）

| 源 | 实测 |
|---|---|
| **QQ 音乐** | ✅ **200 + 真实榜单条目** |
| 网易云 | ❌ `music.163.com/api/top/list` 等 → body `{"code":404,"message":"接口未找到！"}` ⇒ **web 端点已下线**（其**歌词**端点仍好） |
| 酷狗 | ⚠️ `/api/v5/rank/top` → 404；`/api/v3/rank/song` → 「参数不合法」⇒ **参数名待探** |
| 酷我 | ⚠️ `www.kuwo.cn/api/www/chart/kuwo` → 「The request is illegal!」⇒ **缺 `kw_token`** |
| 咪咕 | ❌ 本机 node/curl **TLS 握手失败** ⇒ 需在应用内 Chromium 栈复验 |

### 2.2 QQ 榜单的**真实形状**（`release/verify/t96-02-probe-qq-chart-shape.mjs` / `t96-03-probe-qq-boards.mjs`）

- 端点：`https://c.y.qq.com/v8/fcg-bin/fcg_v8_toplist_cp.fcg?topid=<id>&format=json&page=detail&type=top&song_begin=0&song_num=<n>`
- 必须带头：**UA** + **`Referer: https://y.qq.com/`**（实测带了就通）
- 响应是**扁平**结构（**不在 `data` 下**）：`{ code, songlist, topinfo, total_song_num, … }`
- `code=0` 表示成功；`topinfo.ListName` = 榜单名（**自描述**）
- `songlist[]` 每条 = **榜单专属字段 + `data`（真正的歌）**：
  `data` 的字段名是 **`songname`**（不是 `title`/`name`）、**`singer: [{ id, mid, name }]`**、**`albumname`**、**`interval`（秒）**、`songid`、`songmid`
  ⇒ ⚠️ **写 `title` / `name` 会静默拿到 `undefined`**（第一版探针就踩了）
- ⚠️ **没有「榜单列表」接口**（`page=list` → `code=-1, subcode=400`）⇒ **榜单目录必须在客户端写死**
- 实测出的 `topid ↔ 榜单名`（37 个）见 §四；本轮默认取 4 个：**热歌(26) / 飙升(62) / 新歌(27) / 内地(5)**

### 2.3 数据的真实形状（**直接决定推荐算法**）

| 数据 | 形状 | 结论 |
|---|---|---|
| 服务端 `play-history/list` | total 实测 **414~426**；条目 = 完整歌曲对象；**没有播放时间字段**；**返回顺序不是按时间戳**；**不随本机播放增长**（服务端无「上报播放」端点） | 只能当**曲目池** |
| 本地 `localStorage` 历史 | 上限 **100** 条，最新在前，同一首**不重复占位**，**无时间戳** | 只能当「最近听过的 100 首」；**没有播放次数** |
| 收藏 `favorite-track/list` | **全量** | 强信号 |
| 曲库 `track/list` | 分页；渲染层 `libraryStore` 明确「**没有取全量的入口**」 | ⇒ **不拉全量**，一律**定向查询**（见 §六） |
| `SessionManager.request(path, …)` | 主进程**通用**带凭证请求 | 主进程**不碰曲库**（曲库查询全在渲染层走 `fnm://srv`，与既有曲库页一致） |

⚠️ **两边都没有「播放次数」** ⇒ 本轮**不做**「按播放次数排的热歌榜」（那是待实测点，本轮不碰）。

⚠️ 上面「414~426 / 100 / 17.3 万」这类数字都是**开发机 + demo 账号**的实测值，
**不是协议保证** ⇒ 代码里**不许**拿它们当阈值或上限。

## 三、数据模型（`shared/chartTypes.ts`，**纯类型**）

分两层：**主进程只回「原始榜单」**，**渲染层再匹配出「命中标记」**。

```ts
/** 榜单里的一条（榜源原始信息，还没跟你的曲库对过）。 */
export interface ChartEntry {
  rank: number          // 排名（1 起）
  title: string         // 歌名
  artist: string        // 歌手（多歌手用 ' / ' 连接，展示用）
  album: string         // 专辑（榜源不给 ⇒ ''）
  duration: number | null  // 时长（**秒**；榜源不给 ⇒ null）
}

/** 一个榜单。 */
export interface ChartBoard {
  id: string            // 如 'qq-26'
  name: string          // 如 '巅峰榜·热歌'
  source: string        // 数据源 id（如 'qq'）
  entries: ChartEntry[]
}

/** 榜单拉取结果（主进程 → 渲染进程）。 */
export interface ChartResult {
  status: 'ok' | 'error'
  message?: string        // 失败原因（可读中文，不含凭证）
  boards: ChartBoard[]
}

/** 榜单条目 + **与你的曲库对过之后**的结果（渲染层产物）。 */
export interface MatchedChartEntry extends ChartEntry {
  inLibrary: boolean    // 在**你的**曲库里
  song: Song | null     // 命中时的本地歌曲（能直接播）；未命中 ⇒ null
}

/** 一个已匹配的榜单。 */
export interface MatchedChartBoard {
  id: string
  name: string
  source: string
  entries: MatchedChartEntry[]
  matched: number        // 命中条数（**你的**曲库命中数）
  total: number          // 条目总数
}
```

⚠️ `ChartResult` 里**没有** `libraryStatus`：匹配发生在渲染层，**匹配不到**与**查不了**是两种状态，
由渲染层自己的 `discoverStore` 区分（见 §六 6.1）。

## 四、归一化与匹配（`shared/chartMatch.ts`，**纯函数**）

### 4.1 归一化规则（`normalizeText`）

| 步骤 | 做什么 | 为什么 |
|---|---|---|
| 1 | `String.prototype.normalize('NFKC')` | 全角 → 半角（「（」与「(」等价） |
| 2 | **去掉所有空白** | 本地多歌手用 `' / '` 连接、QQ 用 `/` ⇒ 去空白后两边一致 |
| 3 | 去掉常见标点（中英文逗号/句号/顿号/连字符/引号…） | 「歌曲名，歌手」与「歌曲名 歌手」等价 |
| 4 | 英文转小写 | 大小写差异 |
| 5 | **保留括号内的内容** | ⚠️ 去掉括号会让 Live 版匹配到录音室版 ⇒ **宁可漏匹配，不可误匹配** |

### 4.2 匹配判据（**在给定的候选歌里找**）

⚠️ **不建全量索引** ⇒ 候选歌是**定向查来的**（某个歌手在**你的**曲库里的歌）。

1. **歌名**必须归一化后**完全相等**（不做包含 / 前缀匹配 ⇒ 宁可漏匹配）。
2. **歌手**必须有**至少一个候选**归一化后相等
   （榜源给的是歌手数组；本地 `Song.artist` 是 `' / '` 连接的多歌手串 ⇒ 两边都拆成候选再比）。
3. **时长闸**：
   - 两侧都有时长 ⇒ 只认 `|Δ| ≤ 3 秒`（沿用歌词源 `DURATION_TOLERANCE_SECONDS = 3` 的先例）的那条；多条则取**时长差最小**的；
   - 本地候选**都没有时长** ⇒ 时长闸用不上 ⇒ 取第一条；
   - 本地候选**都有时长但一首都对不上** ⇒ **不匹配**
     （⚠️ **宁可漏匹配，不可误匹配** —— 宁可显示「不在曲库」，也不能让用户点开是另一首歌）。

**总原则：宁可漏匹配，不可误匹配。**

### 4.3 榜单目录（客户端写死，`topid ↔ 名称`）

实测 37 个，本轮**只用 4 个**（通用性最强）：

| topid | 榜单名 | total |
|---|---|---|
| 26 | 巅峰榜·热歌 | 300 |
| 62 | 飙升榜 | 100 |
| 27 | 巅峰榜·新歌 | 100 |
| 5 | 巅峰榜·内地 | 100 |

（其余实测到的 id 一并记在 `electron/chartProvider.ts` 的注释里，**加源/加榜不改结构**。）

## 五、主进程（`electron/`）

### 5.1 `electron/chartProvider.ts`

- `ChartSource` 接口：`{ id, boards(): BoardDef[], fetchBoard(def, fetchImpl, timeoutMs): Promise<ChartBoard> }`
- **QQ 适配器**：
  - URL 模板见 §二；头：UA + `Referer: https://y.qq.com/`
  - 超时 **8 秒**（`AbortController`）
  - 解析：`code !== 0` ⇒ 失败；`songlist[]` → 每条读 `data.songname` / `data.singer[].name` / `data.albumname` / `data.interval`
  - **缺字段不抛异常**：缺 `songname` 的条目**跳过**（名次按原始下标 + 1，不前移），不伪造
- 缓存：成功结果 **5 分钟**；失败**不缓存**（下次重试能立刻恢复）
- 返回 `ChartResult`（`status` / `message`），**永不抛**，失败也要给可读中文
- ⚠️ **榜源地址可被 `FNM_CHART_URL` 覆盖**（**测试 / E2E / 自建镜像**用）：
  - 只接受 `https`，或 `http` + **回环地址**（`127.0.0.1` / `::1`）⇒ 其余一律忽略并回落默认；
  - 渲染层**永远不许**指定地址（与歌词源 `lyric:fetch` 同一条纪律）。
- ⚠️ **榜源两条通道**（2026-11-16 E2E 实测出来的）：
  - **默认榜源（QQ，https）走 Chromium 分区栈**（`http.fetch`）——干净、不带 NAS 凭证，
    而且**走系统代理**（本机外网只能经代理出去，Node 的 undici 不认代理环境变量）；
  - **覆盖地址走 Node 的 fetch** —— 实测本应用的 Chromium 分区栈**全局拦 http 明文**
    （`net::ERR_BLOCKED_BY_CLIENT`）⇒ 自建镜像 / E2E 的 http mock 只能走 Node。

### 5.2 IPC 契约

| 通道 | 方向 | 载荷 |
|---|---|---|
| `discover:charts` | 渲染 → 主（`invoke`） | 无入参 ⇒ 返回 `ChartResult` |

- 主进程负责**抓榜**（带 UA / Referer / 超时 / 缓存），**不碰曲库**；
- 匹配与推荐在**渲染层**做（那里才有当前账号的曲库访问权）。
- 渲染层**不许**指定要抓哪个地址。

## 六、渲染层（`src/`）

### 6.1 `src/api/discover.ts`（定向查询 + 匹配 + 推荐）

#### (a) 榜单匹配（**定向查询**）

```
输入：boards = 主进程回传的原始榜单
步骤：
  1. 收集所有榜单条目里的歌手名（去重、归一化）
  2. 对每个歌手：
       /search/artist?q=<歌手名>      → 取**归一化后全等**的那个歌手（宁可漏，不可错配）
       /track/artist-detail/list?artistGUID=<id>  → 该歌手在**你的**曲库里的歌
  3. 对每条榜单条目：在**该条目歌手**对应的候选歌里跑 §四 的匹配判据
输出：MatchedChartBoard[]（含 matched / total）
```

- ⚠️ **不拉全量曲库**（§零）：每个歌手 **2 个请求**，且**按需并发**（限流 6 路）。
- ⚠️ **查不到歌手 ≠ 出错**：查得到但**没有这个歌手** ⇒ 该条目就是「不在曲库」；
  **请求本身失败** ⇒ 整块标「暂时无法匹配曲库」（**不许**说成「都不在曲库」）。

#### (b) 为你推荐（**纯函数**，可单测）

```
输入：
  seeds      = 收藏 ∪ 本地历史 ∪ 服务端历史   （全部来自**你的** NAS / 本机）
  candidates = 由种子定向扩展出来的候选歌：
                 同歌手的其他歌  → /track/artist-detail/list
                 同专辑的其他歌  → /track/album-detail/list
  exclude    = 本地历史里的歌（刚听过的别推）

打分（origin × via）：
  收藏   × 歌手 3.0   收藏   × 专辑 1.5
  本地历史 × 歌手 2.5  本地历史 × 专辑 1.0
  服务端历史 × 歌手 1.8 服务端历史 × 专辑 0.8

三块（每块 ≤ 10 条）：
  块1「因为你收藏了 X」  = origin = 收藏 的候选
  块2「因为你最近听了 X」= origin = 本地/服务端历史 的候选
  块3「同一位歌手的其他歌」= 因歌手扩展但前两块没展示完的剩余曲目

全局规则：
  − 跨块去重（先到先得）
  − 排除本地历史里的歌
  − 每条附**可读理由**（如「因为你收藏了 云旗」）
  − 某块无内容 ⇒ **该块不显示**（不留空壳）
```

⚠️ **没有「曲库里的新面孔」块**：那需要**全量曲库**（§零）⇒ 本轮**不做**。

### 6.2 `src/state/discoverStore.ts`

- 榜单：加载中 / 成功 / 失败（榜源失败）/ **匹配失败**（NAS 查不动 ⇒ 说「暂时无法匹配曲库」）
- 推荐：加载中 / 成功 / 失败
- 「重试」动作

### 6.3 `src/pages/DiscoverPage.tsx`

- 两个 Tab：「榜单」/「为你推荐」
- 榜单 Tab：左侧榜单切换（4 个），右侧条目列表（排名 + 歌名 + 歌手 + 「在曲库 / 不在曲库」标记）
  - 命中条目 → **可点播放**（用本地 `songId` 走既有 `playerStore` ⇒ NAS `track/stream`，**不新增播放路径**）
  - 未命中 → **不可播**、灰显 + 标「不在曲库」
  - 顶部显示命中率：「榜上 N 首，**你的**曲库里有 M 首」
- 推荐 Tab：三块，每块一个小标题 + 条目列表；每条带推荐理由
- 空态 / 错误态 / 重试按钮（照 `LibraryPageShell` 的既有形状）

### 6.4 `src/App.tsx`

- `MainView` 加 `'discover'`；顶栏主导航加「发现」按钮（与「搜索」并列）；`renderMainView` 加分支

## 七、降级矩阵（**失败不许白屏，也不许说假话**）

| 故障 | 榜单区 | 推荐区 |
|---|---|---|
| 外部源超时 / 失败 | 显示可读错误 + 「重试」 | **照常可用** |
| 曲库定向查询失败 | 显示「暂时无法匹配曲库」（**不把全部标成「不在曲库」**） | 显示「暂时无法加载」+ 重试 |
| NAS 不可达 | 同上 | 同上 |
| 本地历史为空 | 正常 | 只显示「收藏扩展」，不报错 |
| 服务端历史为空 | 正常 | 正常（种子少 ⇒ 结果少，但**不报错**） |
| 曲库很小 / 只有一个歌手 | 正常 | 正常（**不假设规模**） |

## 九、验收点

**A 功能**：A1 榜单 ≥ 20 条且含排名/歌名/歌手；A2 命中条目**可播**（进度条走起来）、未命中不可播且标「不在曲库」；A3 显示命中率（**按当前用户的曲库**算）；A4 推荐每条都能播、不含本地历史里的歌、跨块不重复；A5 三块各自成立、某块空则不显示；A6 每条带可读理由。

**B 降级**：B1 外部源失败 ⇒ 榜单区报错 + 重试，**推荐区照常**；B2 NAS 不可达 ⇒ 两块都报错不白屏；B3 曲库查不动 ⇒ 说「暂时无法匹配曲库」**而不是**「都不在曲库」；B4 本地历史为空 ⇒ 推荐降级不报错。

**C 测试**：C1 新增单测 ≥ 30 条（匹配 ≥ 12 / 适配器 ≥ 8 / 推荐 ≥ 12）；C2 既有 **2684** 条一条不删、断言一条不弱化；C3 `tsc --noEmit` 0 error；C4 vitest 全绿 + playwright 全绿（新增 1 条 E2E）；C5 字节体检 + 控制字符扫描 0 bad；C6 **变异自证**三条（匹配判据改回⇒红／去掉「排除本地历史」⇒红／还原⇒绿）。

**D 性能**：D1 榜单首载 ≤ 3 秒、缓存命中 ≤ 200 毫秒；D2 **定向查询**（每歌手 2 个请求）并发限流 6 路；D3 来回切页不重复拉。

**E 记录**：E1 `docs/calibration.md` 记各源实测状态 + QQ 字段名 + topid↔榜单名；**命中率只在本机账号下记录，并标注「本机（demo 账号）实测」**；E2 台账回填 T96 段；E3 真机复验（隔离 userData + 真实 NAS + 真实 QQ 源）覆盖「榜单命中项可播」「推荐项可播」。

## 十、明确不做

- ❌ **不做**「按播放次数排的热歌榜」（服务端历史**没有**时间戳与次数 ⇒ 名不副实 ⇒ 本轮不做）
- ❌ **不做**「每日推荐 / 个性化推荐歌单」（需要用户账号 cookie ⇒ 不做）
- ❌ **不做**「曲库里的新面孔」（需要**全量曲库** ⇒ 与 §零 冲突 ⇒ 本轮不做）
- ❌ **不接**除 QQ 外的外部榜源（实测不可用；架构留好接口，以后实测通了再加）
- ❌ **不改**「线上优先」等既有政策；**不新增**播放路径（命中项走既有 `playerStore`）
- ❌ **不引**新 npm 依赖
- ❌ **不把曲库规模 / 命中率写死**进代码或文档（曲库因人而异 ⇒ 一律运行时算）
