# T97 规格：「随机 20 首」组一个歌单 —— 从**你自己的** NAS 曲库随机挑 20 首，能存回 NAS

> 状态：**规格先行**（实现前定稿）。
> 起草：2026-11-16。
> 前置任务：T96（「发现」页：榜单 + 为你推荐）。

---

## 零、不变量（**先写死，后面所有设计都受它约束**）

1. **曲库 = 当前登录用户自己的 NAS 曲库**，规模与内容**因人而异**。
   ⇒ 本功能**不假设曲库有多大**（不写死「17 万首」这类数字），
   一切规模相关的量（总曲数、页数）**运行时算**。
2. **不拉全量曲库**：只取**随机若干页**（默认 4 页 × 200 首），再在页内随机挑。
3. **客户端不新增 npm 依赖**；既有测试**一条不许删、断言一条不许弱化**。
4. **不新增播放路径**：随机歌单里的歌**走既有 `playerStore` 播放路径**
   （`onPlay(song, index, list)` 整队口径 ⇒ NAS `track/stream`）。
5. **服务端行为不写死成契约**：一切「服务端怎么分页 / 认不认某个参数」的结论
   都标注「实测（哪台机、哪个账号、何时）」，并把**实测到的限制**显式处理
   （见 §2.2 的页码上限）。

---

## 一、目标与不做

### 目标

在**歌单页**加一个入口：点一下 ⇒ 从**你的**曲库**随机挑 20 首** ⇒ 组成一个**临时歌单**：

- 能**直接播放**（走既有播放路径）；
- 能**换一批**（再随机一次）；
- 能**存回 NAS**（真建成一个歌单，20 首都在里面）。

### 明确不做

- ❌ 不做「每日推荐歌单」（服务端没有这回事；也不需要账号 cookie）；
- ❌ 不做「按播放次数排的热歌榜」（服务端历史没有次数/时间戳）；
- ❌ 不做「曲库里的新面孔」（需要**全量曲库**，与 §零 第 2 条冲突）；
- ❌ 不动 T96 的「发现」页（它的首载是 29 秒的定向匹配，**另一件事**）；
- ❌ 不改服务端行为（页码上限是**服务端的事实**，客户端只能规避，不能修）。

## 二、探针实测基线（**服务端事实**，2026-11-16，本机 + 该账号）

> 探针脚本：`release/verify/t97-01..04-probe-*.mjs`（gitignored）。
> 手法：隔离 userData（只复制 `session.bin` + `Local State`）+ **真实 NAS** +
> 渲染进程里直发 `fnm://srv/…`。
> ⚠️ 探针输出**只记形状与计数**，不落任何真实歌名 / 标识。

### 2.1 `/track/list`（曲库列表）

| 项 | 实测 |
|---|---|
| 响应形状 | `{ list, sort, total }`（`sort` 是**服务端回显的实际排序**） |
| 曲目标识 | `guid`（32 位 hex）；另有 `title` / `artists` / `album` / `duration` / `coverId` … |
| 默认排序 | `createdAt,desc`（**最新入库在前**） |
| `size` | **生效**；服务端上限 **2000** |
| `page` | **生效**，但**有上限**（见 2.2） |
| `sort` | **只认 `createdAt`（`,asc` / `,desc`）与 `title`（`,asc`）**；`random` / `rand` / `shuffle` / `album` / `duration` / `updatedAt,desc` **一律无效**（回显仍是 `createdAt,desc`） |

### 2.2 ⚠️ 页码上限 **2000**：超了会**静默回绕到第 1 页**

| size | 最后一个好页 | 第一个坏页 | 坏页的表现 |
|---|---|---|---|
| 10 | **2000** | 2001 | **回绕到第 1 页**（内容与 page=1 完全相同，**不是空页**） |
| 50 | **2000** | 2001 | 同上 |
| 200 | 869（= 该 size 下的真实末页） | 870 | **空页**（正常越界） |

⇒ **上限是「页码 ≤ 2000」，不是 offset 上限**（size 变、页码上限不变）。

⇒ **对抽样的直接影响**：页码 **必须 clamp 到 ≤ 2000**，否则会抽到回绕页
⇒ 抽出来的 20 首**全是同一批**（探针 ① 就是这么撞上的：三页 30 个 guid 去重后只剩 10 个）。

⇒ **顺带暴露的既有缺陷（不在本任务范围，另记）**：曲库 17.3 万首、默认 `size=50`
⇒ 3473 页 ⇒ 现有「歌曲」页翻到**第 2001 页后会重复第一页**。
（客户端 `libraryApi.songs()` 没有 clamp ⇒ 这是**另一个任务**的活。）

### 2.3 抽样覆盖范围怎么算（**不写死规模**）

`size = 200` ⇒ 总页数 = `ceil(total / 200)`。
以本机（`total = 173671`）为例 = 869 页 **< 2000** ⇒ **全库每一页都翻得到** ⇒
抽样可以覆盖**整个曲库**。

⚠️ 若某人的库大到 `ceil(total / 200) > 2000`（即 total > 40 万），
则**只有前 2000 页**（40 万首）能被翻到 ⇒ 抽样范围就是那部分 ⇒
**如实说明**（见 §4.4），**不假装覆盖了全库**。

### 2.4 歌单写回（`playlist/*`）

| 端点 | 实测 |
|---|---|
| `GET /playlist/list` | `{ list, total }`；该账号当前 **0 个歌单** |
| `POST /playlist/create` | `{ name }` ⇒ **回显 `guid`**（32 位 hex）⇒ 客户端「返回形状未实测」那条**现在有答案了** |
| `POST /playlist/add-track` | `{ guid, trackGUIDs[] }` ⇒ code 0 ⇒ **真的写进去了**（`/track/playlist-detail/list` 的 total 变成 2） |
| `GET /track/playlist-detail/list` | `{ list, total }` ✓ |
| `POST /playlist/delete` | `{ guid }` ⇒ code 0 ⇒ 探针自建的歌单**当场删掉**（**真机上可逆**） |

## 三、抽样算法（**纯函数**，可单测）

模块：`src/api/randomPlaylist.ts`

```ts
export const SERVER_MAX_PAGE = 2000        // 实测：页码上限（超了回绕）
export const RANDOM_SAMPLE_PAGE_SIZE = 200  // 每页取多少首（覆盖全库 + 请求体量折中）
export const RANDOM_PLAYLIST_SIZE = 20      // 随机歌单默认条数
export const RANDOM_SAMPLE_MAX_PAGES = 4    // 最多取几页（多样性 ↔ 请求数折中）
```

### 3.1 步骤

1. `total = await deps.total()`（**1 次**请求，`size=1` 即可）；
   `total ≤ 0` ⇒ 直接返回空数组（**不崩、不假装有**）。
2. `totalPages = ceil(total / pageSize)`；
   `usablePages = min(totalPages, SERVER_MAX_PAGE)` ← **§2.2 的 clamp，必须有**。
3. `pagesNeeded = min(usablePages, RANDOM_SAMPLE_MAX_PAGES)`；
   `perPage = ceil(count / pagesNeeded)`；
   若 `perPage > pageSize` ⇒ `pagesNeeded = min(usablePages, ceil(count / pageSize))`，
   再算一次 `perPage`（保证「要多少首就要多少页」，不会少给）。
4. **随机挑 `pagesNeeded` 个互不相同的页码**（范围 `[1, usablePages]`）。
5. 每页取 `pageSize` 首 ⇒ **页内**再随机挑 `perPage` 首（Fisher–Yates，**注入** `random`）。
6. 汇总 ⇒ **按 `id` 去重** ⇒ 整体再洗一次 ⇒ 取前 `count` 首。
7. **不足 `count` 就如实少给**（库就这么大 ⇒ 就给这么多，**不拿重复的凑数**）。

### 3.2 为什么这样切

- **为什么要分页随机、而不是一次要 20 首**：服务端**没有随机排序**
  （§2.1）⇒ 随机只能客户端做；而一次请求拿 20 首只能拿到**同一页的连续 20 首**
  （相邻 ⇒ 导入时间挨着 ⇒ 多样性差）。
- **为什么每页 200 首、页内再抽**：一页 200 首 ⇒ 页内随机 5 首 ⇒ 20 首来自
  **4 个随机位置**（分散在整个库的不同角落），且每页只传 200 首的元数据
  （中继链路上 ~60 KB/页 ⇒ 4 页 ≈ 240 KB，实测每页 175–320 ms）。
- **为什么页数封顶 4**：再多就只是白花请求与带宽（实测每页 175–320 ms）；
  4 页 × 200 = 800 首候选 ⇒ 抽 20 首，重复概率可忽略。

### 3.3 可测性

- `deps` 可注入（`total` / `page`）⇒ 单测不必打网络；
- `random` 可注入 ⇒ **结果可复现**（用固定序列的假随机）；
- `count` / `pageSize` 可注入 ⇒ 边界好写。

## 四、交互与落点

### 4.1 落点：**歌单页**（`src/pages/PlaylistsPage.tsx`）

**为什么不是「发现」页**：T96 的发现页一进去就要跑榜单定向匹配
（**真机实测冷首载 29.1 秒**，见 `docs/calibration.md` 六十三）
⇒ 用户想用随机歌单，也得先等 29 秒 ⇒ 不合理。

**为什么是歌单页**：这个功能**产出一个歌单** ⇒ 放在歌单页语义最贴；
且歌单页本来就有「新建歌单 + 写回」的现成零件（`playlistApi.create` / `addTracks`）。

### 4.2 交互

```
歌单页左栏顶部
┌──────────────────────────┐
│ [🎲 随机 20 首]            │   ← 按钮（未生成时只有它）
│ 从你的曲库随机挑 20 首     │
└──────────────────────────┘
点它 ⇒ 右栏切到「随机歌单」视图
┌────────────────────────────────────────┐
│ 随机 20 首        [播放全部] [换一批]    │
│ [存为歌单: (随机歌单 11-16 19:12) ▾][存] │
│ ─────────────────────────────────────── │
│ 1. ……                                  │
│ 2. ……   ← SongList（复用既有组件）      │
│ …                                      │
└────────────────────────────────────────┘
```

- **播放全部** ⇒ `onPlay(songs[0], 0, songs)`（**整队 = 这 20 首**）
  ⇒ 走既有 `playerStore` 播放路径（**不新增**）；
- **换一批** ⇒ 再抽样一次（页码/页内都重新随机 ⇒ **每次都是不同的一批**）；
- **存为歌单** ⇒ `playlistApi.create(name)` → `playlistApi.addTracks(guid, ids)`
  ⇒ 成功后**刷新歌单列表并选中新歌单**（用户立刻能在左栏看到它）。
- **错误分开说**：抽样失败 ⇒「随机失败：…」；存回失败 ⇒「存为歌单失败：…」
  （**不假装成功**）。

### 4.3 组件

`src/components/RandomPlaylistPanel.tsx`（新增，**独立组件** ⇒ 可单测）：

| prop | 作用 |
|---|---|
| `deps` | 抽样依赖（测试注入） |
| `save` | 存回歌单（测试注入；生产走 `playlistApi`） |
| `onPlay` | 播放回调（整队口径） |
| `onSaved` | 存回成功后回调（歌单页据此刷新列表并选中） |

### 4.4 ⚠️ 覆盖范围要**如实说明**

抽样范围 = `min(ceil(total/pageSize), 2000)` 页。
若该值 < `ceil(total/pageSize)` ⇒ **只有前 2000 页**能被抽到 ⇒
界面**如实说明**「随机范围：最近入库的 N 首」之类的口径，
**不假装是全库随机**。

## 七、遗留（本轮**不做**，如实记）

- ⚠️ **页码上限 2000 的连带影响**：现有曲库分页（`libraryApi.songs`）**没有 clamp**
  ⇒ 大库的「加载更多」翻过 2000 页会**重复第一页** ⇒ **另开任务**修；
- ⚠️ 抽样**不是全库均匀随机**（服务端没有随机排序；且最多只能翻到前 2000 页）；
- ⚠️ 「存为歌单」在**中继**链路上要发一次 `create` + 一次 `add-track`（20 个 id）
  ⇒ 实测耗时待真机复验记录；
- ⚠️ 随机歌单**不写回本地历史**（它不是「听过」）；
- ⚠️ 外部卡点（用户明确不做）：GitHub 2FA、改已泄露口令、NAS 口令轮换。
