# T67 设计规格：接网易云 yrc 真逐字歌词

## 1. 起因

用户在用 Lyricify Fusion 对比后指出「**比不上 Lyricify，那个准**」。这是实情，差距有明确的
三层：

| 差距 | Lyricify Fusion | 我们（此前） |
|---|---|---|
| ① **逐字时间戳** | 真逐字（Spotify enhanced / 网易云 yrc / QQ qrc） | **行级 LRC + 音节推算的伪逐字** ← **根本差距** |
| ② 手动校准 | 偏移滑块 + 快捷键 | 无手动控件（T66 明确不做） |
| ③ 本地音频强制对齐 | 机器学习对齐到波形 | 无（要引模型，违背「不引新依赖」） |

第 ① 条是致命的：**行级时间戳推出来的逐字永远对不上嘴**。T66 的音节加权只是让**比例**更合理，
**不是真的对**。

### 1.1 本轮要解决的**具体缺口**（实测，非猜测）

我们在 T32/T33 已经接了网易云（`electron/lyricProvider.ts` 的 `fetchNetease`），但：

- 请求 URL 是 `…/api/song/lyric?id=…&lv=1&kv=1&tv=-1` ⇒ **没有请求 `yv`（逐字）参数**
  ⇒ 网易云**根本不会**把 `yrc` 字段回给我们；
- 响应解析只读 `lrc.lyric` / `tlyric.lyric` ⇒ 即使服务端给了 `yrc` 也会被**丢弃**；
- `looksLikeLrc(original)` 判的是**行级**格式 ⇒ 对「只给 yrc 的歌」会**判成没歌词**。

**实测（2026-11-06，匿名请求，无 Cookie）**：

| 抽样 | 返回的字段组合 | 占比 |
|---|---|---|
| 网易云 30 首 | `klyric + lrc + tlyric`（**只有行级**） | 22/30 |
| 网易云 30 首 | **`yrc`（只给逐字，连 `lrc` 都没有）** | **8/30（27%）** |
| 网易云 10 首（带 `yv=-1`） | `klyric + lrc + tlyric + **yrc**` | 3/10 |
| lrclib 71 条 | **零条带逐字**（全是行级） | 0/71 |

⇒ **两笔收益**：
1. **那 27% 的歌现在被我们判成「没找到」**（明明有歌词）⇒ 接上 yrc 直接有歌；
2. **有 yrc 的歌拿到真逐字** ⇒ 卡拉OK 填色真的跟嘴（这是与 Lyricify 的核心差距）。

### 1.2 目标

- 网易云返回 `yrc` 时，**用真逐字**当原文；
- **`yrc` 优先、缺失时回退 `lrc`**（行为一字不变）；
- **零新增解析分支**：把 yrc 转成**标准增强 LRC**（`<mm:ss.xx>` 逐字标签），
  交给**现有**解析器（`parseWordSegments` 早就在等喂）⇒ **渲染层解析器一字不改**；
- 不引新依赖；不新增出网端点（**同一个 URL**，只多一个查询参数）。

### 1.3 不做什么（范围收窄）

- **不改 `src/ui/lyrics/parse.ts`**：转换器在主进程，输出标准增强 LRC ⇒ 现有解析器直接吃；
- **不接 QQ qrc**（密文解密，成本高、接口更灰）⇒ 另议；
- **不做本地音频强制对齐**（要引模型）；
- **不新增用户手动偏移控件** ⇒ 另议（T68 候选）；
- **不改 lrclib / QQ 适配器**（实测它们不提供逐字）；
- **不碰服务端 NAS 歌词**（那是行级，外部源优先策略已定）。

## 2. 设计

### 2.1 yrc 格式（**实测**，2026-11-06 匿名实测）

```
[行开始ms,行时长ms](词开始ms,词时长ms,0)词文本(词开始ms,词时长ms,0)词文本
[0,1000](0,1000,0)首行词
[6190,4440](6190,2190,0)词(8380,540,0),(8920,360,0)词(9280,1350,0)末词
```

实测要点（全部有据）：

| 事实 | 证据 |
|---|---|
| 字段形状 = `{ version, lyric }`（`lyric` 是文本） | 实测样本 `keys=version,lyric` |
| 行头 = `[行开始ms, 行时长ms]` | 实测 `[6190,4440]` |
| 词元组 = `(词开始ms, 词时长ms, 0)` + **紧跟**的文本（**词之间无分隔符**） | 实测 `(8380,540,0),(8920,360,0)` |
| **词时间是绝对毫秒**（从歌开头算起），**跨行连续递增** | 实测行首序列 `0,1000,6190,11770,17860,23440` 严格递增 |
| 词的开始时间 = 该行行开始（首词） | 实测 `[6190,4440](6190,2190,0)…` |
| **词时长可以为 0**（标点/停顿占位） | 实测 `(22940,0,0),` |
| **行时长 = 末词结束 − 行开始** | 实测 `6190+4440=10630 = 9280+1350` |
| 必须请求 `yv=-1` 才有 `yrc` | A/B 实测：不带 → 无 `yrc`；带 → 有 |

### 2.2 转换器 `yrcToEnhancedLrc(yrc): string`（**纯函数，主进程**）

**输出**：标准增强 LRC ——

```
[mm:ss.xx]<mm:ss.xx>词1<mm:ss.xx>词2<mm:ss.xx>词3
```

**现有解析器直接吃**（`parseEnhancedLrc` → `parseWordSegments`）⇒ **渲染层零改动**。

**算法**（定死）：

1. **逐行**扫描；行头用 `^\[(\d+),(\d+)\]` 取「行开始 ms」；
2. 行内按**顺序扫描**找词元组：只认**形如 `(数字,数字,数字)`** 的元组
   ⇒ **词文本里含 `(` / `)` 也不会错位**（不用贪婪正则）；
3. 每个词 → `<mm:ss.xx>`（词开始 ms）+ 词文本；
4. **零时长词**（`词时长 === 0`，实测是标点/停顿）→ **并入前一个词的文本**，
   不单独成词（与既有 `splitIntoWords` 的标点处理一致）：
   - 没有前词可并 → **丢弃**；
5. **词开始早于行开始**（异常数据）→ **钳到行开始**；
6. 一行里**没有有效词** → **跳过该行**（不产生歌词行）；
7. 空串 / 非串 → 返回空串（**不抛异常**）。

**可断言的不变式**（写进单测）：

| # | 不变式 |
|---|---|
| I-1 | 转换后**行数** === yrc 的有效行数（无有效词的行被跳过） |
| I-2 | 转换后**词时间严格递增**（行内 + 跨行） |
| I-3 | **不丢字**：转换前后「剥掉全部结构字符（`[]()`、数字、逗号、空白）」的文本**逐字相同** |
| I-4 | 零时长词**并入前词**，不单独成词（词数因此可能少于 yrc 的元组数） |
| I-5 | 输出**能被 `looksLikeLrc` 接受**（是标准行级格式） |

### 2.3 网易云适配器改动（`electron/lyricProvider.ts`）

1. **请求加参数**：`…&lv=1&kv=1&tv=-1` → **追加 `&yv=-1`**（同一个 URL，**不新增端点**）；
2. **响应类型加字段**：`NeteaseLyricPayload` 加 `yrc?: { lyric?: unknown }`；
3. **原文优先级**：
   ```
   yrc 非空 → original = yrcToEnhancedLrc(yrc)      ← 真逐字
   否则     → original = lrc.lyric                    ← 行级（**行为一字不变**）
   ```
   - 转换结果**为空**（yrc 畸形）→ **回退 lrc**（不因此丢掉整首歌）；
4. **翻译照旧**：`tlyric.lyric`（行级）。
5. `looksLikeLrc(original)` 判据**不变**（转换输出是标准行级格式，必然通过）。

### 2.4 ⚠️ 实测到的**行时间轴差异**（必须写进规格，不能装作没有）

同一首歌，**yrc 的行开始 ≠ lrc 的行开始**，而**翻译 `tlyric` 对齐的是 lrc**：

```
yrc   行首(ms)：0,   1000, 6190, 11770, 17860, 23440
lrc   行时(ms)：0,   1000, 6220, 11320, 17730, 23170
tlyric 行时(ms)：      6220, 11320, 17730, 23170, 30140
差异：      0,      0,  +30,  +450,  +130,  +270
```

⇒ 用 yrc 当原文时，**翻译的行时间会偏几十到几百毫秒**。现有 `attachTranslations` 的容差是
**0.5s（含边界）** ⇒ 实测差异**多数能挂上**，但临界。

**本轮口径（定死）**：**先不动 `attachTranslations` 的容差**（那是 Task 15/19 定死的语义），
**用 yrc 的真实行时间**（词跟嘴比翻译对齐更重要）。
若真机实测发现翻译大面积失配 → 另开任务做「行时间就近对齐 lrc」（**不改**既有容差语义）。

## 3. 验收点

1. `tsc --noEmit` **exit 0**；
2. `vitest run` **全绿**，用例数**只增不减**（基线 **1892 条 / 86 文件**）；
   **既有断言一条不许删、一条不许削弱**；
3. `yrcToEnhancedLrc` 的 I-1~I-5 全部有单测钉住；
4. **「只有 yrc 没有 lrc」**的响应 → `status: 'ok'`、`original` 含 `<mm:ss.xx>`（**真逐字**）；
5. 请求 URL **带 `yv=-1`**；
6. **没有 yrc 时**行为与本轮之前**一字不变**（仍用 `lrc.lyric`）；
7. **yrc 畸形** → 回退 `lrc`，**不丢掉整首歌**；
8. 端到端：转换产物经 `parseLyricEntries` 后，**某行的词数 > 1**（证明是真逐字，不是伪逐字）；
9. `looksLikeLrc(转换结果)` === true；
10. Playwright E2E **全绿**（`npm run e2e:only`）；
11. 字节级自检：无 U+FFFD、无 NUL、无 BOM；行尾保持原样。

## 4. 风险与待真机校准

| # | 风险 | 现状处理 | 待校准 |
|---|---|---|---|
| 1 | 网易云是**非官方公开 Web 接口**，可能变更或限流 | 失败照旧**如实报错**（既有错误路径） | 用户侧真机复验某首歌是否出现真逐字 |
| 2 | `yv=-1` 会不会让**响应变大**（多带一份 yrc） | 只多取一个字段，**不影响**现有解析 | 实测响应体积 |
| 3 | yrc 与 lrc 的行时间轴不一致 ⇒ **翻译偏** | 先不动容差（§2.4），**词跟嘴优先** | 真机看翻译是否还能挂上 |
| 4 | 某些歌的 yrc **词时长为 0** | 并入前词（I-4） | — |
| 5 | 歌词文本里含 `(` `)` | 顺序扫描 + 只认**数字形状**的元组（§2.2 步骤 2） | — |
| 6 | 网易云限流 | 既有失败缓存（5 分钟）兜底 | — |
