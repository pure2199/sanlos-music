# T87.15 规格：重发 v0.2.5（含 T87.12 修复，**版本号不变**）

> 日期：2026-11-11
> 前置：T87.12（自动更新「安装包名不合法」已修）、T87.11/T87.11-b（未签名 v0.2.5 已发布）

---

## 一、为什么要重发同一个版本号

T87.12 修的是**自动更新跨进程契约错配**：客户端回传**绝对路径**，主进程只接受**文件名**
（`sanitizeFileName()` 含 `/` `\` 一律拒）⇒ 应用里的「启动安装」报**「安装包名不合法」**。

⚠️ **这个缺陷影响的是「任意两个版本之间」的一键更新，不只是 v0.2.5 自己**：

- 公开的 v0.2.5 里带着这段坏代码 ⇒ **v0.2.5 用户将来升不到 v0.2.6**（一键更新必失败）；
- 而 v0.2.5 → v0.2.6 是**下一版唯一的自动升级通道**（不 bump 版本号 ⇒ 用户拿不到修复版）。

⇒ 所以必须在发 v0.2.6 **之前**，让公开的 v0.2.5 本身是好的。

**为什么不改版本号**：用户拍板「不改版本号就行」。理由成立：

- 版本号是**客户端同源判断**的依据（`latest.json.version`），改号会让「已是最新」判断与公开清单错位；
- `v0.2.5` 这个号**从未被一个「修好的」版本占用过** ⇒ 重新发布它不是「同号不同物」的欺骗，
  而是「补发一个还没发出去的修复版」；
- 未来 v0.2.6 仍然可以正常发，序号没有被占掉。

## 二、硬前提（缺一不可）

### 前提 1：必须移动 tag `v0.2.5`

`.github/workflows/release.yml` 的 Checkout 步骤是：

```yaml
with:
  ref: ${{ inputs.tag }}
```

⇒ **CI 构建的就是 tag 指向的那个 commit**，不是默认分支。

而 tag `v0.2.5` 当前指向 `d5b7a21`（**不含** T87.12 修复），HEAD `f0b0f12` 才含。

⇒ 要重发含修复的产物，**必须把 tag force 移到含修复的 commit**。

⚠️ 为什么**移动 tag**而不是改 workflow 的 checkout ref：tag 与被构建的代码**必须一致**，
否则「发布的产物」与「公开可查的源码」对不上 —— 对 SignPath 的「可信构建」前提尤其致命
（签名是基于某个 commit 做的，产物必须能从那个 commit 复现）。

⚠️ 副作用（已知并接受）：已下载过原版 v0.2.5 的用户，手里的包与新哈希不符 ⇒ 文档必须写清楚。

### 前提 2：发布前必须先清掉仓库文档里的旧哈希

`release.yml` 的 `Prepare release notes with checksums` 步骤：

1. 读 `docs/releases/${{ inputs.tag }}.md`（**原样**作为说明正文）；
2. 末尾**追加**一节 `## 下载校验（sha256）`，内容由**本次发布的实际字节**算出。

⇒ 若仓库文档里留着**原版**的 sha256 表，Release 页面上就会出现**两份哈希表，其中一份是错的**
⇒ 这正是「先发布、再回填」纪律要防的事：**带旧数字上页面 = 发错数据**。

**处置**（沿用既定口径）：仓库副本**不重复**列哈希表，只留一句指引指向页面末尾那节
（权威值永远是 CI 按实际字节算出来的那份）⇒ 仓库文档从此**不含任何会过期的数字**。

## 四、执行顺序（**顺序不可换**）

1. 写本规格 → **commit 1**（规格先行）；
2. 改 `docs/releases/v0.2.5.md` + `docs/changelog.md` → **commit 2**（实现）；
3. **force 移动 tag** `v0.2.5` → 新 commit → `git push --force origin v0.2.5`；
4. 触发 `Release` 工作流：`tag=v0.2.5`、`pack_only=false`、`sign=false`
   （走**未签名分支**：`fn-check-signature.mjs --expect none` 断言产物确实没签名）；
5. 核对产物与页面；
6. 回填（若需要）→ commit 3 → push。**回填不动 tag**（tag 指向的是「被构建的那份代码」）。

⚠️ 第 3 步是**外部可见且不可逆**的操作 ⇒ 执行前必须已获用户明确同意（本次已同意）。
