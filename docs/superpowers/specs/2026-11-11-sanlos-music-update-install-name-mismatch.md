# T87.12 规格：自动更新「安装包名不合法」—— 渲染层回传了**路径**，主进程要的是**文件名**

> 日期：2026-11-11
> 状态：规格先行（实现另开一个 commit）
> 触发：用户真机复验 v0.2.4 → 点「启动安装」⇒ 红框 **「安装包名不合法」**

---

## 1. 现象（用户真机，截图）

- 当前版本 **v0.2.4**，更新源 = 项目 Releases；
- 「检查更新」⇒ 发现 **0.2.5**（提示「本版未做代码签名」）；
- 「下载更新」⇒ **成功**（82.1 MB，正是 v0.2.5 的 Setup），界面明确写着
  「安装包没有代码签名（**已按你的授权放行**）；主进程仍会核对 SHA-512」；
- 点「启动安装」⇒ 红框：**安装包名不合法** ⇒ **一键更新彻底走不通**。

⚠️ 注意：失败发生在**授权已放行、下载已成功**之后 ⇒
**签名闸与 SHA-512 复核都还没轮到执行**，就被更前面的一道检查挡下来了。

---

## 2. 根因（**代码坐实**，不是推断）

**契约错配**：`update:install` 这条 IPC 的参数**从头到尾都是「裸文件名」**，
而渲染层回传的是主进程给的**绝对路径**。

| # | 环节 | 位置 | 事实 |
|---|---|---|---|
| ① | 渲染层发起 | `src/state/updateStore.ts:264` | `bridge.installUpdate(download.path)` ⇒ 传的是**绝对路径** |
| ② | preload 透传 | `electron/preload.ts:229` | `ipcRenderer.invoke('update:install', { name })` ⇒ 参数**叫 name** |
| ③ | 主进程入口 | `electron/ipc.ts:1493` | `const name = readString(...)` ⇒ 仍按**名字**理解 |
| ④ | 主进程校验 | `electron/update.ts:802` | `sanitizeFileName(name)` |
| ⑤ | **炸点** | `electron/update.ts:154` | `if (/[\\/]/.test(text)) return null` ⇒ **含 `\` 的绝对路径一律判非法** |
| ⑥ | 报错 | `electron/update.ts:804` | `'安装包名不合法'` ⇒ 与截图**逐字一致** |

⇒ **同一条链上 `download` 传的是名字**（`updateStore.ts:226` → `bridge.downloadUpdate(result.file.name)`），
**唯独 `install` 传了路径** ⇒ 纯契约错配，不是安全闸在拦截。

### 旁证：`isInsideDir` 是**死代码**

`electron/update.ts:808` 有一次「拼出来的路径必须仍在下载目录里」的二次确认，
但它前面刚把输入压成了**裸名** ⇒ `join(destDir, safe)` **必然**在目录内
⇒ 这道防线从来不可能触发 ⇒ **两处校验互相矛盾**（一个要裸名、一个防路径穿越）。

## 3. 为什么一直没被发现（**测试缺口**，不是运气）

| # | 缺口 | 后果 |
|---|---|---|
| ① | `test/update-store.test.ts:93` 的假桥**只记录参数、从不跑主进程那套校验** | 而且它把「传路径」当**正确行为**钉死了 ⇒ 反向锁死了 bug |
| ② | **`createUpdateController` 一条测试都没有** | 「check → download → install」的编排整段**零覆盖**（bug 就住在这段） |
| ③ | e2e 只走到「签名不过 ⇒ 按钮禁用」，**没点过「启动安装」** | 真机链路从未被端到端跑过 |
| ④ | 真机复验一直挂着 | `docs/calibration.md` 里明写「**待用户复验**」⇒ 一直没验 |

⇒ **教训**：**假桥只验证「调用发生了」，不验证「参数对不对」**；
⇒ 跨进程契约（渲染层 ↔ 主进程）必须有**一端带真实校验**的测试。

---

## 4. 修法：**改渲染层这一端**（主进程的安全边界一字不动）

> 决策：**主进程把落盘用的「安全文件名」随下载结果一起返回，渲染层原样回传。**

| 为什么这么改 | 依据 |
|---|---|
| 主进程是**唯一真相源** | 名字由主进程自己产生并回传 ⇒ 渲染层不需要「知道」文件系统 |
| 渲染层「**碰不到文件系统**」的既有边界不能破 | 现在它把主进程给的绝对路径**再传回去** ⇒ 等于让渲染层处理路径 |
| **路径穿越防线一字不动** | 主进程**仍然只收裸名**（含 `/` `\` 一律拒）⇒ 防线比「改成接受路径」更严 |
| 契约**对称** | `download(name)` 与 `install(name)` 用**同一个 token** |

### 明确**不做**的事

- ❌ 不把主进程改成「接受路径再取 basename」—— 那会放松「只收裸名」这条刻意的硬契约；
- ❌ 不在渲染层自己算 `basename()` —— 渲染层不许碰路径；
- ❌ 不动 SHA-512 复核、签名闸、`isInsideDir` 三道闸的任何一条。

## 7. 边界与遗留

- ⚠️ **这个 bug 在已发布的 0.2.4 与 0.2.5 里都有** ⇒
  用户要立刻装上 v0.2.5，**仍需手动下载安装包**（本修复要等**含它的下一个版本**）；
- ⚠️ `downloadUpdate()` 里 `sanitizeFileName(file.name) ?? 'update.exe'` 的兜底：
  清单里的文件名带分隔符时，落盘名与清单名对不上 ⇒ `findCached()` 查不到 ⇒
  未签名包会因「没有清单里的 SHA-512 可核对」被拒（**fail-closed，安全**）⇒
  **不在本轮范围**，单独记一条；
- ⚠️ `isInsideDir` 在「只收裸名」的口径下是**冗余**的（死代码）⇒ 保留（不拆防线），但不再指望它防路径穿越；
- ⚠️ 真机复验依赖**新构建** ⇒ 本轮的验收止于「单测 + 契约测试 + e2e」。
