# T61 设计规格：README 补 Release 下载入口

## 1. 起因

T60 把仓库公开发布到 GitHub（`pure2199/sanlos-music`，Public），随后的发布任务又把
**Release `v0.1.0`** 发到了线上（tag → `69bce2b`，4 个资产全部 `state: uploaded`，且已
实际下载校验过字节数与 sha256，4/4 匹配）。

但 **README 里没有下载入口**：

- 首屏是徽章 + 一句话简介 + 技术栈 + 界面预览 → 读者看完不知道**去哪拿安装包**；
- 「三、快速开始」只有「开发」与「构建与打包」两个**开发者向**小节；
- 「七、常见问题」里连「安装包在哪」都没有。

⇒ 一个普通用户（会用自己的 NAS、会装 Windows 软件）打开这个公开仓库，**找不到任何一处
下载二进制的地方**。Release 已经在那里了，只是没人指路。

### 1.1 目标

- 首屏一眼看到「**有现成的安装包可下**」，并能一键跳到 Release 页；
- 「快速开始」里有一节**面向普通用户**的下载说明：下哪个、下完怎么用、会不会被
  SmartScreen 拦、免登录能不能用；
- 下载物的大小与 sha256 **照实写出来**（可被读者自行校验，不做「大概 80MB」这种含糊表述）；
- 口径**不夸大**：未签名就说未签名，中继限速就说限速。

### 1.2 不做什么

- 不改任何**运行时行为**（本轮只动 Markdown 文档）；
- 不 bump 版本号（当前版本仍是 `0.1.0`）；
- 不改 Release 本身（资产、tag、notes 都不动）；
- 不把 `latest.yml` / `.exe.blockmap` 写进「下载表」——它们是**自动更新用的清单**，
  普通用户不需要手动下载；
- 不引新依赖、不动 CI。

## 2. README 的改动口径

### 2.1 首屏：一句下载号召

位置：**徽章行之后、简介与技术栈之后、「界面预览」之前**（读者在还没看到截图时就知道
有没有现成安装包）。

形态：一行 blockquote 提示 + 一个指向 `/releases/latest` 的链接。

- 指向 **`/releases/latest`** 而不是 `/releases/tag/v0.1.0` —— 前者在出 v0.1.1 之后
  自动指向新版本，不会指着一个旧 tag；
- 文案里**带出当前版本号 `v0.1.0`**，让读者知道现在能拿到什么；
- 明确「**免登录直接下载**」，把「要先有 NAS 才能用软件」这个误解挡掉（未登录时主区
  默认就是「本地音乐」页）。

### 2.2 「三、快速开始 → 下载安装」小节

位置：**排在「开发」「构建与打包」之前** —— 这一节整节是给普通用户的，开发者往下翻
就是了。

内容四块：

1. **下载表**：文件名 / 精确字节数 / sha256。 sha256 是**已实测**的值（本地下载远端资产
   逐个重算，与 GitHub digest 一致），读者可自行复算；
2. **SmartScreen 说明**：产物**未做代码签名** → Windows 会拦 → 「更多信息」→「仍要运行」；
   顺带给出 `/S` 静默安装参数；
3. **首次使用**：装完打开 → 顶栏「连接」→ 两种登录方式（链到「二、两种登录方式」）；
   并说明**没 NAS 也能当本地播放器用**；
4. **清单文件说明**：`latest.yml` 与 `.exe.blockmap` 是**自动更新用的清单**，不用手动下载
   （避免读者把四个文件全下下来问「这个怎么装」）。

### 2.3 锚点

README 里用到的文内锚点必须与 GitHub 生成的锚点**逐字一致**：

| 文内链接 | 目标标题 | GitHub 锚点 |
|---|---|---|
| `[下载安装](#下载安装)` | `### 下载安装` | `#下载安装` |
| `[二、两种登录方式](#二两种登录方式)` | `## 二、两种登录方式` | `#二两种登录方式`（顿号被 GitHub 去掉） |

⚠️ 标题里**不要**加「（推荐）」之类的括号 —— GitHub 会把全角括号一并去掉，锚点就变成
`#下载安装推荐`，与手写的 `#下载安装` 对不上。「普通用户看这节」的信息放在正文首句，
不进标题。

## 3. 数据口径（全部为已实测值，不得凭印象写）

| 项 | 值 |
|---|---|
| Release 页 | https://github.com/pure2199/sanlos-music/releases/tag/v0.1.0（HTTP 200 实测） |
| 最新版入口 | https://github.com/pure2199/sanlos-music/releases/latest（HTTP 200 实测） |
| tag | `v0.1.0` → `69bce2b` |
| 安装版 | `FN-Music-Setup-0.1.0.exe`，86,065,585 字节，sha256 `d96bb61378b41e867f29c2ac3ced18fc1b125ea89ac9600b827f26c98731c5df` |
| 便携版 | `FN-Music-Portable-0.1.0.exe`，78,973,187 字节，sha256 `d7317c6b5890d183a612d75614df749bff6fcb71ad45032c47164a2720fda3f8` |
| 自动更新清单 | `FN-Music-Setup-0.1.0.exe.blockmap`（90,175 字节）、`latest.yml`（344 字节） |

⚠️ 字节数写**精确字节**，不写「约 82MB」—— GitHub 页面用十进制 MB、
Windows 资源管理器用 MiB，两种「约」对不上，读者会以为下错了。

## 5. 验收点

1. README 里两个 Release 链接**实际可达**（HTTP 200）；
2. 下载表的**文件名、字节数、sha256** 与 GitHub 已上传资产**逐字一致**；
3. 两个文内锚点与标题**对应得上**；
4. 新增 / 改动的文件：无 BOM、纯 LF（README 原为 LF）、无 U+FFFD、无 NUL 字节、
   私值扫描 0 命中；
5. `tsc --noEmit` exit 0；vitest **1862 条不增不减**；
6. `docs/changelog.md` 的表格行没被改坏（Markdown 表格结构完整）。

## 6. 风险与遗留

- **README 的下载表会随版本变**：发新版时 sha256 与字节数要一起更新 ⇒ 写进本规格，
  下次发布时对着资产表核。
- **未签名状态会长期存在**：没有代码签名证书之前，SmartScreen 拦截是常态，README 里
  如实说明（不写「已签名」这种假话）。
- **本轮不动 `scripts/pack.cjs` 的跨卷 EXDEV 缺陷**（发布时已坐实：拷到桌面的那份产物
  字节损坏、`latest.yml` 变 0 字节）⇒ 另开任务。
