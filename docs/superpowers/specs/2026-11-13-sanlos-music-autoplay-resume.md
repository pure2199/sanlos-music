# T89-⑲ 规格：启动自动播放 + 记住播放位置续播

> 两个功能**一起做**，因为它们共用同一份数据：**「上次是哪一首、播到第几秒」**。
> 没有位置记录，自动播放就无从谈起；没有自动播放，位置记录只是个摆设。

---

## 一、任务与现状（**已查证的事实**，带文件与行号）

### 1.1 需求

- 用户要「**打开软件自动播放**」；
- 用户要「**续播**」——即记住上次播到哪，重开后接着播；
- 两者**一起做**。

### 1.2 现状：**两个都还没有**

| 功能 | 现状 | 证据 |
|---|---|---|
| 打开软件自动播放 | ❌ 无开关、无逻辑 | ① 偏好文件白名单只认 11 个键，**没有** `autoplay`（`electron/ipc.ts:791-794`）；② 设置页「通用」分类只有「关闭窗口时」两档 + 窗口尺寸提示（`src/components/SettingsPanel.tsx:410-437`）；③ 全仓库唯一的 `autoplay` 字样是浏览器拦截播放时的**报错文案**（`src/player/engine.ts:1376`） |
| 续播（记住位置） | ❌ 位置是**纯内存态** | ① `position` 只在 `playerStore` 里（`src/state/playerStore.ts:68`），从不落盘；② 主进程明确把播放状态定性为「**临时态，不落盘**…它不是用户偏好」（`electron/main.ts:131-141`）；③ `localStorage` 只有两个键：`fnmusic-local-history`（本机播放记录，**只有曲目标题等，不含位置**）与 `fnmusic-settings`（上次用的服务器地址）——**没有任何地方存播放位置** |
| 续播（恢复上次曲目） | ❌ 启动只恢复**会话**与**偏好** | 启动时 `sessionStore.restore()` 恢复登录态、`appPrefsStore.load()` 恢复偏好，**没有**任何一条路径去恢复曲目或队列 |

### 1.3 ⚠️ 三个**容易混叫**的东西，其实**已经有了**（本任务**不动**它们）

| 名字 | 实际含义 | 状态 |
|---|---|---|
| 「后台续播」 | 关闭窗口 = **隐藏窗口**，音乐继续放 | ✅ 已有（`closeBehavior` 默认 `hide`，`src/state/appPrefsStore.ts:40`） |
| 「偏好跨重启恢复」 | 主题 / 播放模式 / EQ / 音质档 / 歌词源 / 窗口位置尺寸 | ✅ 已有（`prefs.json`，白名单见 `electron/ipc.ts:791-794`） |
| 「最近播放」 | 历史页里「本机播过哪些歌」 | ✅ 已有（`src/state/historyStore.ts`） |

⚠️ **「最近播放」不是续播**：它只记**曲目**，不记**位置**，也不会自动续上。

## 二、目标与**明确不做**的事

### 2.1 目标

1. 播放时**记住**「哪一首、播到第几秒」；
2. 启动时（且 NAS **已连接**）**自动恢复**那一首，并**从该位置继续播**；
3. 设置里能**关掉**「启动时自动播放」。

### 2.2 明确**不做**

| 不做 | 理由 |
|---|---|
| 恢复**播放队列**（只恢复单曲） | 队列是**上下文**（从哪个歌单点的），跨重启恢复它语义模糊、收益低 |
| 自动连播策略（播完自动下一首） | 那是**播放模式**的职责，`queue.ts` 已经实现，不重复造 |
| 多设备 / 云同步「上次播放」 | 与「纯本地客户端」的定位不符，且要动服务端 |
| 播客式的「上次听过的列表」 | `historyStore` 已经覆盖 |

## 三、存储位置：**两条线各归其位**（关键决策）

| 数据 | 性质 | 存哪 | 理由 |
|---|---|---|---|
| 「启动时自动播放」开关 | **用户偏好** | `prefs.json`（新增白名单键 `autoplay`） | 它和 `closeBehavior` 是**同一类**东西（都是「要不要这样」的开关）⇒ 走既有的偏好单一真相源 |
| 「上次是哪一首、播到第几秒」 | **运行状态** | `localStorage`（新键 `fnmusic-resume`） | 与 `fnmusic-local-history`（本机播放记录）**同族**；`prefs.json` 的语义是「偏好」，塞状态进去会污染那条边界 |

**为什么不放主进程内存？** 主进程重启就没了 ⇒ 等于没实现。

**为什么不放 `session.bin`？** 那是 DPAPI 加密的**凭证**文件；播放位置**不是凭证**，混进去会破坏「偏好 / 状态 / 凭证」三者分离的既有纪律。

⚠️ **因此 `prefs.json` 的白名单只加 `autoplay` 一个键**（11 → 12 个），**播放位置绝不进 `prefs.json`** ——
这正是 `test/island-visibility-wiring.test.ts` 静态钉死的纪律（「临时态不落盘」）。

## 四、数据模型

```ts
/** 上次播放的记录（**只存恢复必需的 7 个字段**）。 */
interface ResumeRecord {
  id: string          // 曲目 guid
  title: string       // 歌名（显示用）
  artist: string      // 歌手（显示用）
  coverId: string     // 封面 id（显示用）
  duration: number    // 时长（秒）——判定「距结尾多远」用
  positionSec: number // 上次播到的秒
  updatedAt: number   // Unix 毫秒
}
```

### ⚠️ 为什么**不存完整 `Song`**，也**不靠记录兜底播放**

`Song` 有 20+ 个字段，大部分与恢复无关；只存 7 个足够「显示 + 定位」。

但**绝不能**用这条记录直接构造一个 `Song` 去播：

| 字段 | 若留空会怎样 |
|---|---|
| `codec` | 引擎用 `song.codec` 判断 Chromium 能不能解（`src/player/engine.ts:761-767`）⇒ 空串会被判成「解不了」⇒ 走兜底转码 ⇒ **可能根本播不起来** |
| `favorite` | 界面会显示「未收藏」，用户一点就可能把服务端的收藏**反过来写掉** ⇒ **误操作数据** |

⇒ **恢复必须拿到曲库里的完整曲目**；拿不到（曲目已删）⇒ **不恢复**，而不是拿残缺数据硬播。

## 五、关键决策（6 条，每条都有代价）

| # | 决策 | 理由 / 代价 |
|---|---|---|
| **D1** | 记录**不是每秒写**：只在「切歌 / 暂停 / 每 10 秒」三个时机写 | 进度每秒变 ⇒ 每秒写盘会把存储打爆；代价：异常退出最多丢 10 秒进度 |
| **D2** | 值得恢复的条件：**位置 ≥ 30 秒** 且 **距结尾 ≥ 15 秒** | 刚开头 3 秒就续 ⇒ 用户觉得「怎么从头开始了」；差 5 秒就播完还续 ⇒ 荒唐。代价：很短的歌可能永远不满足（那就从头播，合理） |
| **D3** | 恢复**必须等 `connected`** | 没登录就拿不到播放地址 ⇒ 恢复必然失败。代价：启动后要等会话恢复完才出声（一般 1 秒内） |
| **D4** | 恢复**必须拿到完整曲目**（扫一次曲库按 id 找） | 见第四节。代价：多一次 `size=2000` 的 `/track/list` 请求（实测全库 797 首 ⇒ 一次拿完） |
| **D5** | `seek` **延后到 `duration > 0` 之后**再执行 | `engine.seek()` 直接写 `element.currentTime`（`src/player/engine.ts:957-965`）；元数据未就绪时写会**落空**。代价：起播后有极短的一瞬从 0 秒开始 |
| **D6** | 关掉「启动时自动播放」**只停恢复，位置照记** | 用户临时关一下再打开，还能续上；代价：关着也会攒一条记录（可手动清除） |

## 七、行为规格（**逐条可测**）

| # | 行为 |
|---|---|
| **B1** | 播放中，每 **10 秒** ⇒ `localStorage` 里那条记录的 `positionSec` 会更新 |
| **B2** | 切歌（下一首 / 上一首 / 点别的歌）⇒ 记录换成**新曲**，`positionSec` 从 0 起 |
| **B3** | 暂停 ⇒ **立即**写一次记录（不必等 10 秒） |
| **B4** | 启动时（`connected` 且 `autoplay=true` 且记录有效且曲目还在曲库）⇒ **自动播放**那一首，并 **seek 到记录位置** |
| **B5** | 记录无效（无记录 / 位置 < 30 秒 / 距结尾 < 15 秒 / 曲目已不在曲库）⇒ **不自动播**，界面正常 |
| **B6** | `autoplay=false` ⇒ **不自动播**（但位置**照记**） |
| **B7** | 设置页能开关「启动时自动播放」，**重启后仍保持**（落在 `prefs.json`） |
| **B8** | 设置页能「清除上次播放记录」⇒ 清除后启动**不恢复** |
| **B9** | 恢复过程中 NAS 不通 ⇒ **不崩、不出声**、界面正常（错误按既有路径走） |
| **B10** | 自动播放被浏览器策略拦截 ⇒ 沿用**既有**的 `NotAllowedError` 文案（`src/player/engine.ts:1376`），不新造提示 |
| **B11** | `localStorage` 不可用（隐私模式 / 配额满）⇒ **静默降级**为「只在本次运行内有效」，不崩 |
| **B12** | 记录里的陌生值（`positionSec: 'abc'`、`updatedAt: null`）⇒ **整条丢弃**，不构造出半截数据 |

## 九、风险与边界

| 风险 | 处置 |
|---|---|
| 启动就出声，可能突兀 | 有开关；且**只有存在「未播完的上一首」时才出声**，老用户升级后行为不变 |
| `localStorage` 里有歌名/歌手（隐私） | **纯本地，不出网**；设置页可一键清除 |
| 曲库极大时扫不全 | 最多扫 3 页（6000 首）；找不到就**不恢复**（如实），不硬播残缺数据 |
| 恢复时 NAS 已离线 | 不恢复，不出声（`connected` 为假时根本不会走到恢复） |
| 与「后台续播」混淆 | 两者**正交**：后台续播 = 窗口关了还播；本任务 = 重开后接着播 |
