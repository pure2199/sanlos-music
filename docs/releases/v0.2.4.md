# Sanlos Music v0.2.4 —— 发布说明

> 相对 **v0.2.3** 的一次更新：**自动更新的签名链路** ——
> 「允许安装未签名的更新包」这个开关**以前是一条死路**（勾了也没用、还**一条报错都没有**），
> 现在**真的生效**；同时**产物能真的带上签名**了。

发布日期：**2026-11-10**

---

## 一、这一版改了什么

### 1. 「允许安装未签名的更新包」**真的生效**了

以前你勾了它、点了「启动安装」，会被这样拒掉：

```text
安装包签名校验未通过，已拒绝启动：未配置「预期的代码签名者」→ 不允许启动安装器
```

**根因**是**两处**各自看起来都合理、叠在一起就把功能堵死了：

| 位置 | 以前的行为 | 问题 |
|---|---|---|
| 主进程探测签名 | 「预期的代码签名者」为空 ⇒ **提前返回**，**连文件都没读** | 主进程**永远不知道**这个包有没有签名 ⇒「未签名放行」那道闸**永远不成立** |
| 渲染层判定 | 按「状态是不是 `NotSigned`」判 | 主进程给的是 `NotChecked` ⇒ 判定**永远为假** |
| 渲染层提前拦截 | 「预期签名者」为空 ⇒ 直接拒绝、不调主进程 | 比主进程**更严** ⇒ 功能被**静默堵死** |

现在：

- 主进程**一律探测**文件，再按探测结果分流；
- 判定逻辑收到**一份**（`evaluateSignatureGate`），**主进程与渲染层共用**；
- 判定口径**解耦**：「允许安装未签名包」管的是「这个包**有没有**签名」，
  「预期签名者」管的是「**有**签名的话，是谁签的」。

### 2. 判定矩阵（**每一格都钉在测试里**）

| 安装包 | 预期的代码签名者 | 允许安装未签名 | SHA-512 | 结果 |
|---|---|---|---|---|
| 没签名 | 空 / 任意 | **开** | 相符 | ✅ **放行** |
| 没签名 | 空 / 任意 | 关 | 任意 | ❌ 拒绝（默认行为**不变**） |
| 没签名 | 任意 | 开 | 不符 / 无从核对 | ❌ 拒绝（哈希是硬闸） |
| 有签名 | 与实际一致 | 任意 | 任意 | ✅ 放行 |
| 有签名 | 空 | 开 | 任意 | ❌ 拒绝（授权只管「未签名」的包） |
| 有签名 | 与实际不符 | 开 | 相符 | ❌ 拒绝（授权**也**救不了） |
| 探测失败 | 任意 | 开 | 任意 | ❌ 拒绝（不猜） |

⇒ **只放宽了「发布者身份」这一条**：SHA-512、同源校验、路径越界**一条都没松**。

### 3. 设置页那三段说明文案**不再自相矛盾**

旧文案一边说「未配置预期签名者时只允许下载，不允许安装」，
一边又说「勾选『允许安装未签名的更新包』后才允许安装」—— **两段描述互斥的规则**。
现在口径统一，且按钮按**已保存**的授权判定（只勾了**没保存**会提示「保存后才会生效」）。

### 4. 产物**能真的带上签名**了

- 新增本地**自签**证书工具 + **打包后签名断言**：
  配了证书却没签上 ⇒ **打包直接失败**（electron-builder 本身可能只警告 ⇒ 不能信「打包成功」）；
- **不用改任何配置**：设 `WIN_CSC_LINK` + `WIN_CSC_KEY_PASSWORD` 就签，没设就跳过；
- ⚠️ **公开产物这一版仍然不签名**（真实 OV 证书未办理）—— 理由见第四节。

### 5. 顺带修掉一个真缺陷：中文签名主体名乱码

PowerShell 往**管道**写 stdout 时用的是**控制台代码页**（简体中文机器 = 936 / GBK），
**不是 UTF-8** ⇒ 客户端读到的签名者主体名是**乱码** ⇒ 与你填的「预期的代码签名者」
**永远对不上** ⇒ 带签名的包会被**莫名其妙**地拒掉。
现在签名者主体走 **base64(UTF-8)** ⇒ **与代码页无关**。

### 工程

- 单元测试 **2195** 条（+31）；Playwright E2E **34** 条（真实 Electron）。
- **10 条变异自证全部被抓住**（T85 五条 + T86 五条）。
- **真包实测**：带签名的安装包（真 PowerShell 探测，不是 mock）跑通更新链路 **8 / 8**。

`FN-Music-Setup-0.2.4.exe.blockmap`（electron-builder 的差分清单）。

⚠️ **更新服务器地址留空即可**（v0.2.2 起的口径）：主进程会自动用项目自己的 Releases
（清单与安装包**同源**，符合客户端的校验规则）。若你想手动填：

```text
https://github.com/pure2199/sanlos-music/releases/latest/download
```

### 想用「一键更新」？这一版起要手动开一次授权

本项目暂未办理代码签名证书 ⇒ 安装包**没有签名** ⇒ 想让应用自己装更新，需要：

1. 设置 →「更新」→ 勾选「**允许安装未签名的更新包**」→ **点「保存」**（**不保存不生效**）；
2. 「检查更新」→「下载更新」→「启动安装」。

⇒ 这一步**只放宽了「发布者身份」**：安装包仍必须 **SHA-512 与清单相符**、
必须与清单**同源**、路径不许越界。

## 三、怎么用

- **不用做任何设置**：装了就能用 —— 歌词来源、卡拉OK、队列、码率切换等与 v0.2.3 一致；
- **两种登录方式**：
  - **方式 A（推荐）**：填 **FN ID**，应用自动构造候选链路并并行探测，列出可达地址供你选；
  - **方式 B**：直接填 **NAS 地址 + 账号口令**（IP 只填 host 会自动补 `5666` / `5667`）。
- **没 NAS 也能用**：未登录时主区默认就是「本地音乐」页，可「添加文件 / 添加文件夹」
  导入本机音乐直接播；下载过的曲目也能直接播。
- ⚠️ **中继限速**：走中继链路（`https://<fnId>.fnos.net`）时播放会限速，
  客户端会带上 `mode=relay` Cookie —— 这是中继的**硬性关卡**，不带会返回 HTML 错误页。

## 四、已知影响（如实标注）

- ⚠️ **这一版的公开产物仍然没有代码签名** ⇒ Windows 仍会提示「未知发布者」。
  真实 OV 证书需要主体材料 + CA 核验 + 硬件 token + 付款，**尚未办理**。
- ⚠️ **签名 ≠ 不弹窗**：即便将来签了名，SmartScreen 判的是**文件哈希的信誉**，
  **第一版照样弹**；要靠真实下载量 + 干净安装积累信誉（通常数周、数百次下载），
  而且**每次重新打包哈希就变 ⇒ 信誉清零**。唯一彻底免的是上 **Microsoft Store**。
- ⚠️ **「允许安装未签名的更新包」默认仍是关的**，需要你**手动勾选并保存**。
- ⚠️ **只对「确实没有签名」的包生效**：万一产物带上了签名而签名者与预期不符，
  **授权救不了**（那是另一个、更糟的情况）。
- ⚠️ **不校验证书信任链**（老口径不变）：我们只保证「这个文件确实由预期的人签的」，
  信任链由 **Windows 自己**判断。

## 五、安全边界（不可放宽）

- **渲染层永远拿不到凭证**：账号口令用 Windows **DPAPI**（`safeStorage`）加密后落盘；
  渲染层只能通过主进程的协议代理取数据，拿不到 token。
- **唯一出网通道**是应用自己的 **NAS 代理**；外部歌词源的抓取也全在主进程。
- **自动更新只查、只报**：不静默下载；下载后必须过 **SHA-512 校验**，
  且安装包地址必须**与更新清单同源**（清单不能把安装包指到别处）。
- **启动前再验一次**：签名 + SHA-512 都**再核对一遍**（用主进程自己缓存的清单，
  不是渲染进程给的值）；安装路径必须**仍在下载目录之内**。
