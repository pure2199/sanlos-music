> 「下一个版本起会带签名」这个预期**没有兑现** ⇒ 后续版本**继续未签名发布**，
> 改用**构建来源证明**（attestation）作为「发布者身份」的替代信任锚。

**为什么不等签名再发版**：签名申请**批不批、何时批不由我们决定**，而审核口径里我们最弱的一项
是「可验证声誉」（0 star / 0 fork / ~73 下载）⇒ 发版被外部审核无限期卡住并不划算；
何况**产物至今本就未签名**（v0.2.4 就是未签名发的），自动更新链路也**早已内置**
「允许安装未签名的更新包」开关 ⇒ **签名从来没有卡住过功能**。

**签名链路整体搬进 CI** —— SignPath 免费计划以「**可信构建**」为前提 ⇒
**本机手工打包的包签不了** ⇒ 发版流程改为「CI 打包 →（可选）送签 → 人工审批 → 校验 → 发版」。

## 0.2.4 —— 2026-11-10

相对 **v0.2.3** 的一次更新：**自动更新的签名链路** —— 「允许安装未签名的更新包」
这个开关**以前是一条死路**（勾了也没用、而且**一条报错都没有**），现在**真的生效**；
同时**产物能真的带上签名**了（打包后自动断言）。完整发布说明（含下载与校验）见
[`docs/releases/v0.2.4.md`](./releases/v0.2.4.md)。

**自动更新的签名链路补齐了** —— 两件事：

1. **签名闸修好了**（T85）：「允许安装未签名的更新包」这个开关**以前是一条死路**（勾了也没用、而且**一条报错都没有**）：主进程在「预期的代码签名者」为空时**压根不探测文件** ⇒ 永远不知道这个包到底有没有签名 ⇒「未签名放行」那道闸**永远不成立**；渲染层还有**两道更严**的拦截（提前 return + 按钮直接 disabled）。现在**两边共用同一份判定口径**。
2. **产物能真的带上签名了**（T86）：新增本地**自签**证书工具 + **打包后签名断言**（配了证书却没签上 ⇒ **打包直接失败**）；并修掉一个**真缺陷** —— PowerShell 走管道时用的是**控制台代码页**（936/GBK）⇒ **中文主体名直传必乱码** ⇒ 带签名的包会被**莫名其妙**地拒掉。

### 变更

| 领域 | 内容 |
|---|---|
| **判定口径** | 「允许安装未签名的更新包」与「预期的代码签名者」**解耦**：包**没有签名** + 用户**显式授权** + 清单 **SHA-512 相符** ⇒ **放行**（**不要求**填预期签名者）；包**有**签名 ⇒ 仍必须与预期签名者一致（没填 / 不符 ⇒ **拒绝**，授权**也救不了**） |
| **一份口径** | 判定逻辑收到 `shared/update.ts` 的 `evaluateSignatureGate()` —— **主进程与渲染层共用同一份**（T85 的根因就是两边各判各的）；主进程**一律探测**文件，不再因「没填预期签名者」提前返回 |

| **中文主体名** | 签名者主体改走 **base64(UTF-8)**（T86）—— PowerShell 往管道写 stdout 用的是**控制台代码页**（简体中文机器 = 936/GBK）⇒ 主体名含中文时直传是**乱码** ⇒ 与用户填的「预期签名者」**永远对不上** |

### 已知影响

- ⚠️ **自签证书不可信** ⇒ 对外发布时 Windows 仍提示「未知发布者 / 不受信任的证书」；**自签产物只用于本地/内部把链路跑通**，**不发到公开 Release**。

### 修复

| 修复 | 影响 |
|---|---|
| **`fnm://` 协议特权被 `fnml://` 覆盖** | Electron 的 `registerSchemesAsPrivileged()` 整个进程只能调用一次，第二次会**静默覆盖**第一次 → `fnm` 不在 Blink 的 scheme 白名单里 → 渲染层 `fetch('fnm://…')` 直接抛 `TypeError: Failed to fetch` → **整个曲库都拉不出来**。现将两个 scheme **合并成一次**注册（`electron/schemes.ts` 的 `registerAppSchemes()` 是唯一正确入口） |
| `fnml://` 缺失跨源放行头 | 该 scheme 开了 `corsEnabled`，Chromium 会强制校验 → 响应不带 `Access-Control-Allow-Origin` 会被浏览器直接拒收 |
| 收藏态多真相源 | 搜索页与收藏页各说各话 → 统一为单一真相源 |
| 分页卡死后无出路 | 停下后提供「继续加载」入口，并复位护栏 |
| 歌单写回后选中态残留 | 写回成功后清空选中 |
| 批量加歌到歌单后**歌单详情仍是旧列表** | 写回成功后未刷新歌单曲目缓存 → 用户打开歌单看到旧（空）列表 → **假成功**。现写回成功后刷新歌单曲目与歌单列表 |
| 批量工具条浮层被裁掉 | 工具条原本 `overflow: hidden` → 绝对定位的「加入歌单」面板被裁掉**永远点不到**。现改为 `overflow: visible`，高度恒定靠固定高度 + 不换行保证 |
| 播放模式重启即丢 | 播放模式只活在内存里，重启应用回到「顺序播放」。现落进 `prefs.json`（`AppPrefs.playMode`），并与队列、引擎**三处同步**（避免「界面写着随机播放、实际按顺序播」的假状态） |
| 播放器错误不可见 | 播放条补上第三行：错误（`role="alert"`）/ 转码中 / 有损说明（`role="status"`） |
| **点 EQ / 队列按钮，屏幕上什么也不出现** | 播放条 `.fnm-playerbar` **没有 `position`** → 两个浮层（`position: absolute; bottom: 100%`）找不到定位祖先 → 一路向上找到**初始包含块（视口）** → 面板整个跑到**屏幕上方之外**。DOM 里确实有面板（`innerText` 读得到），但用户看不见 → 极易误判成「没渲染」。现给播放条补上 `position: relative` 作为定位锚点 |
| **全屏播放页的队列盖住关闭按钮** | `.fnm-fullplayer__body` 用了 `align-items: center` → 右侧面板高度 = **内容高度** → 队列一长就**溢出** body → 队列行**盖住右上角 × 按钮**与底部播放控件（真机实测：× 按钮点不到，Playwright 报「queue-row 拦截指针事件」）；歌词区也挤在顶部、右半屏大片留白。现改 `align-items: stretch` → 面板撑满、队列自己滚动 |
| **同一句歌词显示两遍** | 实测 NAS 对**同一首歌**返回**两条 `source` 不同（1 / 2）但内容逐字相同**的歌词记录（是同一份 LRC 的两份拷贝，不是「原文 + 翻译」）→ 第二条被当翻译挂上 → 每句都显示一遍大字 + 一遍同样内容的小字。现**两层去重**：条目级（整篇实质相同且偏移相同 → 整条丢弃）+ 行级（实质相同 → 不挂翻译）。真翻译（内容不同）照常显示 |
| **全屏页背景永远是白底（取色失败后不再重试）** | 封面刚切过来时可能还没加载好 → 第一次取色失败 → **失败被缓存** → 这一首歌**到重启为止都不再取色** → 背景永远停在兜底色。现**只缓存成功结果**，失败后**有限次重试**（3 次 / 间隔 1.5s） |
| **改了「自定义歌词 API 模板」，歌词还是上一个源的** | 主进程歌词缓存的键是 `源\|歌名\|歌手\|专辑\|时长` —— **没有把模板算进去** → 换了模板（= 换了一个完全不同的词源）却**命中旧缓存** → 用户在设置里换源了，界面上还是**旧源的歌词**。现把**模板**也计入缓存键（仅自定义源），换模板即刻生效 |
| **「音频加载停滞」误报成红色错误** | 媒体元素的 `stalled` / `waiting` 按规范只是「正在取数据、数据一时没到」的**瞬时提示**（播放通常**自行恢复**），早先却写进了 `errorMessage` → 界面挂**红字**（`role="alert"`）而**音乐其实照放**；更糟的是**没人清它** → 红字一直挂到用户切歌（公网中继带宽有限时几乎每首歌开头都会中一次）。现改为独立的「**缓冲中…**」状态（**灰字** `role="status"`），数据到了**自动消失**；真错误仍优先 |
| **点「退出登录」没反应** | 登出会**先等网络**（`await session.request('user/logout')`），而会话层的请求**没有任何超时** → 网络一抖动就永久挂住 → 渲染层 `await` 不返回、按钮 `disabled` → 界面看着就是「点了没反应」。现改成「**先启动通知 → 立刻清理本地会话 → 立刻返回**」：通知在后台自己跑完，失败也不影响登出 |
| **界面老是有顿卡** | 主进程会话层的请求**不传 `signal`、也没有超时** → 网络抖动时挂到 TCP 超时（Windows 默认可达 21 秒以上）→ 界面顿住；token 一旦失效，每个请求还变成 **3 个网络往返**（失败 → 重新登录 → 重试），而重新登录失败时旧代码**照样重试** → 白等一个往返。现给所有会话请求加 **30 秒超时**（真取消 + `Promise.race` 双保险），且**续期失败不再重试**（直接把 99999 交回 → 渲染层立刻切回登录页） |
| **词岛的歌词不是「一行居中」** | 词岛改单行模式后有**两层**问题：① 单行模式的**画布高度 = 整份歌词的总高**（行数 × 34px）→ 歌词区被撑到几千 px → 胶囊（96px）裁剪后露出的是「**歌词表的垂直中点**」，不是当前行；② 量视口的 `useEffect` 依赖写死 `[]` → 挂载那一刻歌词还空（走**空态分支**，**没有视口节点**）→ **歌词到达后不会重跑** → 居中一律按**兜底高度 400** 算。⚠️ 双行模式**完全不受影响**（它用不到视口高度）→ 这个缺陷在双行下**看不出来**。现 CSS 加 `align-self: stretch`（歌词区高度 = 胶囊内容区）+ 组件 effect 依赖加 `safeLines.length`（歌词到达后**重新量**） |
| **词岛频谱柱「右边几乎是空的」** | 频谱初版按「16 段各分一半」（左 = 低频 8 段、右 = 高频 8 段）→ **高频段的能量天然远低于低频段**（真机实测：低频柱 46%、高频柱 4%）→ **右边几乎全是 4% 的小点**，整条胶囊**左右不对称**。现改成「**同一组 8 段 + 右端取逆序**」→ 左右显示的是**同一组**频段 ⇒ **两边永远一样饱满**（真机复核：左右高度逐根互为逆序，完全对称） |
| **灵动歌词「逐字发光」不顺滑** | 词级高亮是**整词跳变**：词一到就整词变色 ⇒ **每个词的边界都在「闪一下」**。现改成**卡拉OK 渐进填色**：当前词按**词内连续比例**（`wordProgress`）从左到右染色，**颜色边界连续推进**。实现上用 `background-clip: text` + 渐变（**不改字形** → 逐字着色层与底层原文依旧严丝合缝），未填的部分**透出底层原文**（就是「还没唱到」该有的颜色）；**整词发光的光晕一并移除**（光晕会把填色边界糊掉）。⚠️ **只影响词岛**，经典悬浮窗与歌词舞台**一字不变** |
| **词岛的长歌词只显示得下一半** | 灵动态词岛的当前行是**定高 44px 的盒子**（`height: 44px`），而歌词允许换行 → 长句折成两行 = 88px 内容**溢出盒子**；词岛的歌词视口又是 `overflow: hidden` → **第二行被整个裁掉**（真机实测：文字占到 91px，可视区下沿只有 85px；且越往歌后面裁得越狠）。现把当前行改成**可长高**、**行高 32px**，并让歌词视口**自己居中**（不再靠 `LyricView` 的滚动定位）→ 折两行 = 64px，**两行完整可见**，且**胶囊高度不变**（仍是 96px）。⚠️ **只影响词岛**，主界面 / 经典悬浮窗 / 歌词舞台**一字不变** |
| **整份歌词整体偏晚** | 歌词按**媒体时间**渲染，而声音从「播放位置」到「用户耳朵里」有一段**物理延迟**（声卡缓冲 / WASAPI 共享模式 / 蓝牙耳机编解码往返）⇒ 整份歌词**统一偏晚**（行级时间戳本身是准的，差的是**渲染到听见**这一段）。现按**音频输出延迟**把歌词**整体延后**（媒体位置 T 的声音在 T+L 才到耳朵 ⇒ 歌词也要等到 T+L 才显示），**读不到延迟就不补偿**（行为与此前完全一致，不谎称已补偿），**换输出设备立即重算**、不必切歌。⚠ **蓝牙耳机的编解码往返在操作系统之外**，浏览器测不到 ⇒ 蓝牙下可能仍偏晚，**待真机校准** |
| **标准音质永远回退原始音质 + 主进程弹「A JavaScript error occurred in the main process」** | NAS 转码产物的响应带 `Content-Disposition: attachment; filename="占位曲目一 - 占位歌手二.mp3"`（**UTF-8 原始字节**）；主进程走 Chromium 分区栈（`session.fetch`）时，Chromium 按 **UTF-8** 解码响应头 → 得到真正的 CJK 字符（`占` = U+5360 = 21344，**正好落在报错的 index 22**）→ Electron 内部把它塞进 undici 的 `Headers` → **ByteString 只允许 0–255** → 抛 `TypeError`。该抛出发生在**事件回调**里 → 变成**主进程未捕获异常**（弹错误框），且那个请求**永远不会返回** → 代理的二进制路径挂死 → 标准音质一直回退原始音质（Node 直连不崩：Node 的 undici 按 **latin1** 解码响应头 → 中文变乱码字节）。现把代理的**二进制路径**改走 Electron 的 `net.request`（**同一个分区 session** ⇒ 证书放行语义一字不变），它的响应头是**普通字符串记录**、**不经过** ByteString 校验；转发给渲染进程时再逐个做 ByteString 安全检查（含非 ASCII 的头一律**跳过**） |
| **仓库与工作区残留用户私有标识与明文口令** | T58 一次性抹除：已跟踪的**代码注释与文档**、gitignored 的**探针脚本与 agent scratch**、仓库外的**台账**。⚠️ **口令从未进过版本库历史**（\`git log -S\` 0 命中，commit message 正文也扫过）。⚠️ 只改**注释与文档** → **运行时行为零变化**（把注释改回旧文本也不会有任何测试变红）；⚠️ **开发者署名**作为产品身份保留（关于页 / 安装包属性 / ICP 备案主体） |
| **新建的桌面歌词窗口停在「第 0 页」、卡拉OK 不动** | 「曲目 + 歌词」与「播放位置」是**两条不同的消息**，而主进程只缓存**最后一条**；新窗口创建时渲染进程推的那些消息**早于页面加载完成** → 被丢弃 ⇒ 窗口**拿到了歌词却没有位置** ⇒ 位置停在 0（经典悬浮窗永远停在第 0 页，灵动态词岛同理；播放时靠后续进度消息才追得上 ⇒ 平时不易察觉，**暂停时永远停在 0**）。真机 E2E 实测：经典悬浮窗里 `--karaoke` 词的数量 = 0。现主进程**分开缓存**两类消息，窗口加载完成时**两条都补发** |
| **托盘「没在播放」时是**空白**，任务栏按钮还是 Electron 默认图标** | 项目**根本没有应用图标资源**（无 `build/` 目录、`electron-builder.yml` 无 `win.icon`）⇒ 托盘的「默认图标」被实现成 `nativeImage.createEmpty()`（**0×0 空图**）：建托盘时就是空图；**没有封面（= 没在播放）就 `setImage(createEmpty())`** ⇒ 播放中显示专辑封面，一停就变回**什么都没有**（用户原话「任务栏图标没播放时是空的」）；封面取失败 / 解不出图也同样保持空白。现补上真正的应用图标（`build/icon.png` 256 + `build/tray.png` 32，**零依赖**脚本 `scripts/make-app-icon.mjs` 生成）：**托盘在没播放时显示应用图标**（**播放中仍显示专辑封面** —— 用户拍板）；**主窗口 / 歌词窗 / 词岛窗设 `icon`** ⇒ 任务栏按钮不再是 Electron 默认图标；**打包产物的 exe / 安装包 / 快捷方式**用同一枚图标（`electron-builder.yml` 补 `win.icon`）。⚠️ 渲染层**不碰**图标（只有主进程读文件） |
| **切了歌词源，桌面歌词不跟着变；一个源匹配不上也不会自动换下一个** | 桌面歌词（经典悬浮窗 / 灵动态词岛）**自己**取词，而取词只在「切歌 / 从关变开 / 输出延迟变化」时发生 ⇒ 用户在设置里换了歌词源，桌面歌词**一直停在旧内容**（全屏歌词页有自己的 effect，会重取）⇒ 同一个应用里两处歌词对不上。又：原先只试**选中的那一个**源，它匹配不上就**直接回落到 NAS 本地**，中间那几个线上源**根本没试过**。现把线上取词改成**源链**（首选源不中 ⇒ 依次试 网易云 → lrclib → QQ → 自定义模板，**每个源各自限时 3 秒**，链走完才回落本地）；桌面歌词**订阅偏好变化** ⇒ 切源 / 切优先级 / 改模板**立刻重新取词并重推**给悬浮窗与词岛；**界面如实显示实际命中的那个源**。⚠️ 桌面歌词**关着**时**不多打** NAS（与既有口径一致）；「不用外部」仍是一个请求都不发 |

### 已知限制

- **无代码签名** → Windows SmartScreen 提示「未知发布者」。
- **应用图标** → T75 起**不再是** Electron 默认图标（`build/icon.png` 256 / `build/tray.png` 32，零依赖生成）：托盘、任务栏按钮、打包产物的 exe / 安装包 / 快捷方式**统一**用同一枚图标。
- **不承诺字节级一致** → NSIS 安装器内嵌构建时间戳；可复现 = 同输入可重建 / 可安装 / 可运行。
- **仅 Windows x64**。
- **兜底解码只对「已下载到本地」的曲目生效**；且不支持 `dff`（本机 FFmpeg build 无 `dsdiff` 解封装器）。
- **真机联调尚未完成** —— 详见 [`calibration.md`](./calibration.md) 的 Step A–K。

## 版本号规则

遵循 **语义化版本（SemVer）** `MAJOR.MINOR.PATCH`：

| 位 | 何时递增 |
|---|---|
| **MAJOR** | 不兼容的改动（如协议、配置格式变更导致旧数据无法读取） |
| **MINOR** | 新增功能 / 新增端点 / 新增设置项 |
| **PATCH** | 缺陷修复、文案与样式调整、构建与依赖维护 |

### 版本号与打包产物

版本号取自 `package.json` 的 `version`，electron-builder 用它命名产物：

```
FN-Music-Setup-<version>.exe
FN-Music-Portable-<version>.exe
```

打包产物的 exe 版本元数据也由它写入（实测：文件版本 `0.2.0` / 产品版本 `0.2.0.0` / 产品名 `Sanlos Music` / 公司 `fnmusic-desktop`）。

### 升级版本号的流程

1. 改 `package.json` 的 `version`；
2. 同步 `package-lock.json`（`npm install --package-lock-only`）；
3. 在本文顶部新增一节；
4. 提交：`chore(release): <版本号>`。
